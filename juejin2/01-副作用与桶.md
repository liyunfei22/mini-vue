# 01 · 副作用与桶：从零写一个最小响应式

先从一个再熟悉不过的场景开始：组件里 `count.value++`，页面上用到 `count` 的地方自己更新了。问题是——**是谁记住了「这个函数用到了这个数据」？记在哪里？数据变化后又凭什么找到它？**

本章从零回答这三个问题。我们会先手写一个二十行左右的「最小响应式」，让它真的跑起来；然后逐一暴露它的硬伤——桶太粗、不分对象不分属性、裸读也收集；最后看本仓库的 `reactivity` 包是如何把一个简单的桶，演进成一张两层的「账本」的。在这个过程中会遇到几个新的问题：为什么裸读响应式对象不会产生任何订阅？数组下标越界赋值为什么要惊动 `length` 的订阅者？这些问题的答案，将构成后面所有章节的地基——组件的渲染函数，本质上就是本章的「副作用函数」。

## 1.1 什么是副作用函数

副作用函数，指的是**执行会反过来影响其他函数执行**的函数。这么说有点抽象，看两个例子就明白了：

```js
// 例一：修改全局变量
let val = 1
function effect() {
  val = 2              // val 改了，其他读 val 的代码全部受影响
}

// 例二：修改 DOM
function effect() {
  document.body.innerText = 'hello vue3'   // body 的内容变了，任何读它的代码都受影响
}
```

副作用无处不在——修改全局变量、改 DOM、发请求，都算。「副作用」这个名字容易让人以为是贬义，其实它是中性描述：**一个函数的执行结果超出了它自己的作用域**。

Vue 的响应式系统，管理的正是这样一批副作用函数：它们读了某些数据，我们希望**这些数据变化时，读过它们的副作用自动重新执行**。

## 1.2 什么样的数据算「响应式」

把上一节的意思翻译成代码。假设有一个普通对象和一个副作用：

```js
const obj = { text: 'hello world' }

function effect() {
  // 副作用执行时，读取了 obj.text
  document.body.innerText = obj.text
}

effect()                    // 页面显示 hello world
obj.text = 'hello vue3'     // 我们希望：这行执行后，effect 自动重跑，页面变成 hello vue3
```

但很明显，我们还做不到这一点。`obj` 是一个普通对象，修改它的属性，除了值本身变了，不会有任何其他反应——`effect` 不会重跑，页面也不会更新。

如果一个对象能在属性变化后，自动通知所有依赖它的副作用重跑，它就是**响应式数据**。下一节我们就来改造 `obj`。

## 1.3 第一版：Proxy 加一个桶

怎么才能「属性变了有反应」？观察上面的代码，能发现两条线索：

- `effect` 执行时，会**读取** `obj.text`；
- 我们希望响应的那一刻，是 `obj.text` 被**设置**新值时。

如果能把「读取」和「设置」这两个动作拦截下来，事情就好办了：读取时把副作用函数记下来，设置时把它取出来执行。JavaScript 里干这件事的标准工具是 Proxy——ES2015 引入的代理能力，可以拦截对象的基本操作，这也是 Vue 3 采用的方式（Vue 2 用的还是 `Object.defineProperty`）。

存放副作用的地方，我们用一个最简单的结构：一个 Set，就叫它「桶」。

```js
// —— 手写朴素版，仅用于演示 ——
let activeEffect = null          // 当前正在执行的副作用
const bucket = new Set()         // 桶：所有副作用都丢进这里

function effect(fn) {
  activeEffect = fn
  fn()                           // 立即执行一次；执行途中的属性读取会被收集进桶
  activeEffect = null
}

const data = { text: 'hello world' }
const obj = new Proxy(data, {
  get(target, key) {
    if (activeEffect) bucket.add(activeEffect)   // 读到了：把当前副作用记进桶
    return target[key]
  },
  set(target, key, newVal) {
    target[key] = newVal
    bucket.forEach(fn => fn())   // 改了：桶里的副作用全部重跑
    return true
  },
})
```

先走读一遍。我们定义了模块级的 `activeEffect` 指针，指向「正在执行的副作用」。`effect(fn)` 做三件事：把指针指向 `fn`、执行一次 `fn`、把指针清空。接着用 Proxy 包住原始数据：`get` 拦截器在**有人读属性且此刻存在活跃副作用**时，把它加进桶；`set` 拦截器在值被修改后，把桶里的函数全部执行一遍。

测试一下：

```js
effect(() => {
  document.body.innerText = obj.text   // 首次执行：obj.text 被读取，副作用进桶
})
obj.text = 'hello vue3'                // set 触发：桶中副作用重跑，页面更新 ✓
```

二十行出头，一个最小响应式就跑起来了。停下来把刚才那次「订阅→触发」完整走一遍，盯住两个变量的值：

| 步骤 | 发生了什么 | activeEffect | bucket |
|---|---|---|---|
| 1 | 调用 `effect(fn)`，指针指向 fn | `fn` | 空 |
| 2 | 执行 `fn`，读到 `obj.text`，get 拦截：把 fn 记进桶 | `fn` | `{fn}` |
| 3 | `fn` 执行完，指针清空 | `null` | `{fn}` |
| 4 | `obj.text = 'hello vue3'`，set 拦截：桶中函数全部执行 | `null` | `{fn}` |

第 4 步执行的就是第 2 步记下的那个函数——「数据变化后该跑谁」这个问题，被一个 Set 回答了。但先别高兴——它离「能用」还差得远。

## 1.4 朴素版的硬伤

往这段代码里再加一个字段、再加一个副作用，问题就藏不住了：

```js
const obj2 = new Proxy({ text: 'a', age: 1 }, handlers)

effect(() => { console.log(obj2.text) })   // 只关心 text
effect(() => { console.log(obj2.age) })    // 只关心 age

obj2.age = 2   // 打印了 text 和 age 两个副作用——问题来了
```

**硬伤一：桶不分青红皂白。** 桶里只有一个 Set，既不区分是哪个对象，也不区分是哪个属性。改 `age` 会把只关心 `text` 的副作用也拉起来重跑——结果是「改了个无关变量，页面动了」，这已经不是性能浪费，是行为错误。

**硬伤二：副作用一旦进桶，永远出不来。** 真实组件里，分支切走之后某个依赖就不该再触发更新了（下一章细讲），桶式设计没有任何「除名」机制。

**硬伤三：裸读也会污染。** `activeEffect` 若忘了清空，事件回调里随手读一下响应式数据，就把回调注册成了订阅者。

三个硬伤指向同一个结论：**桶的粒度必须细化到「哪个对象的哪个属性」**。这就是仓库实现的演进方向。

## 1.5 从桶到两层账本：targetMap

把桶拆细，结构呼之欲出：要能按「对象 → 属性 → 副作用集合」逐层定位。仓库 `packages/reactivity/src/effect.ts` 的实现是一张两层 Map：

```ts
// packages/reactivity/src/effect.ts
const targetMap: WeakMap<any, Map<any, Dep>> = new WeakMap()
```

外层 `targetMap` 以**原始对象**为键，值是一个 `Map`；这个内层 Map 再以**属性名**为键，值是一个 `Dep`——本质是 `Set<ReactiveEffect>`，即订阅了这个属性的副作用集合。画出来是这样：

```text
targetMap (WeakMap)
  ├─ target（原始对象）
  │    └─ depsMap (Map)
  │         ├─ "text" → dep (Set)：effect_A
  │         └─ "age"  → dep (Set)：effect_B, effect_C
  └─ 另一个 target
       └─ …
```

为什么外层偏偏用 WeakMap？因为登记关系不应该拖住数据本身的生命周期：WeakMap 的键是弱引用，原始对象在外部失去引用后，垃圾回收器可以连带收走它名下的整条订阅记录。内层没有这个顾虑，普通 Map 即可。现在「改 `age` 却触发 `text` 订阅者」的问题从结构上就消失了——各查各的账。

订阅的登记发生在 `track` 里：

```ts
// packages/reactivity/src/effect.ts —— track（节选，注释为原文件自带）
export function track(target: object, type: TrackOpTypes, key: unknown) {
  // 关键条件：没有正在执行的 effect，或者追踪被挂起，直接返回 ——
  // 这就是 `reactive({}).foo` 裸读不产生任何副作用的原因。
  if (!shouldTrack || !activeEffect) {
    return
  }

  let depsMap = targetMap.get(target)
  if (!depsMap) {
    targetMap.set(target, (depsMap = new Map()))   // 第一层懒创建
  }
  let dep = depsMap.get(key)
  if (!dep) {
    depsMap.set(key, (dep = createDep()))          // 第二层懒创建
  }

  trackEffects(dep)   // dep.add(activeEffect) + activeEffect.deps.push(dep)
}
```

走读一下。函数一进来先查两个守卫：`activeEffect` 是否存在（现在有没有正在执行的副作用）、`shouldTrack` 开关是否打开。两者任一不满足就直接返回——这正是一处对硬伤三的防御：事件回调、`setTimeout` 里的裸读，因为没有活跃副作用，不会在账本上留下任何记录。接着是两层懒创建，最后 `trackEffects` 做两件对称的事：把副作用加进 dep（正向登记），同时把 dep 记到副作用的 `deps` 数组里（反向索引——下一章的清理就靠它）。

Proxy 的 `get` 拦截器里调用的就是它：属性一被读，账本上就多一行。两层懒创建长什么样，用首次执行逐步看（副作用 `effect_A` 读 `obj.text`）：

| 时刻 | 动作 | targetMap 的状态 |
|---|---|---|
| 进入 `track(obj, GET, 'text')` | `targetMap.get(obj)` 得到 undefined | 空 |
| 第一个 if | `targetMap.set(obj, new Map())` | `{obj → Map{}}` |
| 第二个 if | `depsMap.set('text', new Set())` | `{obj → Map{'text' → Set{}}}` |
| `trackEffects(dep)` | `dep.add(effect_A)`，同时 `effect_A.deps.push(dep)` | `{obj → Map{'text' → Set{effect_A}}}` |

再执行一个读 `obj.age` 的副作用 `effect_B`，前两层直接命中、只有第三层新建——账本按访问惰性生长，没有任何预分配。反向索引（`effect_A.deps`）也在这时埋下：下一章清理旧依赖就靠它把订阅一格一格退回去。

## 1.6 reactive()：从手写 Proxy 到产品形态

到现在为止有一个环节一直是「心灵感应」：手写版里 Proxy 的 get/set 直接调用了桶的登记与通知，那仓库里 `reactive()` 包出来的对象呢？它的拦截器在 `packages/reactivity/src/baseHandlers.ts`，先看读这一半：

```ts
// packages/reactivity/src/baseHandlers.ts —— get 拦截器（节选）
const res = Reflect.get(
  target,
  key,
  // 代理包着 ref 时，方法调用以「裸 ref」为 this，避免解包歧义
  isRef(target) ? target : receiver,
)

if (isSymbol(key) ? builtInSymbols.has(key) : isNonTrackableKeys(key)) {
  return res          // 内建 symbol 与 __proto__ 等不收集
}

if (!isReadonly) {
  track(target, TrackOpTypes.GET, key)   // 就是上一节的那个 track
}
```

核心与手写版一致：读到属性就 `track`。多了两处产品级细节：用 `Reflect.get` 配 `receiver`（保证继承属性与 getter 里的 this 指向代理而非原始对象，依赖才能被正确收集），以及一批不该收集的 key 直接放行。写这一半的结构更值得看：

```ts
// packages/reactivity/src/baseHandlers.ts —— set 拦截器（节选）
// 是否已存在下标（数组 ADD vs SET 的判定）
const hadKey = isArrayWithIntegerKey
  ? Number(key) < target.length
  : hasOwn(target, key)

const result = Reflect.set(target, key, value, isRef(target) ? target : receiver)

// 原型链守卫 + 写真的成功才触发
if (target === toRaw(receiver) && result) {
  if (!hadKey) {
    // 新增 key → ADD（迭代者、数组 length、Map 键集都要卷到）
    trigger(target, TriggerOpTypes.ADD, key, value)
  } else if (hasChanged(value, oldValue)) {
    // 值真的变了 → SET
    trigger(target, TriggerOpTypes.SET, key, value, oldValue)
  }
}
```

注意 trigger 拿到的第三个参数不是「key」而是**操作类型**：新增是 `ADD`、修改是 `SET`、删除是 `DELETE`。为什么要区分？因为「新增一个属性」和「修改一个属性」牵连的订阅者不一样——新增会惊动 `for...in` 的订阅者，修改不会。这正是下一节 trigger 那个 switch 的由来。另外两处守卫也是踩坑换来的：写在原型链上（`target !== toRaw(receiver)`）不算改自己的账；值没变（`hasChanged`）不触发，赋相同值是空操作。

手写的桶、仓库的账本、这一节的拦截器，三块拼起来了：`reactive()` 返回的代理对象，读时经 get 拦截调 track 记账，写时经 set 拦截带着操作类型调 trigger 通知。

## 1.7 写入即通知：trigger

登记完成，另一半是通知。`set` 拦截器调用 `trigger`，它要从账本里找出这次改动牵连的所有 dep，把其中的副作用逐个执行：

```ts
// packages/reactivity/src/effect.ts —— trigger（节选）
export function trigger(target, type, key?, newValue?, ...) {
  const depsMap = targetMap.get(target)
  if (!depsMap) {
    return            // 这个对象从来没被追踪过，改动自然没人关心
  }

  let deps: (Dep | undefined)[] = []

  if (type === TriggerOpTypes.CLEAR) {
    deps = [...depsMap.values()]              // 集合被清空：所有 dep 全部命中
  } else if (key === 'length' && isArray(target)) {
    const newLength = Number(newValue)
    depsMap.forEach((dep, key) => {           // length 调短：越界下标全部失效
      if (key === 'length' || key === ARRAY_ITERATE_KEY ||
          (!isSymbol(key) && key >= newLength)) {
        deps.push(dep)
      }
    })
  } else {
    if (key !== void 0) deps.push(depsMap.get(key))   // 常规路径：先命中被改的 key
    switch (type) {
      case TriggerOpTypes.ADD:
        if (!isArray(target)) deps.push(depsMap.get(ITERATE_KEY))
        else if (isIntegerKey(key)) deps.push(depsMap.get('length'))
        break
      // SET / DELETE 等分支见仓库源码
    }
  }
  // 收集到的 dep 去重后逐个执行（scheduler 优先）——完整收尾见下一章
}
```

常规路径一目了然：改哪个 key，就取哪个 key 的 dep。值得停下来的是另外两处——它们对应着 JavaScript 自身的**隐式行为**：

**数组越界新增。** `arr[5] = 1` 这行代码，除了写入下标 5，还会隐式地把 `arr.length` 从 0 撑到 6。如果有个副作用依赖着数组的长度（比如「根据 length 渲染列表」），它理应被通知——但「改的那个 key」是 `5`，账本的 `length` 一栏没人碰。所以 trigger 里专门有一支：`ADD` 且是数组整数键时，把 `length` 的 dep 一并命中。这是仓库实现过程中真实踩过的坑：测试里 `arr[5] = 1` 之后，关心 `arr.length` 的副作用毫无反应，根因就是漏了这条隐式联动。

**length 调短。** 反过来，`arr.length = 0` 意味着所有元素被删除，那么所有下标大于等于 0 的订阅者都该被通知——这就是 `length` 分支里那个 forEach 在做的事。

还剩一个悬案：`for...in` 怎么订阅？循环里读的是「对象整体结构」，没有一个具体的 key 可以挂账。答案是给「结构变化」单开一个账本栏目：

```ts
// packages/reactivity/src/baseHandlers.ts —— ownKeys 拦截器
function ownKeys(target: Target) {
  // 枚举 key 时，对象整体结构可能变化 → 追踪 ITERATE_KEY（数组特化为 'length'）
  track(target, TrackOpTypes.ITERATE, isArray(target) ? 'length' : ITERATE_KEY)
  return Reflect.ownKeys(target)
}
```

`ITERATE_KEY` 是一个专用 symbol。副作用里执行 `for (const k in obj)` 时，代理的 `ownKeys` 拦截器被触发，订阅就记在 `ITERATE_KEY` 这个「假 key」名下；此后任何 `ADD`（新属性改变了枚举结果）都会把 `ITERATE_KEY` 的 dep 加进通知名单——这就是 trigger 代码里 `deps.push(depsMap.get(ITERATE_KEY))` 那一行的前因。`in` 操作符（`'a' in obj`）同理走 `has` 拦截器记账，因为 key 将来可能被增删。

把 trigger 的命中规则整理成一张总表（对照源码逐分支核对）：

| 变更 | 命中的 dep | 为什么 |
|---|---|---|
| `obj.k = v`（k 已存在且值变了，SET） | `k` | 常规路径 |
| `obj.newK = v`（ADD，对象） | `newK` + `ITERATE_KEY` | 新属性改变枚举结果 |
| `arr[5] = v`（ADD，数组越界） | `5` + `length` | 隐式撑大 length |
| `arr.length = 0` | `length` + 所有下标 ≥ 0 | 隐式删除全部元素 |
| `map.clear()`（CLEAR） | 全部 dep | 所有键同时失效 |
| `map.set(k, v)`（SET，Map） | `k` + `ITERATE_KEY` | 迭代结果变化 |

数组那条可以完整跑一遍（仓库行为，Node 可复现）：

```js
import { effect, reactive } from '@mini-vue/reactivity'

const arr = reactive([])
let len = 0
effect(() => { len = arr.length })   // 订阅 length

arr[5] = 'x'                          // 越界新增：隐式把 length 撑到 6
console.log(len)                      // 6 —— length 的订阅者被通知了
```

没有那条隐式联动的话，这里的输出会是 0——「改了下标，关心长度的副作用毫无反应」，这个仓库实现时真实踩过的坑。**语言自身的每个隐式副作用，都必须显式地通知到**，这就是 trigger 比「查出 key、执行函数」复杂得多的全部原因。

还有一个遗留问题本章故意没展开：收集到 deps 之后，「去重、防自触发、按什么顺序执行」这段收尾逻辑，牵扯到副作用的清理与嵌套——那正是下一章的主角。

## 本章小结

响应式系统的核心是一套登记-通知机制：副作用执行时，经 Proxy 的 `get` 拦截调用 `track`，按「对象 → 属性 → 副作用集合」登记进两层账本 targetMap；属性被设置时经 `set` 调用 `trigger`，按改动类型（含数组 length、迭代键等隐式联动）查出牵连的 dep 并执行。外层用 WeakMap 保证登记关系不拖住数据生命周期；`activeEffect` 指针保证只有「正在执行的副作用」的读取才登记。组件的渲染函数，就是这套机制里最重要的一个副作用。

## 与官方实现的差距

- **数据结构**：本实现的 dep 是 `Set`；官方 3.5 重构为「版本计数 + 双向链表」，依赖清理从全量清空变为增量维护，语义不变、高频更新开销更低（见 [v3.5 发布说明](https://blog.vuejs.org/releases/v3-5)）。差距细节在下一章清理机制处更清楚。
- **迭代键联动**：`MAP_KEY_ITERATE_KEY`（Map 的按-key 迭代）等边角联动，官方分发更全，本实现从简。
