# 08 · 组件的本质：把状态、生命周期与批更新装进一个实例

07 篇把两组子节点的比对收敛到最少移动，但有个前提从未动摇：进入 patch 的 vnode，type 要么是字符串、要么是 Symbol。本章把它换成对象——一个组件定义。

具体要回答的问题是这些：vnode.type 从字符串换成对象，patch 该走哪条路？组件的状态放在哪里、更新又由谁驱动？同一轮同步代码改十次状态，为什么组件只重渲染一次？子组件的更新凭什么排在父组件后面？同步改完状态立刻 `await nextTick()`，为什么一定拿到新 DOM？这也是渲染器部分的收官：官方文档说「每个组件实例创建一个响应式副作用来渲染和更新 DOM」，全章就是把这一句拆开落地。

## 8.1 组件是「带状态的子树」

先看本章的目标形态，一段能跑的组件：

```ts
// 导入均来自 @mini-vue/runtime-dom（可直接放进任一 vitest 文件，jsdom 环境）
const log: string[] = []
const count = ref(0)
const App = {
  setup() {
    onMounted(() => log.push('mounted'))      // 注意：没传组件，它注册给谁？
    return () => h('p', String(count.value))  // 渲染函数：执行时读 count.value
  },
}
const container = document.createElement('div')
createApp(App).mount(container)   // 此刻容器里是 <p>0</p>
```

先用朴素的方式理解组件。05 篇的朴素渲染器拿到 vnode 就 `document.createElement(vnode.type)`，type 是对象时这条路直接走不通。更深的差别是：元素 vnode 自己描述一个节点，组件 vnode 描述的却是「一棵待展开的子树」，子树长什么样由渲染函数当场计算。再算上状态，组件就是「带状态的子树」。

状态放哪、更新谁来喊？先试最朴素的做法：

```js
// —— 手写朴素版，仅用于演示 ——
const MyComp = {
  setup() {
    let count = 0                        // 普通局部变量：闭包持有
    return () => h('p', String(count))   // 渲染函数引用它
  },
}
// count++ 之后：没有任何机制知道「该重新渲染了」，DOM 永远停在 0
```

很明显，我们还做不到自动更新，因为普通变量的读取不留痕迹。把 count 换成 ref，渲染函数读 `.value` 就会经第 1 章的 track 登记订阅。但还缺一环：订阅触发之后执行什么？答案是给每个组件配一个专属副作用，专门跑它的渲染函数——文档那句话里的「实例」与「副作用」，就是本节与下一节的全部内容。

分发不用贴代码也能说清。patch 的 default 分支以一次位与把组件 vnode 送到 processComponent（05 篇埋的伏笔在此收口）：`n1` 为 null 走 mountComponent，否则走 updateComponent，双分支的老结构不变。挂载本体只有三行：

```ts
// packages/runtime-core/src/renderer.ts —— mountComponent
function mountComponent(
  initialVNode: VNode,
  container: any,
  anchor: any,
  parentComponent: ComponentInternalInstance | null,
) {
  const instance = (initialVNode.component = createComponentInstance(initialVNode, parentComponent))

  setupComponent(instance)

  setupRenderEffect(instance, initialVNode, container, anchor)
}
```

三步各管一段：createComponentInstance 建实例，状态的家；setupComponent 执行 setup，用户逻辑的入口；setupRenderEffect 建立渲染副作用，更新的引擎（8.2）。实例（component.ts 的 ComponentInternalInstance）字段分三组读。数据面：props、slots、setupState、render，渲染时要读的东西全在实例上。输出面：subTree 记最近一次渲染产物，update 是 8.2 的主角，next 暂存父级驱动更新带来的新 vnode。生命周期与作用域：bm/m/bu/u/bum/um 六个短键数组存钩子回调，scope 是第 4 章的 EffectScope。

uid 字段值得单独一问：为什么要全局递增 id？因为调度队列需要一个「创建先后」的全序。createComponentInstance 里 `uid: uid++` 分配，父组件必然先于子组件创建，id 因此天然父小、子大——8.3 的排序全靠它。

再看 setup 的执行。setupStatefulComponent 里，setup 函数被这样调用（组件未定义 setup 时直接走 finishComponentSetup 装配 render）：

```ts
// packages/runtime-core/src/component.ts —— setupStatefulComponent（节选）
const setupContext = (instance.setupContext = createSetupContext(instance))
setCurrentInstance(instance)
// 同步执行 setup（async setup 的恢复逻辑 mini 不做，文档注明）
const setupResult = callWithErrorHandling(
  setup,
  instance,
  ErrorCodes.SETUP_FUNCTION,
  [instance.props, setupContext],
)
unsetCurrentInstance()
handleSetupResult(instance, setupResult)
```

setCurrentInstance 与 unsetCurrentInstance 夹住一段同步执行窗口，指针本体在 currentInstance.ts：

```ts
// packages/runtime-core/src/currentInstance.ts（节选）
export function setCurrentInstance(instance: ComponentInternalInstance | null) {
  currentInstance = instance
  instance && instance.scope.on()
}

export function unsetCurrentInstance() {
  const instance = currentInstance
  currentInstance = null
  instance && instance.scope.off()
}
```

现在回答开头按下的问题：onMounted 不传组件，凭什么知道注册给谁？靠 currentInstance 指针——lifecycle.ts 的 injectHook 默认绑定 `target = currentInstance`，把回调包上错误处理后塞进 `instance['m']` 这类数组。setup 执行时指针已设好，回调就落进当前组件；同步段结束指针清空，之后在 setTimeout 里调 onMounted 只会收到一句警告——生命周期注册因此必须写在 setup 的同步段里。scope.on() 是同一窗口里干的第二件事：激活实例作用域，setup 期间创建的 watch、computed 经第 4 章「构造时自动登记」收进实例名下——「组件实例就是一个 effect scope」在此接上实现。

注册侧的工厂值得看一眼实物，两处细节都长在参数表上：

```ts
// packages/runtime-core/src/lifecycle.ts —— injectHook（节选：DEV 警告分支从略）
function injectHook(
  type: LifecycleHooks,
  hook: Function,
  target: ComponentInternalInstance | null = currentInstance,
) {
  if (target) {
    const hooks = (target[lifecycleHooksKey[type]] || (target[lifecycleHooksKey[type]] = [])) as Function[]
    // 包一层错误处理：钩子抛错不影响渲染器主流程
    hooks.push(() => callWithErrorHandling(hook, target, ErrorCodes.COMPONENT_UPDATE))
  } else if (__DEV__) {
    console.warn(/* 无活跃实例时的警告 */)
  }
}
```

其一，`target = currentInstance` 写在默认参数里——默认值在调用那一刻求值，onMounted 执行时指针指着谁，回调就落谁家。其二，存进数组的是包了 callWithErrorHandling 的壳，用户钩子抛错只走错误处理通道，不会打断渲染器主流程。注册到此完成；派发在 8.3 的 post 队列，那边的链路表会把两头接起来。

setup 的返回值两态，由 handleSetupResult 归一：返回函数，直接充当 render；返回对象，经 proxyRefs 浅解包成 setupState（模板里读裸值，第 3 章）。render 的空缺再由 finishComponentSetup 按优先级补齐：setup 返回的函数 > options.render > 模板运行时编译 > 空占位。数据面至此齐了，还缺两件事：渲染谁来做、更新谁来喊。下一节看 setupRenderEffect 怎么一次解决。

## 8.2 枢纽一行：instance.update = effect(fn, { scheduler })

mountComponent 的第三步做两件事：定义 componentUpdateFn，再交给 effect 工厂。先看函数本体，双分支对应「渲染」与「更新」两个动词：

```ts
// packages/runtime-core/src/renderer.ts —— setupRenderEffect（节选：componentUpdateFn）
const componentUpdateFn = () => {
  if (!instance.isMounted) {
    // beforeMount 钩子
    invokeHooks(instance, 'bm')

    const subTree = (instance.subTree = renderComponentRoot(instance))
    patch(null, subTree, container, anchor, instance)
    initialVNode.el = subTree.el

    // onMounted：等渲染完（post flush）统一执行
    queuePostRenderEffect(() => invokeHooks(instance, 'm'))

    instance.isMounted = true
  } else {
    // 关键是：响应式依赖变 → 触发 instance.update （经 scheduler 进队列）
    if (instance.next) {
      // 父级驱动更新：把 next vnode 的 props/attrs/slots 应用到实例
      applyPreUpdate(instance, instance.next)
    }

    const prevTree = instance.subTree
    const nextTree = renderComponentRoot(instance)
    instance.subTree = nextTree

    // beforeUpdate 钩子
    invokeHooks(instance, 'bu')

    patch(
      prevTree,
      nextTree,
      hostParentNode(prevTree.el!),
      getNextHostNode(prevTree),
      instance,
    )
    // ……（nextTree.el 回写与 onUpdated 进 post 队列，见源码）
  }
}
```

挂载分支走读。renderComponentRoot 以 proxy 为实参调用 render，归一化返回值并做 attrs 透传（componentRenderUtils.ts 一句话交代）。patch(null, subTree) 把子树真正挂出去——组件 vnode 的「待展开」在此完成，05 到 07 篇的全部挂载与比对能力都被这次 patch 复用。收尾把根元素回写给组件 vnode：`initialVNode.el = subTree.el`，还是 05 篇那条回写通道。

更新分支末尾被节略的两行补在这里（接在 patch 调用之后）：

```ts
// packages/runtime-core/src/renderer.ts —— componentUpdateFn 更新分支的收尾（前文节选的补全）
        ;(nextTree as VNode).el = nextTree.el as any

        // onUpdated 钩子
        queuePostRenderEffect(() => invokeHooks(instance, 'u'))
```

第一行是自赋值：nextTree.el 在 patch 内部已经就位（patchElement 与 processComponent 都会回写 n2.el），这行再抄一遍、值不变——「树根 el 回写」的收尾在两条分支里由此对齐。第二行把 updated 钩子排进 post 队列，与挂载分支的 m 同一待遇，理由也相同：等整批渲染落定再派发。

mounted 为什么不当场执行，要进 post 队列？因为同一批刷新里别的组件未必渲染完；post 队列等整批渲染作业结束后统一执行，届时这一轮的 DOM 全部就位。父子组件的钩子顺序也在这条队列里自然成立：父的 patch 先递归挂完整棵子树，子的 mounted 先入队、父的后入队，执行序因此子先父后（runtime-dom 的 renderer.spec.ts 有锚定）。

更新分支的关键在 instance.next。组件的更新有两条来路：自身状态变化，trigger 经 scheduler 找上门（8.3）；父组件重渲染，updateComponent 发现子的 props/slots 有变，把新 vnode 挂到 instance.next 再调 instance.update()。所以更新分支先经 applyPreUpdate 把 next 的 props 原地改写、attrs 重建、slots 刷新并入实例，再重渲染、以旧树为 n1 调 patch。props 为什么原地改写而不是换新对象？源码注释写明：保住对象身份，读旧 props 的渲染副作用才能被触发。接下来是本章的枢纽一行：

```ts
// packages/runtime-core/src/renderer.ts —— setupRenderEffect（节选：副作用装配）
const update: SchedulerJob = (instance.update = effect(componentUpdateFn, {
  // 重要：调度器让它走 job 队列（微任务批量刷新），而不是同步重渲染
  scheduler: () => queueJob(update),
  allowRecurse: true,
  // 渲染 effect 显式归属组件 scope：卸载时 scope.stop() 会一并停掉它。
  // 若不登记，卸载后共享依赖再变化，仍会经 scheduler 把已卸载组件重新 patch 回 DOM（僵尸复活）。
  scope: instance.scope,
}) as any)

update.id = instance.uid
```

effect 工厂默认立即执行一次 componentUpdateFn——首次挂载就发生在这里，渲染函数读过的每个响应式数据都经 track 登记为依赖。文档那句话的两个动词就此落地：首跑完成「渲染」，scheduler 承接「更新」——依赖变化时 trigger 不再同步重跑，而是把 update 送进调度队列。第 4 章把 scheduler 选项交给了消费者，组件渲染是它最大的消费者。

末两行补两件事。update.id = instance.uid 给作业一个排序锚点，8.3 用。scope: instance.scope 把渲染副作用显式登记进实例作用域——为什么必须登记？看卸载路径，unmountComponent 在摘除 subTree 之前先做这件事：

```ts
// packages/runtime-core/src/renderer.ts —— unmountComponent（节选）
// 停止实例 scope：连带停掉 setup 期创建的 effect/computed
instance.scope.stop()
```

scope.stop() 一停，setup 期的 watch 与 computed、渲染副作用、连同子组件的整棵 scope 树一起停止。不登记会怎样？渲染副作用还活在全局账本里，共享依赖再变化时它仍会入队、把已卸载的组件重新 patch 回 DOM——第 4 章处理过的「僵尸复活」，上面装配代码里的注释就是当时的修复记录，runtime-dom 测试里也有对应锚定。allowRecurse 则给「更新中又改了自身依赖」的场景开重入绿灯，第 2 章的自触发防护对它放行。

副作用建好了，但它从不直接跑——scheduler 把它送进队列。队列怎么去重、怎么排序、什么时候刷？最后一节。

## 8.3 批更新：调度队列与 nextTick

先做实验。给 8.1 的组件加上计数与记录，看三次赋值之后发生什么：

```ts
// 导入均来自 @mini-vue/runtime-dom（可直接放进任一 vitest 文件，jsdom 环境）
const order: string[] = []
const count = ref(0)
let renders = 0
const App = {
  setup() {
    onUpdated(() => order.push('updated'))
    return () => {
      renders++                            // 渲染函数每跑一次记一笔
      return h('p', String(count.value))
    }
  },
}
const container = document.createElement('div')
createApp(App).mount(container)
await nextTick()                           // 首跑完成：<p>0</p>，renders 为 1

count.value = 1
count.value = 2
count.value = 3
order.push('sync-end')                     // 同步代码结束
// 此刻实测：container.textContent 仍是 '0'，DOM 一步没动

await nextTick(() => order.push('tick'))   // 排在整批刷新之后
// 实测结果：renders 为 2——三次赋值只重渲染一次；
//           textContent 为 '3'，order 为 ['sync-end', 'updated', 'tick']
```

现象有四个。三次赋值只触发一次重渲染；同步代码结束时 DOM 还是旧的；渲染与 updated 都发生在微任务里；nextTick 的回调排在它们全部之后。第 4 章手写的 Set 加微任务十行版解释得了前两个，解释不了后两个的「顺序感」——组件的更新还要求父先子后、生命周期排在渲染后。仓库 scheduler.ts 把四件事一起接走。

第一件，去重。三次赋值各自同步触发一次 trigger，也就各自调一次 update 的 scheduler——三次 queueJob(update)：

```ts
// packages/runtime-core/src/scheduler.ts —— queueJob
export function queueJob(job: SchedulerJob) {
  // 同一作业已在队列（含正在执行的部分）→ 跳过
  if (!(job.flags! & QUEUED)) {
    job.flags = (job.flags || 0) | QUEUED

    const jobId = getId(job)
    const last = queue[queue.length - 1]
    if (!last || jobId >= getId(last)) {
      queue.push(job)
    } else {
      // 二分找插入位，保证 id 升序
      let start = flushIndex + 1
      let end = queue.length
      while (start < end) {
        const mid = (start + end) >>> 1
        if (getId(queue[mid]) < jobId) {
          start = mid + 1
        } else {
          end = mid
        }
      }
      queue.splice(start, 0, job)
    }
    queueFlush()
  }
}
```

第一次入队时在 job.flags 打上 QUEUED 位，第二次、第三次在入口就被挡掉——「改十次只渲一次」的机制本体就这一个位。尾部快速路径：新作业 id 不小于队尾就直接 push，按序入队的多数场景不必挪动。

第二件，排序。id 小于队尾时二分找位再 splice，队列始终保持 id 升序。为什么要排序？对照官方 scheduler 同段代码的注释，动机有两条。其一，uid 按创建序分配，父组件必然先创建、id 更小——父先更新，子组件一次就能拿到父改过的新 props 渲染到位；反过来子先父后，子要白渲染一次。其二，父组件更新时若把某子组件卸载，子组件排在队里的更新作业就应当作废（官方靠作废位做到，本实现尚缺，差距节展开）。二分为什么从 flushIndex + 1 起搜？flushIndex 之前是已执行区，新作业不许插到它前面。

排序的动因值得一次全程目击。造一棵三层树：App 渲染 Child、Child 渲染 Grand；三个状态各归其主——p 归 App 且经 prop 传下去，c 归 Child，g 归 Grand。挂载后故意倒序触发（孙、父、子），让二分插入全部出场：

```ts
// 导入均来自 @mini-vue/runtime-dom（jsdom；可直接跑，实测数据见下）
const p = ref(0), c = ref(0), g = ref(0)
const log: string[] = []
const Grand = {
  setup() { onUpdated(() => log.push('G:u')); return () => h('span', 'g' + g.value) },
}
const Child = {
  props: { msg: Number },
  setup(props: any) {
    onUpdated(() => log.push('C:u'))
    return () => h('div', [h('i', `c${c.value}m${props.msg}`), h(Grand)])
  },
}
const App = {
  setup() { onUpdated(() => log.push('P:u')); return () => h(Child, { msg: p.value }) },
}
createApp(App).mount(container)   // uid 实测：App 0、Child 1、Grand 2
await nextTick()

g.value++   // ① 孙先变：队列空，push 即可
p.value++   // ② 父再变：id 0 小于队尾 2 → 二分插入
c.value++   // ③ 子最后：id 1 小于队尾 2 → 二分插入
await nextTick()
```

三次入队的账面，逐行对照 queueJob：

| 触发 | 作业（id） | 走尾部快速路径？ | 二分过程 | 入队后队列 |
|------|-----------|------------------|----------|------------|
| g.value++ | G（2） | 队列空，`!last` → push | — | [G] |
| p.value++ | P（0） | 0 不小于队尾 2，不走 | start=0、end=1；mid=0：queue[0] 的 2 小于 0？否 → end=0；命中位 0 | [P, G] |
| c.value++ | C（1） | 1 不小于队尾 2，不走 | start=0、end=2；mid=1：queue[1] 的 2 小于 1？否 → end=1；mid=0：queue[0] 的 0 小于 1？是 → start=1；命中位 1 | [P, C, G] |

为什么父的 id 必然小？`uid: uid++` 在 createComponentInstance 的「建实例」一步分配，而孩子的实例要等父的 componentUpdateFn 首跑、patch 递归进 mountComponent 才创建——创建序即嵌套序，父先拿号。所以排序不是锦上添花，是正确性：P 先执行，新的 props 才能在这一轮就流进 C；反过来 C 先跑，拿到的是旧 prop，P 跑完还得再赔一次 C 的渲染。

执行序的实测里有一处容易漏看。flushJobs 从 P 开始；P 重渲染时 patch 遇到 Child 的新 vnode，updateComponent 判定 props 有变，调用的是 `instance.update()`——直接调用，不过队列。于是 C 在 P 的作业体内同步重渲染了一次（applyPreUpdate 吃掉 next，新 prop 与已变的 c 一起生效）；轮到 C 自己的队内作业时，next 已空、数据没再变，仍按流程再渲染一遍。实测渲染计数 P 2 次、C 3 次、G 2 次（挂载各占 1 次），updated 日志为 ['C:u', 'P:u', 'C:u', 'G:u']——第一条 C:u 来自那次嵌套执行，它在 P 的函数体跑完之前就进了 post 队列，所以排在 P:u 前面。C 多付的这一次渲染是本实现的账：官方的作业本体是 effect.runIfDirty，执行前先查脏位，同步跑过之后队内作业直接跳过——差距节「作业的本体」一条的实证。

还有一处咬合值得点破。嵌套执行里 applyPreUpdate 原地改写 shallowReactive 的 props，这一写会 trigger C 的渲染副作用、经 scheduler 再次 queueJob(C)——但 C 的 QUEUED 位还亮着（队内作业尚未轮到），入口处直接挡掉。原地改写保住依赖通道，QUEUED 位防住重复入队，两件事在这一刻配合。

第三件，安排微任务。queueJob 的收尾总调 queueFlush，本体四行：`isFlushing` 与 `isFlushPending` 双开关挡住重复安排，`currentFlushPromise = resolvedPromise.then(flushJobs)` 把刷新排进微任务并握住这条 promise——nextTick 马上要用它。resolvedPromise 是模块级的 `Promise.resolve()`，整条流水线复用同一个已决议实例，十个组件入队、安排的也是同一条微任务。

第四件，刷新本体：

```ts
// packages/runtime-core/src/scheduler.ts —— flushJobs
function flushJobs() {
  isFlushPending = false
  isFlushing = true

  // 1. pre 作业优先（插槽/渲染前的 watch 回调）
  flushPreFlushCbs()

  try {
    for (flushIndex = 0; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex]
      if (job) {
        // 清掉 QUEUED 再执行，允许 wait：执行中途又能被 queueJob
        job.flags! &= ~QUEUED
        job()
      }
    }
  } finally {
    flushIndex = -1
    queue.length = 0

    // 2. post 作业（onMounted/onUpdated 等）
    flushPostFlushCbs()

    isFlushing = false
    currentFlushPromise = null

    // 3. 刷新中又来了新作业 → 再来一轮
    if (queue.length || pendingPostFlushCbs.length || pendingPreFlushCbs.length) {
      flushJobs()
    }
  }
}
```

最值得停在循环条件上：queue.length 是活引用，不是快照。执行父组件的更新时又触发了子组件的依赖，queueJob 直接 push 进同一个数组，本轮循环接着消费——刷新期间入队的作业同轮跑完。执行前清 QUEUED 位，作业因此能在执行中再次入队，配合 allowRecurse 支撑自更新。顺序是三段式：pre（渲染前的 watch 回调）→ 主队列（渲染）→ post（生命周期），post 段执行时主队列已清空，钩子看到的 DOM 必然就位。收尾判稳定：三条队列任一非空就再刷一轮，因为 post 回调里改了状态还会产生新作业。

post 段的本体还没有展开，而它正是 mounted 派发的最后一环：

```ts
// packages/runtime-core/src/scheduler.ts —— flushPostFlushCbs（完整）
export function flushPostFlushCbs() {
  if (pendingPostFlushCbs.length) {
    const deduped = [...new Set(pendingPostFlushCbs)]
    // 按 id 稳定排序（onMounted 钩子同序执行）
    deduped.sort((a, b) => getId(a) - getId(b))
    pendingPostFlushCbs.length = 0

    if (activePostFlushCbs) {
      // 嵌套 flush
      activePostFlushCbs.splice(0, 0, ...deduped)
      return
    }

    activePostFlushCbs = deduped
    for (postFlushIndex = 0; postFlushIndex < activePostFlushCbs.length; postFlushIndex++) {
      const cb = activePostFlushCbs[postFlushIndex]
      cb.flags! &= ~QUEUED
      cb()
    }
    activePostFlushCbs = null
    postFlushIndex = 0
  }
}
```

Set 去重、按 id 排序、清 QUEUED 后逐个执行——与主队列同一套纪律。把 8.1 埋下的 onMounted 从注册到派发接成一条链，每步对着代码行与时机：

| 步 | 时机 | 代码位置 | 动作 |
|---|------|----------|------|
| 1 | setup 同步段开始 | component.ts setupStatefulComponent：setCurrentInstance(instance) | 指针指向实例，instance.scope.on() |
| 2 | setup 体内 | lifecycle.ts injectHook：target 默认取 currentInstance | 回调包错误处理后 push 进 instance.m |
| 3 | 渲染副作用首跑 | renderer.ts componentUpdateFn 挂载分支 | renderComponentRoot 产出 subTree，patch 挂进容器 |
| 4 | 挂载分支末尾 | queuePostRenderEffect(() => invokeHooks(instance, 'm')) | 闭包进 pendingPostFlushCbs |
| 5 | 微任务收尾 | scheduler.ts flushJobs 的 finally → flushPostFlushCbs() | 主队列已清空，逐个派发，DOM 全部就位 |

第 4、5 步之间还藏着一个顺序问题。父组件的 patch 是深度优先：子的 m 闭包先入队、父的后入队；这些闭包本身没有 id，getId 一律返回 Infinity，排序比较恒判相等，稳定排序保持入队序——「子的 mounted 先于父」由入队序天然保证。renderer.spec.ts lifecycle 组锚定的父子顺序，机制就在这张表与这段排序里。

最后是 nextTick，实质只有一行：

```ts
// packages/runtime-core/src/scheduler.ts —— nextTick
export function nextTick<T = void>(fn?: () => T): Promise<T | void> {
  const p = currentFlushPromise || resolvedPromise
  return fn ? p.then(fn) : p
}
```

回到实验的最后一问：同步改完立刻 await nextTick，为什么一定拿到新 DOM？因为此刻 currentFlushPromise 正指着那条 flushJobs 微任务，p.then(fn) 保证回调排在它之后——promise 的 then 语义就是执行顺序。没有刷新排队时回退 resolvedPromise：回调仍走微任务段，但不等待任何东西。实验里 order 的三个元素——sync-end 在前、updated 居中、tick 收尾——一个数组把三段时序全钉住了。

章首的四个问题至此全部有答：状态放实例、更新由渲染副作用驱动、改十次只渲一次靠 QUEUED 位、nextTick 挂在刷新 promise 上。00 篇数据流图的 ③④ 两步，链路闭合。

## 本章小结

组件 vnode 的 type 是对象，patch 经位与分发到 processComponent；mountComponent 三步走——建实例、跑 setup、建立渲染副作用。setup 在 currentInstance 指针的同步窗口内执行，生命周期注册与副作用归属都靠这个窗口。渲染副作用首跑完成挂载，依赖变化经 scheduler 入队而非同步重跑；实例 scope 收编全部副作用，卸载时一并停止。调度队列以 QUEUED 位去重、按 uid 二分插序保证父先子后，queueFlush 一轮只安排一条微任务，flushJobs 以活引用同轮消费新作业、按 pre、主、post 三段刷到稳定；nextTick 挂在 currentFlushPromise 上，回调必在整批渲染之后。

## 与官方实现的差距

以下均经 `third_party/vue-core`（v3.5.x）源码核对：

- **PRE 位统一排序**：官方 3.5 把 pre watcher 一并经 queueJob 送进主队列，作业带 PRE 标志位；findInsertionIndex 的比较条件含「同 id 且带 PRE 则插后」，同组件的 pre watcher 因此排在它当轮渲染作业之前（源码注释明说）。本实现无 PRE 位，同 uid 的 pre 作业插在已入队的渲染作业之后——第 4 章从 watch 侧讲过同一事实，此处是渲染侧视角。
- **递归上限与作废位**：官方有 `RECURSION_LIMIT = 100`（超限报 Maximum recursive updates exceeded）与 DISPOSED 位——unmountComponent 在 scope.stop() 后立即给 job 打 DISPOSED，flushJobs 见位即跳过。本实现两者皆无，且实测可复现缺口：同一轮里子组件的更新已入队、父组件更新又把它卸载，排队作业仍会执行并走挂载分支，把已卸载的组件重新挂回 DOM。父先于子的排序降低不了这个风险，DISPOSED 位才是闸门。
- **渲染副作用的归属机制**：官方以 instance.scope.on() / off() 包裹 new ReactiveEffect 的创建窗口完成登记，实例 scope 是 `new EffectScope(true)`（detached）；本实现经 effect() 的 options.scope 显式登记，实例 scope 非 detached、挂在父实例 scope 名下。机制有别、归属等价：两侧卸载时 scope.stop() 都会停掉渲染副作用。
- **作业的本体**：官方的 job 是 effect.runIfDirty 的绑定——执行时先查脏位、不脏不跑，是 QUEUED 位之外的第二层去重；本实现的作业就是渲染函数本身，执行即渲染。官方初次挂载显式调用 update()，本实现靠 effect 工厂的非惰性首跑。
