# 11 · 编译优化：补丁标记、区块与静态提升

上一篇走完了编译器的后半程：transform 把 AST 改写成可生成代码的形态，codegen 吐出一个包在 `with (_ctx)` 里的 render 函数。但这份产物与手写 `h()` 的产物，在渲染器眼里毫无区别。第 7 章的 diff 已经很聪明——头尾扫描、查表配对、LIS 压移动数——为什么 Vue 3 还要专门让编译器插手性能？

本章回答这一族问题。一个永远不变的 `<span>ok</span>`，更新时凭什么连看都不用看？`:title` 会变、`id="a"` 永不变，渲染器凭什么知道该比谁、跳过谁？模板里哪些信息是编译期就能确定、运行时恰好用得上的？答案是一份「编译器生产、渲染器消费」的性能契约，条款有三：补丁标记 patchFlag、区块 block、静态提升。第 5 章在 `patch` 开头埋下的那行 `if (n1 === n2) return`，也将在本章兑付。

## 11.1 patchFlags：把「哪里会变」写进 vnode

先复述问题。第 6/7 章写好的 `patchElement` 对属性是全量比对：遍历新 props 逐个比，再遍历旧 props 查删除。对一个只有 `:title` 会变的输入框，`id="a"` 也要陪跑一轮。为什么不能只比会变的键？因为渲染器拿到的是两份普通对象，「谁会变」这份信息它根本没有，只有逐键比对才能保证正确。

编译器恰好有这份信息。上一篇走读 transformElement 时，`:title="t"` 与 `id="a"` 走的是两个分支——前者 exp 是表达式、后者是字面量。当时这份数据被扔掉了，要做的只是装进 vnode 捎给渲染器。装法是位掩码（bitmask）：用一个整数的每个二进制位独立表达一个语义，多个标记用 `|` 合并、用 `&` 检查。官方文档的表述是，补丁标记「在 vnode 创建调用中直接编码了每个元素所需的更新类型」，如 CLASS 为 2、STABLE_FRAGMENT 为 64，「一个元素可以有多个更新类型标记，会被合并成一个数字」，运行时以位运算检查。取值定义在 shared 包：

```ts
// packages/shared/src/index.ts —— PatchFlags 枚举（节选，中间四个 fragment 位从略）
export const enum PatchFlags {
  TEXT = 1,
  CLASS = 1 << 1,
  STYLE = 1 << 2,
  PROPS = 1 << 3,
  FULL_PROPS = 1 << 4,
  // ……（NEED_HYDRATION / STABLE_FRAGMENT / KEYED_FRAGMENT / UNKEYED_FRAGMENT）
  NEED_PATCH = 1 << 9,
  DYNAMIC_SLOTS = 1 << 10,
  HOISTED = -1,
  BAIL = -2,
}
```

本仓库实际生产与消费的是前五个正数位；NEED_PATCH、DYNAMIC_SLOTS 等位只有定义、暂无生产者（差距节再谈）。HOISTED 与 BAIL 是负数哨兵——负数永远过不了 `patchFlag > 0` 这类检查，天然不与位运算混用，只作整值比较。

生产端在 transformElement 的属性扫描里。class 与 style 享有特殊待遇，由 markDynamicProp 统一发放：`name === 'class'` 返回 `flag | PatchFlags.CLASS`，`'style'` 同理，其余属性名 push 进名单并返回 `flag | PatchFlags.PROPS`。为什么这两位特殊？因为 class 与 style 是最高频的动态属性，且 patchProp 对它们有专门的归一逻辑，值得独占一位、不挤名单。其余动态属性走 PROPS 位，属性名同时记进 dynamicProps——编译期确定的动态属性名数组。主扫描循环的骨架：

```ts
// packages/compiler-core/src/transforms/transformElement.ts —— 统计与扫描（节选，
// ATTRIBUTE 分支与各指令细分从略；注释为原文件自带）
let patchFlag = 0
let dynamicPropsNames: string[] | null = null
let hasDynamicProps = false
let hasDynamicText = false
// ……（预扫 children 汇总 hasDynamicText：插值/含插值的复合文本才算动态，从略）

for (let i = 0; i < el.props.length; i++) {
  // ……
  if (name === 'bind' && arg && exp) {
    if ((arg as any).isStatic) {
      properties.push(createObjectProperty(arg, exp))
      // :class / :style 特定位，其它进 PROPS 名单
      const argName = (arg as any).content
      patchFlag = markDynamicProp(patchFlag, argName, dynamicPropsNames || (dynamicPropsNames = []))
      hasDynamicProps = true
    } else {
      properties.push({ type: NodeTypes.JS_PROPERTY, key: arg, value: exp, computed: true, loc: (arg as any).loc } as any)
      patchFlag |= PatchFlags.FULL_PROPS
      dynamicPropsNames = null
      hasDynamicProps = true
    }
  } else if (name === 'on' && arg && exp) {
    // ……（修饰符分流：.prevent → _withModifiers、.enter → _withKeys，从略）
    properties.push(createObjectProperty(createSimpleExpression(keyName, true), handlerExp))
    // 事件 handler 也在变化（每条 onXxx 都是动态 prop）
    patchFlag |= PatchFlags.PROPS
    if (dynamicPropsNames && !dynamicPropsNames.includes(keyName)) dynamicPropsNames.push(keyName)
    hasDynamicProps = true
  }
}

// ……（vnodeProps 与 children 组装从略）
if (hasDynamicText) patchFlag |= PatchFlags.TEXT
// 全静态 → HOISTED（可提升）
if (!hasDynamicProps && !hasDynamicText && dirs.length === 0 && !isComponent) {
  patchFlag = -1
}
```

三个分支读法。静态参数名的 `:title="t"`：属性进 props 对象，flag 经 markDynamicProp 累加，`title` 进名单。属性名本身是变量的 `:[name]="x"`：键在编译期不可知，名单无法静态列出，升级为 FULL_PROPS 并把名单清空。事件 `@input`：每次渲染 handler 都可能换新函数，onXxx 同样占 PROPS 位、进名单。v-model 文本形态内联出的 `value` 与 `onInput` 也逐个登记，源码注释记着漏登的后果：「patchFlag 置了 PROPS 位但名单为空 → 渲染器什么都不比」，程序化改模型将不驱动输入框回显。

codegen 把统计结果原样吐进调用参数，genVNodeCall 的收尾两行 `push(\`, ${patchFlag}\`)` 与名单数组拼接，产物里一眼可辨。实测一段模板：

```js
// compile('<input :title="t" :key="k" id="a" />').code（实测产物，首行 helper 解构与函数包装从略）
return _openBlock(), _createElementBlock("input", {title: t, key: k, id: "a"}, null, 8, ["title", "key"])
```

`8, ["title", "key"]` 就是契约本体：8 是 PROPS 位（1 << 3），名单列出仅有的两个动态键；静态的 `id: "a"` 只出现在 props 对象里，不占任何标记。

统计本身值得逐属性走一遍。换一个各形态齐全的元素：`<p id="a" :class="c" :title="t">{{ msg }}</p>`。transformElement 的退出钩子里，patchFlag 从 0 出发，按属性在标签里的出现顺序逐步累加（对照 transformElement.ts 的扫描循环与收尾两行）：

| 扫描到 | 走的分支 | patchFlag 累计 | dynamicProps 名单 |
|---|---|---|---|
| （起点） | — | 0 | 无 |
| `id="a"` | ATTRIBUTE：静态字面量只进 props 对象 | 0 | 无 |
| `:class="c"` | bind 静态参数名，markDynamicProp 特判 | 0 \| CLASS = 2 | class 不进名单 |
| `:title="t"` | bind 静态参数名，markDynamicProp 常规 | 2 \| PROPS = 10 | `["title"]` |
| children `{{ msg }}` | 预扫命中 hasDynamicText，收尾补位 | 10 \| TEXT = 11 | `["title"]` |

收尾两行再核对：hasDynamicProps 为真，全静态改写 -1 不触发；最终 11 = TEXT(1) | CLASS(2) | PROPS(8)。实测产物与推演一致：

```js
// compile('<p id="a" :class="c" :title="t">{{ msg }}</p>').code 的 return 行 —— 实测
return _openBlock(), _createElementBlock("p", {id: "a", class: c, title: t}, _toDisplayString(msg), 11, ["title"])
```

再做删减实验，两条边一起验证（实测产物，首尾从略）：

```js
// <p id="a" :class="c">{{ msg }}</p> —— 去掉 :title
return _openBlock(), _createElementBlock("p", {id: "a", class: c}, _toDisplayString(msg), 3)
// <p id="a">{{ msg }}</p> —— 连 :class 也去掉
return _openBlock(), _createElementBlock("p", {id: "a"}, _toDisplayString(msg), 1)
```

去掉 `:title` 后收尾变成 `, 3)`，只剩 TEXT|CLASS，名单参数整个消失——没有 PROPS 位就不输出名单；连 `:class` 也去掉，收尾是 `, 1)`，只剩孤零零的 TEXT。位与名单谁随谁走，删一下就看清了。

消费端回到 patchElement。第 7 章差距节预告过这段，现在展开：按位分流，位没打到的属性一概不比。

```ts
// packages/runtime-core/src/renderer.ts —— patchElement 的 props 动态路径（节选）
if (oldProps !== newProps) {
  const hasDynamicFlag = patchFlag & (PatchFlags.CLASS | PatchFlags.STYLE | PatchFlags.PROPS | PatchFlags.FULL_PROPS)
  if (patchFlag === PatchFlags.BAIL || !hasDynamicFlag) {
    // 无优化标记：朴素全量 diff（回退路径，保证安全）
    // ……（新旧 props 全键两轮遍历：改动的打补丁、消失的置 null，从略）
  } else {
    // CLASS / STYLE 独立处理（真 Vue 同款：这两类不住 dynamicProps 名单）
    if (patchFlag & PatchFlags.CLASS) {
      hostPatchProp(el, 'class', oldProps['class'], newProps['class'])
    }
    // ……（STYLE 位同法，只比 style 一个键，从略）
    // PROPS：按编译期声明的名单逐个 diff
    if (patchFlag & PatchFlags.PROPS) {
      const keys = dynamicProps || EMPTY_ARR
      for (const key of keys) {
        if (key === 'class' || key === 'style') continue
        if (newProps[key] !== oldProps[key]) {
          hostPatchProp(el, key, oldProps[key], newProps[key])
        }
      }
      // ……（第二轮名单遍历查删除、FULL_PROPS 键并集，从略）
    }
  }
}
```

走读分流。手写渲染函数的 vnode patchFlag 为 0，走 if 支回退全量比对——这就是「纯增量收益」：没有标记的路径一行不差地保留旧行为。编译产物走 else 支：CLASS 位只比 class 一个键，PROPS 位只遍历名单，FULL_PROPS 取键并集。为什么 PROPS 位不用管删除？因为名单来自新 vnode 的编译期声明，名单里的键在新 props 里必然存在；真正可能消失的动态键会走 FULL_PROPS。「哪个键可能变、会不会消失」，编译器替渲染器全想完了。

第一件套至此闭环：比对范围从「全部属性」收缩到「编译期已知会变的属性」。但它只优化了「一个元素自己的比对」——元素所在的树，更新时仍要递归走查。下一节解决树的问题。

## 11.2 block：把树打平成动态清单

第二组朴素问题。设想更新一棵十层深的模板树，动态的只有两处文本。即便每个元素都带上了 patchFlag，「哪些节点带标记」仍要靠递归遍历才能知道——走到那个节点，才知道它动不动态。能不能把动态节点提前列成一张清单，更新时只走清单？

清单当然可以列，难在列的动作发生在哪。运行时列等于先递归一遍，白费。答案还是编译期：编译器知道模板结构，也就知道每个动态节点在结构里的位置。官方文档给这里的机制起名区块（block）：「内部结构是稳定的一个部分可称之为一个区块」，它追踪「所有带更新类型标记的后代节点（不只是直接子节点）」，收益是更新时「只需要遍历这个打平的树而非整棵树」。本仓库实现的是单块版本：根节点是块。上一节的产物里已经出现过 `_openBlock(), _createElementBlock(...)`，它由两步产生：transform 收尾的 createRootCodegen 把根（单根或多根 Fragment）的 codegenNode 置 isBlock 并注册 helper；codegen 遇 isBlock 先吐 `_openBlock(), `，再把 `_createElementVNode` 换成 `_createElementBlock`。

运行时的一半在 vnode.ts：

```ts
// packages/runtime-core/src/vnode.ts —— block 树（节选，注释为原文件自带）
export let currentBlock: VNode[] | null = null
const blockStack: (VNode[] | null)[] = []

/** 开启一个新块：此后创建的「动态 vnode」会被收进 currentBlock */
export function openBlock() {
  blockStack.push((currentBlock = []))
}

// ……（closeBlock：弹栈恢复外层块，从略）
function setupBlock(vnode: VNode): VNode {
  vnode.dynamicChildren = currentBlock || null
  closeBlock()
  return vnode
}

/** 块根：先整棵创建（含收动态子节点），再把 dynamicChildren 挂到自己身上 */
export function createElementBlock(
  type: any,
  props?: any,
  children?: any,
  patchFlag?: number,
  dynamicProps?: string[] | null,
): VNode {
  const vnode = createVNode(type, props, children, patchFlag, dynamicProps, true /* isBlockNode */)
  return setupBlock(vnode)
}
```

收集发生在建 vnode 的途中。render 执行时先调 `_openBlock()` 压一个空数组作为 currentBlock；此后每次 `_createElementVNode`，createBaseVNode 末尾都过一遍收集条件：

```ts
// packages/runtime-core/src/vnode.ts —— createBaseVNode 末尾
  // block 收集（7-3）：动态（patchFlag>0 或组件）且非块自身 → 进当前块
  if (
    !isBlockNode &&
    currentBlock &&
    (vnode.patchFlag > 0 || vnode.shapeFlag & ShapeFlags.COMPONENT)
  ) {
    currentBlock.push(vnode)
  }
```

两个条件值得各问一句。为什么 `patchFlag > 0`？因为 HOISTED 的静态节点不该进清单——它们另有零成本通道（11.3 节），而负数哨兵恰好被这个大于号排除。为什么组件 vnode 放行？因为组件常带 patchFlag 0 却必须更新——子组件内部状态的变化不经过父级属性。`isBlockNode` 排除块自身。收集是沿途的：建立深层子树时，孙子辈的动态 vnode 一样路过这个条件进清单，这正是「不只是直接子节点」的实现。子树建完，setupBlock 把 currentBlock 挂为块根的 dynamicChildren 并弹栈。optimization.spec.ts 第 4 例实测锚定了结果：`<div><span class="s">static</span><p>{{ x }}</p></div>` 的根块清单长度为 1，唯一成员是 `<p>`。

**把收集过程逐步跑出来看。** 换一张信息更密的模板：`<div><span>ok</span><input :title="t"><b>{{ b }}</b></div>`——静态 span、动态 :title 的 input、插值 b 各占一类。先看产物（实测）：

```js
// compile('<div><span>ok</span><input :title="t"><b>{{ b }}</b></div>').code —— 实测
const { createElementVNode: _createElementVNode, toDisplayString: _toDisplayString, openBlock: _openBlock, createElementBlock: _createElementBlock } = Vue
const _hoisted_1 = _createElementVNode("span", null, "ok", -1)
return function render(_ctx, _cache) {with (_ctx) {
    return _openBlock(), _createElementBlock("div", null, [_hoisted_1, _createElementVNode("input", {title: t}, null, 8, ["title"]), _createElementVNode("b", null, _toDisplayString(b), 1)], -1)
  }
}
```

产物已经定了执行序：`_hoisted_1` 在渲染函数外，render 每次执行只引用不重建。再给运行时的三个入口（openBlock、createElementVNode、createElementBlock）各包一层打点，在每个调用前后读取 currentBlock 的实时值（实测，打点方式见章末「动手验证」）：

| 执行到 | 这一步发生了什么 | currentBlock 此刻 |
|---|---|---|
| （render 外）求值 _hoisted_1 | patchFlag 为 -1，非正数进不了清单；此刻也没有块开着 | null |
| `_openBlock()` | 压栈并新开空清单，blockStack 深度 0 到 1 | `[]` |
| `_createElementVNode("input", …)` | patchFlag=8 大于 0，进清单 | `[<input>]` |
| `_createElementVNode("b", …)` | patchFlag=1 大于 0，进清单 | `[<input>, <b>]` |
| `_createElementBlock("div", …)` | 先整棵建块根（isBlockNode=true，自身不进清单），setupBlock 把 currentBlock 挂为 dynamicChildren 后弹栈 | 弹栈后仍指向刚挂载的清单，见下注 |

收口后的实测结果：根 vnode 的 dynamicChildren 恰好是 `[<input> flag=8 名单["title"]>, <b> flag=1>]`，静态 span 不在场。它有两重不在场的理由：被提升后 render 不再重建；即便重建，-1 也过不了收集条件的大于号。块根本人实测 patchFlag 也是 -1（div 无动态属性、children 是数组不算动态文本），但 isBlock 让它既不提升也不进任何清单。

两处脚注。其一，实测中 createElementBlock 返回后 currentBlock 并不归 null，而是仍指向刚收口的数组：本仓库的 closeBlock 写作 `currentBlock = blockStack.pop() ?? null`，pop 的返回值正是被弹出的数组本身。仓库只有根一层块、栈深恒为 1，这个残留无行为影响；官方的 closeBlock 是 pop 之后再读新栈顶，多层块下才能正确恢复外层清单（差距节再记）。其二，children 里的 `_toDisplayString(b)` 求值成字符串，不产生 vnode、更不进清单——插值的动态性记在宿主元素 b 的 TEXT 位上，更新走 b 自己的 TEXT 快路径。

更新时的消费在 renderer。块根的 patchElement 走到 patchChildrenAndBlock，先过守卫：

```ts
// packages/runtime-core/src/renderer.ts —— patchChildrenAndBlock（节选，注释有删节）
// 守卫：dynamicChildren 必须「非空 + 等长」才升，否则回退全量 diff——
//  `<div>{{x}}</div>` 这类根自身是动态（TEXT 位）但无独立动态子节点的情况，
//  块快速路径会漏更新根自己的文本
if (
  n1.dynamicChildren &&
  n2.dynamicChildren &&
  (n2.dynamicChildren as any[]).length > 0 &&
  (n1.dynamicChildren as any[]).length === (n2.dynamicChildren as any[]).length
) {
  patchBlockChildren(n1, n2, el, parentComponent)
  return
}
```

守卫通过就逐位配对：

```ts
// packages/runtime-core/src/renderer.ts —— patchBlockChildren
  function patchBlockChildren(
    n1: VNode,
    n2: VNode,
    fallbackContainer: any,
    parentComponent: ComponentInternalInstance | null,
  ) {
    const oldDyn = (n1.dynamicChildren || []) as VNode[]
    const newDyn = (n2.dynamicChildren || []) as VNode[]
    for (let i = 0; i < newDyn.length; i++) {
      patch(oldDyn[i], newDyn[i], fallbackContainer, null, parentComponent)
    }
  }
```

两件套在这里合流：清单里每个节点自己的比对，回到 11.1 的按位分流。递归依旧存在，但只在动态节点身上发生——静态子树连被看一眼的机会都没有。

两个守卫各有一段血泪。为什么要求非空？因为块路径命中后 return，跳过了根自己的 TEXT 位处理。实测最小反例：模板 `<div>{{ x }}</div>` 挂载后，根的 `patchFlag === 1`（TEXT 位），`dynamicChildren` 却是长度 0 的数组——根自己就是块、不进清单，children 是字符串也不产生子 vnode。若去掉非空守卫径直走块路径，清单空转一圈返回，根的文本永远停在首屏。为什么要求等长？因为结构变化会让清单长度改变。实测 v-for：模板 `<div><p v-for="i in n">{{ i }}</p></div>`，`n` 从 3 改到 5 后清单长度由 3 变 5；逐位配对会越界错配，守卫放下全量 diff 兜底，页面上五个 p 全部正确渲染。

**三条守卫案例逐条实测。** 口头说「翻车」不如把翻车现场摆出来，三个模板各挂载一次、改值、看 DOM。

案例一，非空守卫。模板 `<div>{{ x }}</div>`：实测挂载后根 patchFlag=1、清单长度 0；`x.value = '2'` 加一次 nextTick，DOM 由 `<div>1</div>` 变成 `<div>2</div>`。守卫在长度 0 处判否，流程落进后面的 TEXT 快路径，文本更新由此兑现。反事实推演（对照 patchBlockChildren 的循环体）：若无非空判断，块路径对空清单循环零次即 return，TEXT 路径被 return 挡在身后，DOM 停在 `<div>1</div>`——「清单空转、文本停首屏」的具体形态。

案例二，等长守卫。模板 `<div><p v-for="i in n">{{ i }}</p></div>`，实测两代清单与 DOM：

| n 值 | dynamicChildren 长度（实测） | DOM（实测） |
|---|---|---|
| 3 | 3 | `<div><p>1</p><p>2</p><p>3</p></div>` |
| 5 | 5 | `<div><p>1</p><p>2</p><p>3</p><p>4</p><p>5</p></div>` |

长度 3 对 5 配不上对，守卫判否回退全量 diff，五个 p 全部正确落页。逐位配对若强行执行，第 4、5 位的新节点会对上 undefined，越界错配正是守卫要拦的形态。回退之后发生的事也实测过一遍：patchChildren 走数组对数组的全量路径，更新前的三个 p 与更新后的前三个 p 是同一批 DOM 节点（逐个 `===` 比较为 true），新增的第 4、5 个 p 被挂载，文本落在 1 到 5。也就是说回退不是「推倒重来」，第 7 章的 diff 在旧节点复用的意义上依旧是增量的——优化分层各自让路，正确性与复用始终保底。

案例三是一条实测撞见的残余边界：清单非空且等长，但根自身还带动态文本。模板 `<div>{{ x }}<b>{{ y }}</b></div>`，根 patchFlag=1、清单是 `[<b>]`——两条守卫全放行，块路径照走、return 照返回，根自己的 x 处在谁也不管的地带。实测把 x 与 y 同时改值再 nextTick，DOM 是 `<div>x1<b>y2</b></div>`：b 里的 y 更新了，根自己的 x1 停在首屏。这不是守卫的逻辑写错，而是它防不住的形态——守卫只判断「清单能不能配对」，判断不了「根的 TEXT 位还有没有活没干」。官方实现把根的 TEXT 处理放在块路径之后单独执行，案例一与案例三的形态一并覆盖；本仓库的 TEXT 快路径排在块路径 return 之后，只能靠守卫排除空清单，案例三是留给后续改进的已知边界。

官方文档还说明「v-if 和 v-for 指令会创建新的区块节点」——本实现没有做。实测 v-if 分支的产物：

```js
// compile('<div v-if="ok"><p>{{ x }}</p></div>').code（实测产物，首行 helper 解构与函数包装从略）
return (ok) ? _createElementVNode("div", null, _createElementVNode("p", null, _toDisplayString(x), 1), -1) : _createCommentVNode("v-if", true)
```

分支里是普通 `_createElementVNode`，没有 `_openBlock`；根是条件表达式时整棵模板连块都不是。代价如实说：结构一旦变化——v-if 切换（带标记的分支节点被无标记的注释占位顶替，清单长度变了）、v-for 增删——守卫一律回退全量 diff，第 7 章的五步 keyed diff 原样接管。那套算法正是为回退而保留的，正确性优先，优化只锦上添花。

树的问题至此有了清单解。但清单思路还剩最后一个浪费：完全不变的节点，连「进不进清单」都不该是问题。下一节把它们请出所有比对。

## 11.3 静态提升：不变的东西只造一次

第三个朴素问题。`<span>ok</span>` 这样纯静态的子树，每次渲染都重新 `_createElementVNode` 一遍，还以「无标记节点」的身份参与 children 比对。两次渲染的结果必然全等，凭什么不能只造一次？官方文档的机制名是缓存静态内容：首次渲染时缓存 vnode，重渲染「完全跳过对它们的差异比对」。

实现是 codegen 的一个预扫描。generate 在输出 render 函数之前，先沿 codegenNode 树收集可提升的子树，逐个生成模块顶层的 const：

```ts
// packages/compiler-core/src/codegen.ts —— generate 开头（节选，注释为原文件自带）
// 7-3 静态提升：先收集可提升的静态子树，逐个生成 const（渲染期只会创建一次）
const hoistedNodes: any[] = []
collectHoistedNodes(ast.codegenNode, hoistedNodes)
if (hoistedNodes.length) {
  for (let n = 0; n < hoistedNodes.length; n++) {
    const tmp = createSubContext(context)
    // ……（生成 const 本体时揭掉提升标记、防止自引用，从略）
    push(`const _hoisted_${n + 1} = ${tmp.code}`)
    newline()
  }
}
push(`return function render(_ctx, _cache) {`)
```

对照实测产物读：

```js
// compile('<div id="a"><span>ok</span><b>{{ n }}</b></div>').code（实测产物，首行 helper 解构与函数包装从略）
const _hoisted_1 = _createElementVNode("span", null, "ok", -1)
return _openBlock(), _createElementBlock("div", {id: "a"}, [_hoisted_1, _createElementVNode("b", null, _toDisplayString(n), 1)], -1)
```

`_hoisted_1` 是渲染函数外的常量，render 每次执行引用的都是同一个 vnode 对象，原位置只剩一个名字。渲染器的配合只有一行——第 5 章埋的伏笔在此兑付：

```ts
// packages/runtime-core/src/renderer.ts —— patch 第一行
  if (n1 === n2) return
```

两条通道都通向「完全跳过差异比对」：全量回退路径里，提升节点作为 children 参与时新旧是同一引用，patch 开头直接短路；块路径里，HOISTED 是负数、进不了 dynamicChildren 清单。零比对、零创建，只剩一次变量查找。

提升判定的保守程度值得单独看：

```ts
// packages/compiler-core/src/codegen.ts —— collectHoistedNodes（节选，注释为原文件自带）
const hoistable =
  node.patchFlag === -1 &&
  !node.isComponent &&
  !node.isBlock &&
  // children 必须是纯静态形态（JS 调用如 renderSlot 依赖 _ctx，提升会把 _ctx 移出
  // with 作用域 → ReferenceError；多 children 数组保守不升）
  (node.children == null ||
    typeof node.children === 'string' ||
    node.children.type === NodeTypes.TEXT_CALL) &&
  // props 必须全静态（动态值 age = _looseToNumber(...) 在 with 外引用会 ReferenceError）
  isStaticProps(node.props)
// ……（命中则登记 _hoistedId 收进 out，其余情况深入子节点继续找，从略）
```

逐条读。`patchFlag === -1` 即 11.1 收尾的全静态判定；children 只允许字符串或单个静态文本调用，多子节点的数组一律不升；`isStaticProps` 要求每个属性值都是静态字面量。为什么苛刻到这个地步？根子在上一篇的 `with (_ctx)` 方案：提升会把表达式搬到 render 函数外的 const 里，脱离 with 块，凡靠 `with (_ctx)` 解析的名字在那里全部失联。

这不是假想的坑，仓库真实踩过。看 v-model.number 的实测产物：

```js
// compile('<input v-model.number="msg" />').code（实测产物，首行 helper 解构与函数包装从略）
return _openBlock(), _createElementBlock("input", {value: msg, onInput: ($event) => (msg = _looseToNumber($event.target.value))}, null, 8, ["value", "onInput"])
```

假设它被误判全静态而整体提升：`value: msg` 与箭头函数体里的 `msg` 都靠 `_ctx.msg` 解析，搬出 with 块后求值即抛 ReferenceError，渲染函数一创建就白屏。修复提交 f49d408 把它记为「展示页白屏根因」，此后 isStaticProps 进了判定。有趣的对照是 `_looseToNumber` 不怕提升：helper 名在首行 `const { looseToNumber: _looseToNumber, ... } = Vue` 顶层解构，本来就不靠 with——transformElement 里那句注释「裸名在 with(_ctx) 里解析不到」说的正是反向的同一件事。

官方文档还提到更进一步的一招：大量连续的静态内容会被存成纯 HTML 字符串、经 innerHTML 一次挂载。本实现未做——它需要渲染器新增 insertStaticContent 宿主操作与连续静态节点的计数统计，收益场景（超长静态模板）在教学主干之外。

三件套至此齐了。标记收缩「一个元素的比对」，区块收缩「一棵树的遍历」，提升干脆取消「静态节点的参与」。贯穿三者的纪律只有一条：编译期确定的信息，运行期不再重复计算。

## 本章小结

编译器与渲染器之间是一份单向性能契约。transformElement 扫描属性时把动态性统计成 patchFlag 位掩码与 dynamicProps 名单，patchElement 按位分流，无标记则回退全量。根节点经 openBlock/createElementBlock 把沿途的动态 vnode 收进 dynamicChildren，更新时「非空且等长」守卫通过才走打平清单，否则回退全量 diff。纯静态子树被 codegen 提升为渲染函数外的 const，跨渲染同一引用，经 patch 开头的 `n1 === n2` 与「负数进不了清单」两条通道跳过比对。提升判定刻意保守，为的是不让依赖 `with (_ctx)` 的表达式漏出作用域。

## 与官方实现的差距

以下均对照 `third_party/vue-core`（v3.5.x）核对：

- **v-if/v-for 不建新块**：官方 vIf.ts 以 convertToBlock 把每个分支转成块（源码注释「Change createVNode to createBlock」），vFor.ts 为每个迭代项置 `childBlock.isBlock = shouldUseBlock`；本仓库只有根是块，实测产物分支为普通 `_createElementVNode`。结构变化一律靠守卫回退全量，正确性等价、更新成本更高。
- **空清单守卫**：官方对「新旧 dynamicChildren 长度不等」强制回退（源码标记 #6385），但不要求非空——根自身的 TEXT 位在块处理之后的 `patchFlag > 0` 段单独执行，空清单不漏更新；本仓库把根的 TEXT 放在块路径 return 之后，必须自加非空守卫。
- **PROPS 位细节**：官方对名单内与旧值相等的 `value` 键仍强制 patch（#1471，修输入框回显时序），本仓库一律 `!==` 才比。
- **提升面更窄**：官方 cacheStatic 除整棵子树外，还提升常量 props 对象与 dynamicProps 数组；本仓库只提升整棵子树，多 children 数组保守不升。官方另有 v-memo/v-once，本仓库没有。
- **无预字符串化**：官方编译器把连续静态节点拼成 HTML 字符串、runtime-dom 的 insertStaticContent 经 innerHTML 挂载；本仓库未实现。
- **枚举空位**：NEED_PATCH（1 << 9，官方语义为「仅需 ref/指令等非属性 patch，标记以便父块追踪」）、DYNAMIC_SLOTS 等位在本仓库只有定义、无生产者也无消费者；-1 哨兵官方已更名 CACHED，本仓库沿用旧名 HOISTED。
- **closeBlock 的恢复方式**：官方先 pop 再读新栈顶（`blockStack.pop(); currentBlock = blockStack[blockStack.length - 1] || null`，`runtime-core/src/vnode.ts`），多层块嵌套时能正确恢复外层清单；本仓库写作 `currentBlock = blockStack.pop() ?? null`，pop 的返回值即被弹数组，收口后 currentBlock 仍指向已挂载的清单（11.2 实测可见残留）。单层块下无行为差异；若将来按官方做法给 v-if/v-for 建子块，此处需先修正，否则内层块收口会把外层清单顶掉。
