## 1. 这一阶段学到了什么

一句话：**Vue3 响应式 = 用 Proxy 包裹对象 + 两套 HashMap 记录依赖 + 写时精确触达受影响的效果**。

完整心智模型（配上下面的脑袋图理解）：

```
        targetMap (WeakMap<target, Map<key, Dep>>)
        ┌─────────────┐
        │   target    │──► depsMap (普通 Map)
        │             │       ├─ key「foo」──► dep = Set<Effect>{effect1, effect2}
        │             │       └─ ITERATE_KEY ► dep = Set<Effect>{effect3}
        └─────────────┘
        effect.deps（反向索引，每个 effect 都记得自己订阅过哪些 dep）
```

- **读**（`state.foo`）→ Proxy get → `track(target,'get','foo')` → 把**当前正在运行的 effect** 加进 `foo` 的订阅集合；
- **写**（`state.foo = 2`）→ Proxy set → `trigger(target,'set','foo')` → 把订阅了 `foo` 的所有 effect 排队执行。

### 概念清单（每一条都能在代码里指出来）

| 概念 | mini 位置 | 一句话 |
|---|---|---|
| `targetMap` / `dep` | `effect.ts` | 「对象 → key → 订阅者集合」的两层索引 |
| 分支切换清理 | `cleanupEffect` | effect 每次重跑前摘除旧订阅，防止幽灵依赖 |
| `activeEffect` | `effect.ts` | 当前正在执行的 effect，track 时的「谁在订阅」 |
| `effectStack` | `effect.ts` | 嵌套 effect / computed 链，执行完成后还原外层订阅者 |
| ADD vs SET | `baseHandlers.ts` `createSetter` | 新增 key 触发 ADD（连迭代者一起），改值触发 SET |
| `ITERATE_KEY` | `operations.ts` | for...in / Object.keys 的订阅锚点 |
| 惰性深度代理 | `createGetter` | 嵌套对象被访问到时才包 Proxy，同一对象缓存同一代理 |
| `ReactiveFlags.*` | `operations.ts` | 暗号字段，isReactive/toRaw 的零成本通道 |
| ref 解包 | `createGetter` + `RefImpl` | reactive 里的 ref 属性读出来是裸值 |
| computed 脏位 | `computed.ts` `_dirty` | lazy + 只重算一次的开关 |

### 2.2 3.5 内部与 mini 的差异（行为一致，性能不同）

| 维度 | 3.5.x | mini |
|---|---|---|
| 依赖集合 | `Link` 双向链表 + 每 dep 一个 `version` 号 + `globalVersion` | `Set<ReactiveEffect>`数组 |
| 触发批处理 | `batch()` + `NOTIFIED` 位 + `startBatch/endBatch` | 直接同步逐个执行 |
| 空 dep 回收 | `dep.map.delete(key)`（无人订阅即删除） | 保留空 Set（简化，可回收不追求） |
| 抖动 | `EffectFlags` 位标记 ACTIVE/RUNNING/TRACKING/DIRTY… | boolean 字段 |
| computed 优化 | 全局版本号快速路径 + 无订阅不重算 | `_dirty` 位 |

> 关键认知：**行为由协议（track/trigger 语义）保证，数据结构只是实现**。这也是为什么 mini 能先做简化版、后面再读复杂版时依然能懂。

### 2.3 三个必须反复读的点

1. **`set` 里的 receiver 守卫**（`baseHandlers.ts`）：
   子对象 `child` 的 setPrototypeOf 挂在父对象 `parent` 下，`child.own = 1` 会走到 `parent` 的 set trap，此时 `receiver = child`，`target = parent`。`target === toRaw(receiver)` 为 false → 不触发父的更新。这是「只对自己负责」。

2. **数组整数下标新增**：
   `arr[3] = x` 在 length=3 时是 ADD（`Number(key) < target.length` 判定），ADD 会顺带触发 `length` 的订阅者 —— 因为越界写改变了数组长度。

3. **computed 的懒 + 脏**：
   `.value` 被读 → `trackRefValue` 收订阅者 → 脏才重算。依赖变化时调的是它的 **scheduler**（只置脏 + 通知下游），绝不在触发瞬间同步重算 —— 若没人读它，就一直脏着，省一次计算。

## 3. review gate 参考答案

### Q1：trigger 里为什么要 `[...dep]` 拷贝再遍历？

触发一个 effect 会先 `cleanupEffect` 再重跑，重跑时会**改写同一个 dep（把旧订阅删掉、加新订阅）**。如果遍历的是原集合，边遍历边删会产生：
- 漏跑（被删除的元素index错位）或
- 重复跑/死循环（新加进的订阅又被遍历到）。

拷贝一份快照遍历，保证「这一轮触发只面对触发瞬间的真实订阅者」，过滤掉中途增删的噪音。真 Vue 3.5 用的链表同样在触发前通过 `NOTIFIED` 位快照。

### Q2：computed 的 `_dirty` 如何实现「lazy + 只重算一次」？

- `_dirty=true` 表示「缓存失效，下次读 .value 时重算」；
- 依赖变化时 scheduler **只**置 `_dirty=true` 并 `triggerRefValue`（通知下游「我脏了」），**不**立刻重算 —— 步骤 1 就完成了 lazy；
- 下游 effect 因 `triggerRefValue` 被触发，重新执行时读 `.value`，发现 `_dirty`，重算一次并缓存 —— 步骤 2 完成「只重算一次」；
- 若这一轮没人读它，就一直脏着，零计算。

### Q3：新增一个本来不存在的属性，为什么不会让已有 effect 重跑？（/ 它怎么做到）

其实**会** —— 如果那个 effect 订阅的是「整个对象」（for...in、Object.keys 走 ownKeys→`ITERATE_KEY`）。真正「不会」的是只订阅「具体 key」的 effect：新增属性只触发 `dep(Foo)` 和 `ITERATE_KEY`，不触发 `dep(bar)`。
所以答案是：renderer 渲染函数其实读了很多 key 但**通常没订阅 ITERATE_KEY**（模板里不会 for...in 一个普通对象），于是新增属性不会重渲染。而 Vue 3 对「响应式对象添加新 key 后模板能显示」的支持来自 **watch deep / computed 访问链 / 渲染函数按需重新读取**（用户手动触发），这是另一个话题 —— 关键结论：**浅层收集 = key 级，深层收集 = 对象级（ITERATE）**，理解了这个区分就理解了行为。
