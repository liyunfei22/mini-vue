# 01-手写响应式系统：把「数据变了我自己动」拆成一张两层表

> 本篇写给：会用 `ref`、`reactive` 写 Vue3 组件，但没想过「敲下 `count.value++` 时，页面上那几处用到它的文本为什么跟着变了」的读者。
> 读完你会得到一张完整的心智地图：targetMap 两层表、track/trigger 两个入口、effect 的 cleanup 与分支切换、computed 的 lazy 与脏位、ref 的解包容器，最后落在 effectScope——为什么各种状态库都拿它当地基。

## 为什么需要：先回答「谁在依赖谁」

Vue 的招牌是「声明式 UI」：我只管数据，界面自己跟上。但这句广告语的背面藏着一个工程问题——当 `count` 变化时，运行时要凭空找出「此刻屏上所有用过 count 的地方」，并且只更新它们，不能每分钟把 DOM 全量扫一遍。

所以响应式系统的本质就两笔账：

1. **读账**：某个函数执行时访问了 `state.count`，运行时要记下「count 被这个函数依赖了」；
2. **写账**：某处改了 `state.count`，运行时要凭账本找出所有依赖者，逐一通知。

「读」叫 track（收集），「写」叫 trigger（触发）。支撑它们的心脏，是一张两层的表——这就是本篇的主线。

## 关键实现：targetMap 两层表 + track / trigger

数据模型只有一截：

外层 `targetMap`：键是原始对象，值指向内层 `Map`；内层 `Map` 的键是属性名，值是一份 dep（一个 `Set<ReactiveEffect>`）。外层用 WeakMap 是刻意的——原对象被回收时，挂在它身上的整条依赖记录能跟着一起消失，不会拖住内存。

```ts
// packages/reactivity/src/effect.ts
const targetMap: WeakMap<any, Map<any, Dep>> = new WeakMap()   // Dep 就是 Set<ReactiveEffect>
export function track(target: object, type: TrackOpTypes, key: unknown) {
  if (!shouldTrack || !activeEffect) {
    return                                    // 没有在干活的 effect: 裸读不产生订阅
  }
  let depsMap = targetMap.get(target)
  if (!depsMap) {
    targetMap.set(target, (depsMap = new Map()))
  }
  let dep = depsMap.get(key)
  if (!dep) {
    depsMap.set(key, (dep = createDep()))
  }
  trackEffects(dep)                           // dep.add(activeEffect) + effect.deps.push(dep)
}
```

`activeEffect` 是全局指针，指向「正在执行的副作用」；`shouldTrack` 是收集总开关。两者齐备，访问属性才会建立订阅——这解释了 `reactive({}).foo` 的裸读为什么毫无副作用。

trigger 反着走：从 targetMap 找出所有命中的 dep，逐个执行其中的 effect。难点在于「一次改动可能要打中多个 dep」——数组的隐式联动最典型（下面节选 CLEAR / length / ADD 三类命中；Map 的 SET、DELETE 等分支与「去重后执行」的收尾见配套工程源码）：

```ts
export function trigger(target, type, key) {
  const depsMap = targetMap.get(target)
  if (!depsMap) return
  let deps: (Dep | undefined)[] = []
  if (type === TriggerOpTypes.CLEAR) {             // 清空：所有 dep 全命中
    deps = [...depsMap.values()]
  } else if (key === 'length' && isArray(target)) {
    // length 被调短：下标 ≥ 新长度的 dep 一并命中（forEach 细节见工程源码）
  } else {
    if (key !== void 0) deps.push(depsMap.get(key))   // 先命中"被改的那个 key"
    if (type === 'ADD' && !isArray(target))           // 新增 key：for...in 订阅者
      deps.push(depsMap.get(ITERATE_KEY))
    if (type === 'ADD' && isArray(target) && isIntegerKey(key))
      deps.push(depsMap.get('length'))              // 数组越界新增：length 联动
  }
} // 命中后：逐 dep 收集 → 去重 → 防自触发 → scheduler 优先执行（见工程源码）
```

数组新增下标会隐式改 length、Map 的 set / Set 的结构变化要惊动迭代器——这些「隐式副作用」都必须显式 trigger。真 Vue 3.5 的内核没变，只是把 Set 换成了版本号 + Link 双向链表（官方源码见 https://github.com/vuejs/core），语义一致、成本更低；我的复刻过程先用最朴素的 Set 把道理讲透。

## effect 的生命周期：cleanup 与分支切换

`effect(fn)` 首次调用就执行 fn，之后 fn 依赖的数据一变化，trigger 就会重跑它。但有一件事必须在每次重跑前处理好，叫**分支切换**：

```ts
effect(() => {
  result = state.ok ? state.a : state.b
})
```

当 `ok` 从 true 翻成 false，fn 重跑后只访问 `b`、再不碰 `a`。如果依赖表还留着「这个 effect 订阅了 a」，之后改 `a` 会让它白跑一次——这就是幽灵依赖：不但浪费，还会造成「改了个无关变量界面却动了」的诡异 bug。

解法一句话：每次 run 之前，把旧订阅**全量抹掉**，跑 fn 时再从头收集。全量清空而不是精挑细选，简单且永远正确。

```ts
// packages/reactivity/src/effect.ts —— ReactiveEffect.run：重跑前先清空旧订阅
// （类身上的 deps 数组是"订阅过的所有 dep"的反向索引，从略）
run(): T | undefined {
  // 已停用的 effect 退化为朴素执行、不再收集（分支从略）
  if (!effectStack.includes(this)) {    // 防止对自身重入
    cleanupEffect(this)                 // <-- 关键：run 之前清空旧订阅
    try {
      effectStack.push(this)
      activeEffect = this               // 全局指针指向自己，收集开始
      return this.fn()
    } finally {
      effectStack.pop()
      activeEffect = effectStack[effectStack.length - 1]  // 还原外层 effect
    }
  }
}
```

`cleanupEffect` 把 effect 从它订阅过的每个 dep 里摘除，并清空反向列表；fn 一跑，刚刚访问过的属性又被重新收集。这一进一出，保证了「dep 集合里永远只有当前这次执行真正访问过的东西」。这是整个响应式系统里最值得想明白的一段。

## computed：lazy + 脏位

computed 是「三合一」：它本身是一个 Ref（有 `.value`）；内部挂着一个订阅者 effect（getter 执行时收集源依赖）；自己身上也带一个 dep（记录谁读了它）。

```ts
// packages/reactivity/src/computed.ts —— 源变化的 scheduler：只置脏位（节选）
constructor(getter) {
  this.effect = new ReactiveEffect(getter, () => {
    if (!this._dirty) {
      this._dirty = true        // 不重算，只置脏位
      triggerRefValue(this)     // 告诉读者"我脏了，重新读我"
    }
  })
}
```

读取侧在 getter 里——脏才重算，算完缓存：

```ts
// packages/reactivity/src/computed.ts —— 读取侧：脏才重算（节选）
get value(): T {
  trackRefValue(this)          // 读者登记为本 computed 的订阅者
  if (this._dirty) {
    this._dirty = false
    this._value = this.effect.run()!
  }
  return this._value
}
```

两个设计点值得细品。一是 **lazy**：`_dirty` 初始为 true，第一次读 `.value` 才真正 run，结果存在 `_value`，之后再读直接返回缓存。二是 **scheduler 不重算、只置脏位**：源依赖变化时，computed 内部的 effect 接收到的是 scheduler——它不重算 getter，只把 `_dirty` 置回 true，再通过 `triggerRefValue` 通知读过它的 effect。等到下一轮真的有人重新读 `.value`，才重算一次。于是「没人读就不算」，一个表达式被十个地方引用，也只算一次、更新一次。

## ref：给原始类型一个容器

`reactive` 靠 Proxy 代理整张对象图，但 Proxy 只能代理对象。`count = 0` 这种原始值怎么响应式？答案是包一层容器：把读写收敛到 `.value` 上，读走 `trackRefValue`、写走 `triggerRefValue`——和 effect 里那套完全复用同一个入口。

```ts
// packages/reactivity/src/ref.ts —— 读写收敛到 .value（节选）
class RefImpl<T = any> {
  private _rawValue: T          // 存"原始值"，判等用
  constructor(value, private readonly shallow) {
    this._rawValue = shallow ? value : toRaw(value)
    this._value = shallow ? value : toReactive(value)  // 对象则深代理
  }
  get value() { trackRefValue(this); return this._value }   // 读走 track
  set value(newVal) {
    if (hasChanged(newVal, this._rawValue)) {   // 值真变了才触发
      this._rawValue = newVal
      this._value = toReactive(newVal)          // shallow/readonly 判定从略
      triggerRefValue(this, newVal)             // 写走 trigger
    }
  }
}
```

`ref({...obj})` 时 `toReactive` 把对象转成 reactive 代理，所以 ref 也具备深响应式；`hasChanged` 保证「赋相同的值不触发」。而模板里你从不需要写 `.value`，是因为编译器在 render 时对顶层 ref 做了自动解包，setup 返回值那一层则由 `proxyRefs` 的浅解包代理处理——无论走哪条路，内核都是 trackRefValue / triggerRefValue 这两个函数。

## effectScope：为什么状态库拿它当地基

收尾一个「被真实生态反复使用」的抽象。它回答的问题是：effect 的清理太散。组件卸载时，它一路的 watch、computed、渲染 effect 要逐一 stop；状态库更甚——一个 store 可能开了几十个 effect，漏停一个就是孤儿订阅，改数据时静默地多跑没人收听的逻辑。

scope 的答案是：把「一批 effect 的生命周期」捆成一个整体。

```ts
// packages/reactivity/src/effectScope.ts —— run：把"当前 scope"换成自己（节选）
export class EffectScope {
  effects: ReactiveEffect[] = []     // 本 scope 收编的 effect
  scopes: EffectScope[] | undefined  // 子 scope
  run<T>(fn: () => T): T | undefined {
    if (this._active) {
      const currentScope = activeEffectScope
      try {
        activeEffectScope = this    // run 期间 new 出的 effect 自动登记进本 scope
        return fn()
      } finally {
        activeEffectScope = currentScope
      }
    }
  }
}
```

机制就一句：`scope.run(fn)` 执行期间把全局 `activeEffectScope` 换成自己，这段代码里 new 出的每个 ReactiveEffect 都会被构造器自动收进 `scope.effects`。于是状态库在顶层建一个 detached 的 scope，把所有 store 的 state、computed、订阅都创建在它内部，库销毁时一个 `.stop()` 递归停掉全部 effect、执行 `onScopeDispose` 清理回调、连子树 scope 一起带走——不留一个孤儿。组件实例本质也是一个非 detached 的 effect scope，所以才说 `onScopeDispose` 与组件的 `onUnmounted` 天然对偶。

## 动手验证：一张最小可运行五脏俱全

把上面的概念压到三十行，跑一遍就全通了：

```ts
import { effect, reactive, computed, effectScope } from '你的响应式包'

const state = reactive({ ok: true, a: 1, b: 2 })
let result = 0

effect(() => { result = state.ok ? state.a : state.b })   // 首次执行: result === 1

state.ok = false      // 分支切换: 依赖集合从 a 换成 b
state.a = 100         // 旧分支已清理 -> result 不动, 仍是 2
state.b = 10          // 新分支: result === 10

const double = computed(() => state.b * 2)   // lazy: 此刻还没算
let log = 0
effect(() => { log = double.value })          // 读 value 才触发计算: log === 20
state.b = 20                                  // 置脏 + 通知下游: log === 40
// double 的 getter 全程只被真正重算了两次

const scope = effectScope()
scope.run(() => {
  effect(() => { /* 挂在 scope 里的 effect */ })
})
scope.stop()          // 一批 effect 集体失活, 不剩孤儿订阅
```

## 真实踩过的坑

- **幽灵依赖**。第一版没有 cleanup，`ok` 翻转后再改 `a`，effect 会平白多跑一次，而且这类问题极难从现象反推。根因是「依赖表里留着早已不再访问的属性」。修正不是试着精准删那一条，而是「每轮重跑前全量清空、跑完重新收集」——前者是局部修补，后者是让每轮依赖都从本次执行中重新长出来，永远自洽。

- **嵌套 effect 的 activeEffect 还原**。早期用单个全局变量存 activeEffect，内层 effect 执行完直接清空，结果外层 effect 剩余代码里的属性访问全部收集失败，subscription 静默丢失。根因是「一个全局指针表达不了多层上下文」。改用 effectStack：入栈执行、finally 出栈并还原 `activeEffect = effectStack[栈顶]`。同一处还顺手防了自触发递归——trigger 收集时跳过「正在执行且没开 allowRecurse」的那个 effect，否则 `count.value++` 这种写法会把 effect 自己无限重入。

- **数组越界新增忘了 length**。测出 `arr[5] = 1` 之后关心 `arr.length` 的 effect 毫无反应，调试半天才意识到：JS 里给数组塞越界下标会自动把 length 撑大，而在响应式世界里，「语言的隐式副作用」也必须显式 trigger。修法就是 trigger 里专门的一支：`ADD + isArray + isIntegerKey(key)` 时额外通知 `length` 的订阅者；反过来把 `arr.length` 调短，还要找出所有「下标 ≥ 新长度」的 key 一起触发。

## 三步走复盘

- **机制怎么串**：targetMap 两层表是账本，track 记账、trigger 凭账通知；effect 每轮重跑前先 cleanup，保证账上永远只有本轮真正访问过的依赖；computed 用脏位把重算推迟到「有人读」那一刻；effectScope 把一批 effect 的生死捆成一个整体，`.stop()` 一键收割。
- **复刻第一行**：`const targetMap = new WeakMap()`——先立账本，track 和 trigger 都是围着这本账记与查；跑通「读记账、写通知」的最小闭环，再逐个补 cleanup、computed、scope。
- **讲给同事听**：「响应式系统就是一张『谁依赖谁』的账本：读的时候记账，写的时候照账通知，其余的全是让这本账保持准确的花活。」

## 自查三问

1. `targetMap` 为什么是两层？外层为什么必须用 WeakMap，而内层用普通 Map 也无妨？
2. 为什么必须在每次 run 之前全量 cleanup？假如改成"只删不再访问的那一条依赖"，会掉进什么坑？
3. computed 的 scheduler 为什么不直接重算，而只把 `_dirty` 置位再通知下游？试着想两个场景：十个地方读同一个 computed；改一个已经没有人再读的 computed 的源。
