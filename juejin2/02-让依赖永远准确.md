# 02 · 让依赖永远准确：账本的三种说谎方式

上一章收尾时，trigger 停在半路：收集到一堆 dep 之后，「去重、防自触发、按什么顺序执行」没有展开。当时说，这段收尾牵扯到副作用的清理与嵌套。现在还债——**账本记下的每一行订阅，凭什么保证它仍然是真的？**

本章把这个问题拆成账本说谎的三种方式。在这个过程中，我们会遇到三个新问题：分支切换之后，切走的旧依赖为什么还躺在账上？副作用里面再执行副作用，一根 `activeEffect` 指针为什么顾了里头就丢了外头？副作用读写同一个属性，为什么会自己触发自己、直到调用栈溢出？三个问题对应三道保险：每轮重跑前清账、执行栈、递归防护，装完之后，上一章留下的 trigger 收尾自然就位。

## 1.1 分支切换与幽灵依赖

先看一个最小的分支例子。很多组件里都有这样的逻辑：开关打开用 A 数据，关掉用 B 数据。写成副作用：

```js
// —— 手写最小例子 ——
const state = reactive({ ok: true, a: 1, b: 2 })
let result = 0

effect(() => {
  result = state.ok ? state.a : state.b
})
```

`ok` 为 true 时，副作用访问了 `ok` 和 `a`，账本上登记两条。把 `ok` 翻成 false，副作用重跑，这一轮真正访问的是 `ok` 和 `b`。问题来了：**`a` 那一行还在账上**。口说无凭，实测一下。照上一章两层账本的结构手写一版，刻意不做任何「除名」：

```js
// —— 手写朴素版：上一章的两层账本，只登记、从不出账 ——
let activeEffect = null
const targetMap = new WeakMap()

function track(target, key) {
  if (!activeEffect) return
  let depsMap = targetMap.get(target)
  if (!depsMap) targetMap.set(target, (depsMap = new Map()))
  let dep = depsMap.get(key)
  if (!dep) depsMap.set(key, (dep = new Set()))
  dep.add(activeEffect)          // 登记之后，再没有人动过这一行
}

function trigger(target, key) {
  const dep = targetMap.get(target)?.get(key)
  if (dep) for (const fn of dep) fn()
}

function effect(fn) {
  activeEffect = fn
  fn()
  activeEffect = null
}
// Proxy 拦截器沿用上一章：get 调 track，set 调 trigger
```

```js
let runs = 0
effect(() => { runs++; result = state.ok ? state.a : state.b })

state.ok = false    // 重跑：这一轮真正访问的是 ok 和 b
state.a = 10        // a 已经与结果无关，然而……
console.log(runs, result)   // 3 2 —— 副作用又跑了一次，result 原地不动
```

`runs` 从 2 涨到 3，`result` 却还是 2。这次重跑一无所获，是纯空跑。残留的 `a` 订阅像一个影子：依赖已经不在了，账上还有它的记录。这就是**幽灵依赖**。

它的害处分两层。轻的一层是浪费：切走的分支读的数据再怎么变，重跑也产不出新结果。重的一层是牵连。模板里的 `v-if`/`v-else` 正是这个三元表达式的真身，渲染副作用被幽灵依赖误触发，就是一次本不必要的重渲染。渲染函数整段重跑、新旧 vnode 全树比对，结果多半没变，开销是白付的。

空口说「白白重渲染」还不够硬。把朴素版与仓库版放进同一个测试文件并排跑，幽灵依赖的空跑一眼可见。朴素版连同它依赖的 Proxy 拦截器一起抄进来，仓库版直接导入：

```ts
// —— 对照实验：朴素版 vs 仓库版（可保存为临时 spec 运行，导入方式同 effect.spec.ts）——
import { describe, expect, it } from 'vitest'
import { effect, reactive } from '@mini-vue/reactivity'   // 仓库版

describe('幽灵依赖对照', () => {
  it('朴素版：a 残留在账上，空跑一次', () => {
    // —— 朴素版：与 1.1 完全一致，只登记、从不出账 ——
    let activeEffect: any = null
    const targetMap = new WeakMap()
    function track(target: any, key: any) {
      if (!activeEffect) return
      let depsMap = targetMap.get(target)
      if (!depsMap) targetMap.set(target, (depsMap = new Map()))
      let dep = depsMap.get(key)
      if (!dep) depsMap.set(key, (dep = new Set()))
      dep.add(activeEffect)
    }
    function trigger(target: any, key: any) {
      const dep = targetMap.get(target)?.get(key)
      if (dep) for (const fn of dep) fn()
    }
    function effect(fn: any) {
      activeEffect = fn
      fn()
      activeEffect = null
    }
    function reactive(obj: any) {
      return new Proxy(obj, {
        get: (t: any, k: any) => { track(t, k); return t[k] },
        set: (t: any, k: any, v: any) => { t[k] = v; trigger(t, k); return true },
      })
    }

    const state = reactive({ ok: true, a: 1, b: 2 })
    let runs = 0, result = 0
    effect(() => { runs++; result = state.ok ? state.a : state.b })

    state.ok = false
    state.a = 10
    console.log('朴素版：', runs, result)      // 朴素版：3 2
    expect([runs, result]).toEqual([3, 2])
  })

  it('仓库版：每轮清账，没有空跑', () => {
    const state = reactive({ ok: true, a: 1, b: 2 })
    let runs = 0, result = 0
    effect(() => { runs++; result = state.ok ? state.a : state.b })

    state.ok = false
    state.a = 10
    console.log('仓库版：', runs, result)      // 仓库版：2 2
    expect([runs, result]).toEqual([2, 2])
  })
})
```

两份实现的输入完全相同，输出并排放在一张表里：

| 步骤 | 朴素版 | 仓库版 |
|---|---|---|
| 创建副作用 | 首跑，runs = 1，账上登记 ok、a | 首跑，runs = 1，登记 ok、a |
| `state.ok = false` | 重跑，runs = 2；旧账原封未动 | 重跑，runs = 2；先清账再登记 ok、b |
| `state.a = 10` | 幽灵订阅拉起副作用，runs = 3，result 不动 | `dep(a)` 已空，收集不到订阅者，无事发生 |
| 最终输出 | `3 2`（多一次纯空跑） | `2 2`（每一次执行都有产出） |

对照里最容易看漏的一行是朴素版的最后一步：副作用确实又执行了一遍，`runs` 涨了，`result` 却纹丝不动。执行而没有产出，正是幽灵依赖的全部代价。

那能不能只精确删掉不再用的那几条，重跑时对比新旧两轮的访问清单？想法自然，但行不通。副作用体内是任意控制流：if/else、循环、提前 return 都可能出现，下一轮会访问哪些属性，在跑之前无从判断。跑完再对比，又得维护新旧两份访问清单，边角正确性很难咬死。

仓库的选择反其道而行：不猜，也不打补丁。**重跑之前把旧账全部清空，让这一轮的依赖从当次执行里重新长出来**。每轮结束，账上留下的必然是刚刚真实访问过的属性，结构上自洽，不需要任何对比。

落到代码。仓库把副作用升级成 `ReactiveEffect` 类，清账的核心是 `run()` 与 `cleanupEffect()` 这对搭档：

```ts
// packages/reactivity/src/effect.ts —— ReactiveEffect.run（类方法，注释为原文件自带）
  run(): T | undefined {
    // 已 stop 的 effect：直接跑一次 fn，但不做任何收集
    if (!this.active) {
      return this.fn()
    }
    // 防止递归 run（自身 guard：effect 的调度器/依赖把自身触发时跳过重入）
    if (!effectStack.includes(this)) {
      cleanupEffect(this)
      try {
        // 进入执行区：无条件开启收集（把外层 pauseTracking 状态压栈保护）
        enableTracking()
        effectStack.push(this)
        activeEffect = this
        return this.fn()
      } finally {
        effectStack.pop()
        // 恢复外层追踪状态
        resetTracking()
        activeEffect = effectStack[effectStack.length - 1]
      }
    }
  }
```

```ts
// packages/reactivity/src/effect.ts —— cleanupEffect（注释为原文件自带）
function cleanupEffect(effect: ReactiveEffect) {
  const { deps } = effect
  if (deps.length) {
    for (let i = 0; i < deps.length; i++) {
      deps[i].delete(effect)
    }
    deps.length = 0
  }
}
```

走读 `run()`。一进来先处理两种「不正常」：已 stop 的直接裸跑不收集；发现自己已在执行栈上的直接跳过，这行判断是 1.3 节的伏笔。正常路径四步：`cleanupEffect` 清旧账；压栈并接管 `activeEffect`；执行 `fn`，途中每次属性读取重新登记；`finally` 出栈还原。`cleanupEffect` 本体极简：遍历 `effect.deps`，把自己从每个 dep 里删掉，再清空这份列表。`enableTracking`/`resetTracking` 这对开关负责收集的暂停与恢复，与本章主线无关，先按下。

这里终于用上了上一章埋的伏笔。1.5 节走读 `trackEffects` 时有一行 `activeEffect.deps.push(dep)`：登记订阅的同时，把 dep 也记进副作用自己的 `deps` 数组。这就是**反向索引**。正向账本回答「哪个属性有哪些订阅者」，反向索引回答「这个订阅者订过哪些属性」，清理需要的恰好是后者。没有它，想把自己摘干净只能全表扫描 targetMap；有了它，清账只遍历自己名下的几行。

清账还顺带暴露一个隐蔽的坑：**清理发生在执行途中，而执行可能正发生在遍历里**。假设 trigger 直接边遍历 dep 边执行副作用：第一个副作用一进来先清账，会把自己、也可能把还没轮到的同伴从 Set 里删掉。Set 的迭代语义是删除尚未访问的元素等于跳过，本该执行的订阅者就这么无声丢失。所以仓库的 trigger 拆成两段：先把命中的副作用收进一个数组，再统一执行。ref/computed 复用的 `triggerEffects` 更直接，遍历的就是一份 `[...dep]` 拷贝；这段收尾的完整代码，1.3 节贴。

账不会过期了。但「每轮全清重收」立刻撞上下一种谎言：副作用执行到一半，另一个副作用进来插了一脚，`activeEffect` 该听谁的？

## 1.2 嵌套副作用与 effect 栈

嵌套不是刻意构造的边角。组件树就是天然场景：父组件的渲染副作用执行到「挂载子组件」那一步，子组件的渲染副作用就在父的执行途中被创建并立即运行。还有更早遇到的：在副作用里读一个 computed，computed 内部的计算 effect 也要当场 run，那是第 3 章的主角。先用手写版把问题造出来，`effect`/`track`/`trigger` 全部沿用 1.1 的朴素版：

```js
const obj = reactive({ bar: 1, foo: 2 })
let outerRuns = 0

effect(function outer() {
  outerRuns++
  effect(function inner() {   // 内层：创建后立即执行，读 obj.foo
    void obj.foo
  })
  void obj.bar                // 外层的读取，发生在内层之后
})
```

逐步跟踪指针。外层 `effect` 把 `activeEffect` 指向 outer，开始执行。执行到一半创建内层 effect：指针被改指 inner，inner 跑完，指针置空。回到 outer 的最后一行，`obj.bar` 的读取发生在指针已置空之后，`track` 一看没有活跃副作用，直接返回。把这段话展开成一张逐步推演表，每一行的 `activeEffect` 值都列出来：

| 步 | 动作 | activeEffect | 此步的读取登记到谁名下 |
|---|---|---|---|
| 1 | `effect(outer)` 启动：指针指向 outer，outer 开始执行 | outer | — |
| 2 | outer 执行到 `effect(inner)` 这一行 | outer | — |
| 3 | 内层 effect 启动：指针改指 inner | inner | — |
| 4 | inner 读 `obj.foo` | inner | `foo` 的 dep 记下 inner，登记正确 |
| 5 | inner 跑完，朴素 effect 把指针置空 | null | — |
| 6 | outer 继续，读 `obj.bar` | null | `track` 见无活跃副作用，直接返回，订阅丢失 |
| 7 | outer 跑完，指针再次置空 | null | — |

问题全部出在第 5、6 步之间。内层退出时不知道「外面还有人在等」，把指针直接置空；外层紧随其后的读取就成了无主读取，登记被 `track` 的守卫挡在门外。单根指针在同一时刻只能记住一个正在执行的副作用，而嵌套发生的时刻，内外两个都在执行中。指针错位不是偶发失误，是单指针在这个场景下的必然结局。

```js
obj.bar = 99
console.log(outerRuns)   // 1 —— 外层没有重跑：bar 的账上无人登记
```

最麻烦的不是不跑，而是**静默**。没有报错，没有警告，订阅悄悄没建立。真实项目里这类丢失几乎无法从现象反推。

修法似乎是「内层跑完把指针还给外层」，可还给谁？内层并不知道谁在外面，那就把外层存起来。存一个变量够吗？三层嵌套时，外面站着两层。需要的其实是一个栈：进入时压栈、退出时出栈，指针永远指向栈顶，也就是正在执行的那一个。

仓库的实现就是这四个字：压栈、出栈。模块级的 `effectStack` 就是一个数组：

```ts
// packages/reactivity/src/effect.ts（注释为原文件自带）
/** effect 执行栈：嵌套 effect（effect 里再建 effect/访问计算属性）时外层入栈，内层完成后还原 */
const effectStack: ReactiveEffect[] = []
```

进出动作就写在 1.1 贴过的 `run()` 里。`effectStack.push(this)` 接管指针；`finally` 里 `effectStack.pop()` 出栈，再把指针还原为新的栈顶。关键的还原行只有一句：

```ts
activeEffect = effectStack[effectStack.length - 1]
```

为什么还原成「栈顶」而不是干脆置空？因为当前 run 结束时自己已经出栈，栈顶恰好是还在执行中的外层。等最外层也跑完，栈空了，这行表达式的结果是 `undefined`，指针随之置空。一个表达式覆盖了嵌套与顶层两种情况。放进 `finally` 还有一层用意：副作用哪怕中途抛异常，出栈与还原也一定发生。

用仓库实现重跑开头的嵌套例子，行为就对了。有个细节值得盯住：

```js
const obj = reactive({ bar: 1, foo: 2 })
const log = []
effect(() => {
  effect(() => { log.push(obj.foo) })   // 内层：只依赖 foo
  void obj.bar                          // 外层：依赖 bar（在内层之后才读）
})

obj.foo = 3    // 只有内层重跑
// log: [2, 3]
obj.bar = 9    // 外层重跑：清账 → fn 重新执行 → 又创建了一个新内层
// log: [2, 3, 3]
```

`foo` 变化只叫醒内层，说明内层的读取确实登记在它自己名下，这是栈的功劳。`bar` 变化叫醒外层，外层按 1.1 的规矩先清账再重跑，于是 fn 完整执行了一遍：包括重新创建一个内层，它读到当前的 `foo` 并登记。注意，上一轮创建的内层并没有被停掉，它仍订阅着 `foo`，这个演示里旧内层成了无人认领的订阅。真实组件树不会如此：父组件重渲染走的是组件实例复用（`updateComponent`，第 8 章），子组件的渲染副作用跟着实例走，不会每轮重建。至于副作用如何成批停掉，第 4 章的 effectScope 再收拾。

栈治好了指针错乱。还剩最后一种失控，也是三种谎言里最烈性的：副作用读写同一个属性，把自己点着了。

## 1.3 自触发与递归防护

先看只有一行的副作用：

```js
const counter = reactive({ num: 0 })

effect(() => {
  counter.num++
})
```

`counter.num++` 不是一次操作，是「读、加一、写」三步。读 `num` 时，副作用把自己登记进 `num` 的 dep。写 `num` 时，trigger 把这个 dep 里的订阅者逐个叫醒，第一个被叫醒的就是它自己。于是 run、读、写、trigger、run……在朴素版里实测，这行代码的归宿是调用栈溢出。

修法的直觉人人都有：**正在执行的副作用，别被自己触发**。仓库用两道防线实现这个直觉，各堵一种漏洞。

第一道防线在 trigger 的收集阶段。上一章欠下的收尾段，现在完整贴出：

```ts
// packages/reactivity/src/effect.ts —— trigger 收尾（节选，注释为原文件自带）
  // !!! 稳定遍历的关键：一个 effect 可能同时被多个 dep 命中（比如既订阅了 key 又订阅了
  // ITERATE_KEY）。先去重（保持 dep 存入顺序 = 稳定的执行顺序），再统一执行。
  const effects: ReactiveEffect[] = []
  for (const dep of deps) {
    if (dep && dep.size) {
      for (const effect of dep) {
        // 跳过「正在执行并且没开 allowRecurse」的那个 effect，防止自触发死循环
        if (effect !== activeEffect || effect.allowRecurse) {
          if (!effects.includes(effect)) {
            effects.push(effect)
          }
        }
      }
    }
  }

  for (const effect of effects) {
    if (effect.scheduler) {
      // 有调度器（computed / watch / 组件渲染）：交给它决定何时重算
      effect.scheduler()
    } else {
      // 普通副作用：同步立即重跑
      effect.run()
    }
  }
```

这段就是「收集 → 去重 → 执行」三步。收集时跳过 `activeEffect`，也就是此刻正在执行的那个，除非它显式声明了 `allowRecurse`。去重的理由注释写得明白：一次改动可能同时命中多个 dep，同一个副作用会被数到两次。

空说三步不如逐步推演。回到本节开头那个 `counter.num++` 的副作用，把它的首次执行与一次外部触发的重跑全过程铺开，盯住 `activeEffect`、`dep(num)` 和 `effects` 数组各自的变化：

| 步 | 动作 | activeEffect | dep(num) | effects |
|---|---|---|---|---|
| 1 | 创建即首次 `E.run()`：查栈通过，`cleanupEffect` 清旧账（首轮无旧账，空操作） | undefined | （尚未创建） | — |
| 2 | 压栈，指针接管，`fn()` 开始执行 | E | （尚未创建） | — |
| 3 | `num++` 先读：`track` 创建 dep 并登记 E | E | {} → {E} | — |
| 4 | `num++` 再写：set 拦截器**同步**调 `trigger`，进入收集段 | E | {E} | [] |
| 5 | 收集：E === activeEffect 且未开 allowRecurse，跳过 | E | {E} | [] |
| 6 | 执行段：数组为空，一次也不跑 | E | {E} | [] |
| 7 | `fn` 返回，`finally` 出栈还原 | undefined | {E} | [] |
| 8 | 外部赋值 `counter.num = 4`：trigger 再临，无人在执行，无人可跳 | undefined | {E} | [E] |
| 9 | 执行段调 `E.run()`：先清账（{E} → {}），fn 重跑，读到 4 登记新账、写 5 又自触发 | E | {} → {E} | [] |
| 10 | 第二轮自触发撞上第 5 步同款判断，再次被拦，停在稳定态 | undefined | {E} | [] |

第 3 步与第 4 步的先后是整个机制成立的前提：读在前、写在后，等写触发 trigger 时，自己早已在 dep 里了——所以收集段才需要那行跳过判断。第 8 步则展示跳过判断的另一面：外部赋值时 `activeEffect` 是 undefined，谁都不该跳过，E 顺利进入 `effects` 被同步重跑。整张表里没有「标志位复位」之类的额外状态，防护完全由「此刻谁在执行」这一个事实推出。

去重不是防御性的摆设，它有真实的命中场景。一个副作用同时订阅「某个 key」和「整个对象的迭代」，这在一处很常见：Map 的读取方。`m.get('a')` 登记进 `dep('a')`，`m.forEach` 登记进 `dep(ITERATE_KEY)`——迭代者订的是「整个集合」这个特殊键。而 Map 的 `set` 覆盖已有键时，trigger 恰好会同时命中这两个 dep（`effect.ts` 的 trigger 里 `TriggerOpTypes.SET` 分支：`if (isMap(target)) deps.push(depsMap.get(ITERATE_KEY))`）。实测：

```js
const m = reactive(new Map([['a', 1]]))
let runs = 0
effect(() => {
  runs++
  void m.get('a')        // 订阅一：登记进 dep('a')
  m.forEach(() => {})    // 订阅二：登记进 dep(ITERATE_KEY)
})

m.set('a', 2)            // SET：deps = [dep('a'), dep(ITERATE_KEY)]
console.log(runs)        // 2 —— 两个 dep 里都是同一个 effect，去重后只重跑一次
```

`runs` 从 1 到 2，而不是 1 到 3。若把那行 `effects.includes` 去掉，收集循环会把同一个 E 塞进数组两次，执行段就重跑两次——对外表现是回调翻倍。这段代码也兑现了 1.1 末尾的承诺：收集循环虽然在直接遍历 Set，但遍历期间没有任何副作用执行（`includes` 只是读取），Set 不会在半路被清账；等到执行段，遍历的已经是 `effects` 这个独立数组，run 里的清账再怎么动 dep 也伤不到它。「先收集、再执行」两段式因此同时解决了跳过、去重、稳定遍历三件事。

执行段只有一处值得停下：**scheduler 优先**。副作用若带调度器，trigger 只发通知、不亲自执行，何时跑由调度器决定。这一个分支是 computed、watch、组件批量渲染三家的共同地基，分别在下一章、第 4 章和第 8 章展开。

执行段还有一个不显眼但值得钉死的性质：**登记序即执行序**。收集循环先按 deps 的存入顺序、再按每个 Set 的插入顺序走访，`effects` 数组保住了这个顺序，执行循环从数组头跑到尾。两个订阅同一个属性、先后创建的副作用，重跑顺序与创建顺序一致：

```js
const obj = reactive({ n: 0 })
const order = []
effect(() => { order.push('E1'); void obj.n })
effect(() => { order.push('E2'); void obj.n })

order.length = 0
obj.n = 1
console.log(order)   // ['E1', 'E2'] —— 按登记顺序执行
```

顺序为什么重要？渲染场景里，父组件总是先于子组件创建，渲染副作用也就先登记；同一轮批量触发时按登记序执行，父组件的子树先更新，子组件随后的重渲染建立在父层已就位的结构上。第 8 章的调度队列会把「按 uid 排序」显式写进队列，根子就是这里的稳定执行序。

第一道防线为什么不够？它只认「此刻正在执行的那一个」。设想两个副作用互相咬：A 的执行改了 B 依赖的数据，B 的执行又改了 A 依赖的数据。trigger 收集 A 时，`activeEffect` 是 B，A 不等于 B，照收不误。于是 A 重跑完又触发 B，B 又触发 A，一棒接一棒永远停不下来。

第二道防线在 run 的入口，就是 1.1 贴过的那行 `if (!effectStack.includes(this))`。A 还在栈上：它最初那次 run 还没有返回，正等在 trigger 的执行链里。重入 `run()` 时发现自己已在执行中，直接跳过。间接递归的链条在这里被剪断。

两道防线合起来，`counter.num++` 的行为变成：

```js
const counter = reactive({ num: 0 })
let calls = 0
effect(() => { calls++; counter.num++ })
// num === 1, calls === 1：首次执行，途中的自触发被拦下

counter.num = 4
// num === 5, calls === 2：外部赋值触发一次，重跑途中的自触发再次被拦下
```

`allowRecurse` 打开的口子到底是什么样子，也实测一遍。给副作用装上「把执行推迟到微任务」的调度器，再让它执行途中改自己订阅的属性：

```js
const state = reactive({ n: 0 })
const runs = []
const runner = effect(
  () => {
    runs.push(state.n)
    if (state.n === 1) state.n = 2   // 执行途中改了自己订阅的属性
  },
  {
    allowRecurse: true,
    scheduler: () => Promise.resolve().then(() => runner()),
  },
)

state.n = 1
// 微任务尘埃落定后：runs 为 [0, 1, 2]
```

时序拆开看。`state.n = 1` 触发 scheduler，重跑被排进微任务；这次重跑读到 1、把它记进 `runs`，接着把 n 改成 2——自触发发生，此刻 `activeEffect` 正是它自己。因为开了 `allowRecurse`，收集段放行，scheduler 再次被调、再次推迟；等这次重跑出栈、微任务到点，第三轮执行读到 2。若把 `allowRecurse` 去掉、其余不动，`runs` 只到 `[0, 1]` 为止：执行途中的那次自触发被收集段整个丢掉，n 变成 2 这件事没人再响应。两道防线与 allowRecurse 的分工至此清晰：查栈拦截同步重入，allowRecurse 只放行「经调度器推迟」的合法自触发——推迟到执行时，自己早已出栈，查栈自然放行。

至于 `allowRecurse` 这个例外，普通副作用几乎不需要，但有两类消费者会打开它。组件的渲染副作用创建时带着 `allowRecurse: true`，写在 `packages/runtime-core/src/renderer.ts` 的 `setupRenderEffect` 里。watch 的回调 effect 也会打开，见 `packages/runtime-core/src/apiWatch.ts`。渲染为什么必须允许自触发，牵扯到调度队列的合并语义，第 8 章展开。

至此，三道保险全部装好，trigger 的收尾也一文不缺。回看账本：登记的每一行都来自刚刚发生的真实读取，通知的每一个函数都确实该跑。但「每轮清空重建」不是免费的。高频更新时，订阅关系被反复拆了又建，官方 3.5 在这里动了一次大手术，本章末尾的差距一节细说。下一章，我们在账本之上加盖两层最常用的积木：惰性求值的 computed，与装得下原始值的 ref。

## 本章小结

本章给账本装上三道保险。run 前全量清账、执行中重新收集，保证依赖集合永远等于当次真实访问，幽灵依赖无处藏身；反向索引 `effect.deps` 让清账只遍历自己的账，不必全表扫描。`effectStack` 压栈出栈、还原栈顶，嵌套副作用各自的读取登记到各自名下。trigger 收集时跳过 `activeEffect`、run 入口查栈，两道防线拦住直接与间接的自触发；执行段 scheduler 优先，把「何时跑」的决策权交给上层。至此 track/trigger 与副作用执行模型完整闭环。

## 与官方实现的差距

- **清理从「全拆重建」变「增量维护」**。官方 3.5 把 dep 从 Set 重构为「版本计数 + Link 双向链表」（`third_party/vue-core/packages/reactivity/src/dep.ts`）：run 之前 `prepareDeps` 只把该副作用名下所有 link 的版本号置 -1；执行中访问到的 link 把版本同步回 dep 当前值；run 之后 `cleanupDeps` 只摘除仍为 -1 的 link。语义与本章的「全清重收」等价，但依赖没变时既不删除也不重插，高频更新省下整笔拆除重建的开销。这正是本章方案的升级路径。
- **嵌套还原没有栈数组**。官方 `run()` 用局部变量存住 `prevEffect`，`finally` 里还原，语义与 effectStack 等价，少一个数组。
- **递归防线收敛为一处**。官方在 `notify()` 里统一设防（RUNNING 标记 + ALLOW_RECURSE），RUNNING 覆盖整个执行期，同步场景下一处就能拦住直接与间接递归；本仓库用 trigger 跳过与 run 查栈两道防线达到同样效果。去重也由 NOTIFIED 标记位替代本仓库的数组 `includes` 扫描，重复判断从 O(n) 降到 O(1)。

## 动手验证

```bash
pnpm test -- packages/reactivity
```

重点看三个用例（`packages/reactivity/__tests__/effect.spec.ts`）：`should remove old dependencies after branch switch`、`should avoid infinite loops when using effects on itself`、`should allow nested effects`。

本章新增的演示也都可以照抄成临时 spec 实测：1.1 的幽灵依赖对照（输出 `3 2` 与 `2 2`）、1.3 的 Map 去重（`runs` 从 1 到 2）、1.3 的 allowRecurse 时序（`runs` 为 `[0, 1, 2]`，去掉该选项则停在 `[0, 1]`）——预期值均经本仓库实际运行核对。

再给一个可亲手跑的对照实验。把 1.1 的朴素版抄进 Node，跑出空跑；再对照仓库版的输出：

```js
const state = reactive({ ok: true, a: 1, b: 2 })
let runs = 0, result = 0
effect(() => { runs++; result = state.ok ? state.a : state.b })

state.ok = false
state.a = 10
console.log(runs, result)
// 朴素版：3 2（幽灵依赖触发空跑）
// 仓库版：2 2（a 的 dep 已被清空，收集不到任何订阅者）
```

顺手验证 1.1 提到的语言细节：Set 迭代途中删除未访问的元素，它会被直接跳过——

```js
const s = new Set(['a', 'b', 'c', 'd'])
const visited = []
for (const x of s) {
  if (x === 'a') s.delete('c')   // c 尚未被访问
  visited.push(x)
}
console.log(visited)   // [ 'a', 'b', 'd' ] —— c 不见了
```
