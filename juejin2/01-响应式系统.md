# 01 · 响应式系统：依赖收集与副作用调度

> 本篇实现 `packages/reactivity`。前置阅读：00 篇的整体数据流。产出：一套完整的响应式系统——代理、依赖收集、副作用执行模型、调度器、computed、ref 与 effectScope，并说明与官方 3.5 实现的差异。

## 引言

官方文档「深入响应式系统」一页将 Vue 3 响应式的工作方式概括为：使用 Proxy 创建响应式对象，在 `get` 拦截器中调用 `track` 记录依赖，在 `set` 拦截器中调用 `trigger` 查找并执行该属性的所有订阅副作用；订阅关系保存在全局 `WeakMap<target, Map<key, Set<effect>>>` 结构中。其中副作用（effect）指会读写响应式状态的函数——组件的渲染函数就是这样一个副作用：文档明确表述为「每个组件实例创建一个响应式副作用来渲染和更新 DOM」。

这段描述就是本篇的实现规格。我们要解决四个子问题：

1. 订阅关系的数据结构与读写协议（track/trigger）；
2. 副作用的执行模型——依赖清理、嵌套、递归；
3. 副作用执行时机的可配置性（scheduler，批处理的基础）；
4. 在此之上组合出 computed、ref、effectScope 三个上层 API。

## 一、依赖的存储：targetMap

依赖收集（dependency tracking）需要一个「谁订阅了哪个属性的哪个值」的登记结构。Vue 采用两层映射：

```ts
// packages/reactivity/src/effect.ts
const targetMap: WeakMap<any, Map<any, Dep>> = new WeakMap()   // Dep 即 Set<ReactiveEffect>
```

外层以原始对象为键，值是「属性名 → dep」的内层 Map；dep 是一个 `Set<ReactiveEffect>`，即该属性的全部订阅者（subscriber）。外层选用 WeakMap 是内存语义的要求：登记结构不应延长键的生命周期，原始对象在外部失去引用后，其名下的整条依赖记录应随之可回收；内层则无此顾虑，普通 Map 即可。

## 二、track：读取即订阅

属性被读取时，若当前存在正在执行的副作用，就把它登记进对应 dep：

```ts
// packages/reactivity/src/effect.ts
export function track(target: object, type: TrackOpTypes, key: unknown) {
  if (!shouldTrack || !activeEffect) {
    return                                    // 无正在执行的副作用：裸读不产生订阅
  }
  let depsMap = targetMap.get(target)
  if (!depsMap) {
    targetMap.set(target, (depsMap = new Map()))
  }
  let dep = depsMap.get(key)
  if (!dep) {
    depsMap.set(key, (dep = createDep()))
  }
  trackEffects(dep)                           // dep.add(activeEffect) + effect.deps.push(dep)
}
```

`activeEffect` 是指向当前正在执行的副作用的模块级指针，`shouldTrack` 是收集总开关。两者同时就绪才建立订阅——这解释了一个容易困惑的现象：在事件回调或 `setTimeout` 中读取 `reactive` 对象的属性并不建立任何依赖，因为此时没有「正在执行的副作用」上下文。此外 `trackEffects` 同时把 dep 记入 `effect.deps`，形成反向索引，供后续清理使用（第四节）。

## 三、trigger：写入即通知，以及隐式联动

属性被写入时，按变更类型收集应通知的 dep 并执行其中的副作用。完整规则比「通知本属性」要宽，因为 JavaScript 的对象语义存在**隐式联动**：

```ts
// packages/reactivity/src/effect.ts
export function trigger(target, type, key, newValue, oldValue, oldTarget) {
  const depsMap = targetMap.get(target)
  if (!depsMap) return
  let deps: (Dep | undefined)[] = []
  if (type === TriggerOpTypes.CLEAR) {
    deps = [...depsMap.values()]               // 集合清空：所有属性的订阅者全部命中
  } else if (key === 'length' && isArray(target)) {
    const newLength = Number(newValue)
    depsMap.forEach((dep, key) => {
      if (key === 'length' || key === ARRAY_ITERATE_KEY ||
          (!isSymbol(key) && key >= newLength)) {
        deps.push(dep)                         // length 调短：越界下标全部失效
      }
    })
  } else {
    if (key !== void 0) deps.push(depsMap.get(key))   // 先命中被修改的属性
    switch (type) {
      case TriggerOpTypes.ADD:
        if (!isArray(target)) deps.push(depsMap.get(ITERATE_KEY))
        else if (isIntegerKey(key)) deps.push(depsMap.get('length'))
        break
      case TriggerOpTypes.SET:
        if (isMap(target)) deps.push(depsMap.get(ITERATE_KEY))
        break
    }
  }
  const effects: ReactiveEffect[] = []
  for (const dep of deps) {                    // 去重：一个副作用可能被多个 dep 同时命中
    if (dep && dep.size) for (const effect of dep) {
      if (effect !== activeEffect || effect.allowRecurse) {
        if (!effects.includes(effect)) effects.push(effect)
      }
    }
  }
  for (const effect of effects) {
    effect.scheduler ? effect.scheduler() : effect.run()
  }
}
```

四类隐式联动值得逐一说明：

- **CLEAR**：`Map.clear()` 使所有键失效，订阅任何一个键的副作用都应被通知；
- **length 调短**：数组截断使所有下标大于等于新长度的元素被删除，这些下标的订阅者都应被通知；
- **ADD + 数组整数键**：`arr[5] = x` 会隐式增大 `length`，订阅 `length` 的副作用（例如依赖数组长度的渲染）必须被通知——这是一个典型易错点，测试之外很难从现象反推；
- **ADD/SET + 迭代键**：对象新增键影响 `for...in`，`Map` 的 `set` 即使值未变也影响迭代结果，因此迭代（`ITERATE_KEY`）的订阅者需要额外联动。

收集阶段还有两处防御：同一副作用可能被多个 dep 命中，需要去重；正在执行的副作用默认跳过自身，防止 `count.value++` 这类「读写同一状态」的写法无限递归，除非显式声明 `allowRecurse`。

## 四、副作用的执行模型

`effect(fn)` 首次调用即执行 `fn`，此后 `fn` 的依赖变化时被重新执行。执行模型要处理三个问题：依赖清理、嵌套、递归。

### 4.1 依赖清理与分支切换

考虑一个包含条件分支的副作用：

```ts
effect(() => {
  result = state.ok ? state.a : state.b
})
```

`ok` 为 true 时订阅 `{ ok, a }`；当 `ok` 翻转为 false，重新执行后只访问 `b`。若依赖集合仍保留对 `a` 的订阅，此后修改 `a` 会触发一次空跑——这类残留订阅不仅浪费，还会导致「修改了与当前分支无关的状态、界面却发生变化」的错误。解法是在每次重新执行前**全量清空**旧订阅，执行过程中重新收集：

```ts
// packages/reactivity/src/effect.ts
class ReactiveEffect<T = any> {
  deps: Dep[] = []        // 反向索引：本副作用订阅过的全部 dep
  active = true

  run(): T | undefined {
    if (!this.active) {
      return this.fn()    // 已停止：朴素执行，不收集依赖
    }
    if (!effectStack.includes(this)) {      // 递归保护
      cleanupEffect(this)                   // 关键：重新执行前清空旧订阅
      try {
        enableTracking()
        effectStack.push(this)
        activeEffect = this
        return this.fn()
      } finally {
        effectStack.pop()
        resetTracking()
        activeEffect = effectStack[effectStack.length - 1]   // 还原外层副作用
      }
    }
  }
}

function cleanupEffect(effect: ReactiveEffect) {
  const { deps } = effect
  if (deps.length) {
    for (let i = 0; i < deps.length; i++) deps[i].delete(effect)
    deps.length = 0
  }
}
```

选择「全量清空、重新收集」而非「精确删除不再访问的那一条」，是基于正确性的考虑：副作用体内可以有任何控制流，静态判断「哪些依赖仍然被需要」不可靠；让每轮依赖集合都从当次执行中重新生成，则结构上保证了集合与实际访问一致。代价是清空与重建的固定开销，官方 3.5 的重构（见第九节）正是针对这笔开销。

### 4.2 嵌套与 activeEffect 还原

副作用可以嵌套——组件树就是天然场景：父组件渲染函数执行中创建子组件，子组件的渲染副作用在父的执行栈内运行。单个全局指针无法表达多层上下文，因此用 `effectStack` 维护执行栈：进入时压栈并接管 `activeEffect`，`finally` 中出栈并把 `activeEffect` 还原为栈顶（即外层副作用）。若内层执行后直接清空指针，外层后续代码中的属性读取将全部收集失败，且这种丢失是静默的。

## 五、执行时机：调度器

trigger 的最后一行给出了一个重要约定：

```ts
effect.scheduler ? effect.scheduler() : effect.run()
```

副作用可以携带 `scheduler` 选项：不提供时，依赖变化直接重新执行 `fn`；提供时，依赖变化转交 `scheduler` 处置。这一个分支是三处上层机制的共同基础：

- **组件更新的批处理**：渲染副作用的 scheduler 把更新任务入队，由调度队列在微任务中合并执行（02 篇实现）；
- **computed 的脏位**：内部副作用的 scheduler 不重算，只标记失效（第六节）；
- **watch 的时序控制**：`flush: 'pre' | 'post' | 'sync'` 三种时机（官方文档默认 `'pre'`）在 scheduler 层面区分。

## 六、computed：惰性求值与脏位

computed 在依赖收集之上实现「按需、缓存」的派生值。它具有三重身份：对外是一个 ref（暴露 `.value`）；内部持有一个订阅副作用（getter 在其中收集源依赖）；自身又携带一个 dep（登记读取它的下游副作用）。

```ts
// packages/reactivity/src/computed.ts
export class ComputedRefImpl<T = any> {
  _dirty = true
  dep?: Dep

  constructor(getter, private readonly setter, isReadonly) {
    this.effect = new ReactiveEffect(getter, () => {       // scheduler：源依赖变化时
      if (!this._dirty) {
        this._dirty = true                                  // 只置脏位，不重算
        triggerRefValue(this)                               // 通知下游“值已失效”
      }
    })
  }

  get value(): T {
    const self = toRaw(this) as ComputedRefImpl<T>
    trackRefValue(self)          // 读取者登记为下游订阅者
    if (self._dirty) {           // 脏位（dirty flag）：脏才重算，算后缓存
      self._dirty = false
      self._value = self.effect.run()!
    }
    return self._value
  }
}
```

两个设计点分别对应「惰性」与「失效」：

- **惰性求值**：构造时不执行 getter，首次读取 `.value` 才求值并缓存于 `_value`；此后读取直接返回缓存。十个订阅者共享一次计算。
- **失效传播**：源依赖变化时，scheduler 仅将 `_dirty` 置回 true 并通知下游，不做计算。真正的重算推迟到下一次有人读取。于是「无人读取则永不重算」。

官方文档将 computed 的可写形式描述为「传入带 get/set 函数的对象」，实现上即上述类挂载 `set value` 转调 setter，此处从略。

## 七、ref：原始值的响应式容器

Proxy 只能代理对象，原始值（number、string 等）无法进入代理体系。ref 的方案是把原始值包进容器对象，将读写收敛到 `.value` 属性的 getter/setter 上——官方文档的表述是「在 Vue 3 中使用 Proxy 创建响应式对象，仅将 getter/setter 用于 ref」。

```ts
// packages/reactivity/src/ref.ts
class RefImpl<T = any> {
  _value: T
  private _rawValue: T
  dep?: Dep

  constructor(value, private readonly shallow) {
    this._rawValue = shallow ? value : toRaw(value)     // 保存原始值，用于判等
    this._value = shallow ? value : toReactive(value)   // 对象值转为深层代理
  }

  get value() {
    trackRefValue(this)
    return this._value
  }
  set value(newVal) {
    const useDirectValue = this.shallow || isShallow(newVal) || isReadonly(newVal)
    newVal = useDirectValue ? newVal : toRaw(newVal)
    if (hasChanged(newVal, this._rawValue)) {   // 值确实变化才触发
      this._rawValue = newVal
      this._value = useDirectValue ? newVal : toReactive(newVal)
      triggerRefValue(this, newVal)
    }
  }
}
```

三处细节对应文档语义与一个易错点：

- **深层转换**：对象赋给 ref 时经 `toReactive` 转为 `reactive()` 代理——文档明确「如果将一个对象赋值给 ref，那么这个对象将通过 reactive() 转为具有深层次响应式的对象」；避免深层转换则使用 `shallowRef`。
- **判等用原始值**：`_rawValue` 保存 `toRaw` 后的原始对象，否则「代理对象与解包后的同源对象」会被 `Object.is` 判为不等，造成误触发。
- **相同值不触发**：`hasChanged` 判断通过后才走 `triggerRefValue`，赋相同值是空操作。

模板中无需书写 `.value`，由两处机制完成自动解包：编译器对顶层 ref 生成解包访问；setup 返回值经 `proxyRefs` 浅解包代理。两者最终都落在 `trackRefValue` / `triggerRefValue` 这对入口上，与 effect 共用同一套协议。

## 八、effectScope：副作用的生命周期管理

组件卸载时，其渲染副作用、setup 中创建的 watch 与 computed 都需要停止；状态管理库更甚——一个 store 可能创建数十个副作用，遗漏停止会留下失去监听者的订阅，状态变化时静默执行无用逻辑。effectScope（作用域）把「一批副作用的生命周期」捆绑为整体：

```ts
// packages/reactivity/src/effectScope.ts
export let activeEffectScope: EffectScope | undefined

export class EffectScope {
  effects: ReactiveEffect[] = []      // 本作用域直接创建的副作用
  cleanups: (() => void)[] = []       // onScopeDispose 登记的清理回调
  parent: EffectScope | undefined
  scopes: EffectScope[] | undefined

  constructor(public detached = false) {
    if (!detached && activeEffectScope) {      // 处于某作用域内：登记为子作用域
      if (activeEffectScope.active) {
        this.parent = activeEffectScope
        this.index = (activeEffectScope.scopes ||
          (activeEffectScope.scopes = [])).push(this) - 1
      } else {
        this._active = false                   // 父已停止：子作用域创建即失活
      }
    }
  }

  run<T>(fn: () => T): T | undefined {
    if (this._active) {
      const currentScope = activeEffectScope
      try {
        activeEffectScope = this               // run 期间创建的副作用
        return fn()                            // 由构造器自动登记进本作用域
      } finally {
        activeEffectScope = currentScope
      }
    }
  }
}
```

机制与第四节的 effect 执行栈同构：`run` 执行期间接管模块级指针 `activeEffectScope`，期间创建的 `ReactiveEffect` 在构造器中被自动收编。`stop()` 递归停止子树、执行 `onScopeDispose` 回调。两个消费者说明了它的定位：状态库（如 Pinia）在顶层创建 detached 作用域承载全部 store 的副作用，销毁时一次收割；组件实例本身就是一个作用域，因此 `onScopeDispose` 与组件的 `onUnmounted` 在时机上互为对偶。

## 九、与官方实现的差异

上述实现保持 Set + 脏位的最简形态，官方 3.4/3.5 对内部结构做过两轮重构，语义不变、数据结构不同：

- **3.5**：dep 由 `Set` 改为「版本计数 + 双向链表」，依赖清理从「全量清空重建」变为按版本增量维护，降低高频更新的开销；
- **3.4**：computed 重构为版本对比——源变化后重算，若新值与旧值 `Object.is` 相等，则不再向下游传播触发，避免下游空跑。

本工程的 `collectionHandlers`（Map/Set 的代理转发）与 `markRaw`、`shallowReactive` 等边角 API 与官方语义对齐，篇幅所限不在正文展开，实现见 `packages/reactivity/src/collectionHandlers.ts`。

## 小结

响应式系统由一张两层登记表（targetMap）与两个入口（track/trigger）构成核心：读取时在 `activeEffect` 上下文中登记订阅，写入时按变更类型——包括四类隐式联动——收集并通知订阅者。副作用的执行模型以「每轮全量清理、重新收集」保证依赖集合与实际访问一致，以执行栈支持嵌套；scheduler 选项把「是否执行、何时执行」的决策权上交调用方，是组件批处理与 computed 失效传播的共同基础。computed 用脏位实现惰性缓存，ref 用容器把 Proxy 无法覆盖的原始值纳入同一协议，effectScope 把副作用生命周期成组管理。
