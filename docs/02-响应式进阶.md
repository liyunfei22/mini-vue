## 1. 这一阶段学到了什么（四大块）

### 1.1 effectScope —— 批量收编 + 批量拆毁
```
effectScope()           创建一个作用域容器（默认挂在当前父 scope 下）
scope.run(fn)           执行期间 activeEffectScope = scope → 里面 new 的 effect 自动登记
onScopeDispose(fn)      在 run 期间注册清理回调
scope.stop()            ① 逐个 stop 收编的 effect ② 执行 cleanups ③ 递归停子 scope ④ 从父摘掉自己
```
- `detached=true` → 不挂父目录（pinia 创建顶层 scope 用）；
- **先把整个 destroy 协议跑通的意义**：阶段 3 组件实例就是「一个非 detached scope + onUnmounted hooks」；阶段 8 pinia 在顶层 scope 里养全部 store。

### 1.2 collectionHandlers —— Map/Set 为什么不走 baseHandlers
- **内部槽**：`Map.prototype.set` 读取 `this` 的私有 `[[MapData]]`，把 Proxy 当 `this` 调用必然抛错；
- **方案**：get trap 把方法访问**改道**到 `instrumentations`（换过血的方法表），用 `this = 代理` 再调用；
- 两个新锚点 key：`ITERATE_KEY`（size/forEach/迭代）与 `MAP_KEY_ITERATE_KEY`（Map.keys 只看键集）；
- 迭代器包一层外壳：每个 `next()` 吐出的值都 `wrap` 成响应式形态。

### 1.3 shallow / markRaw —— 选择性关闭深度响应式
- `shallowRef`/`shallowReactive`：一层可控，内部保持原样（存谁就是谁）；
- `triggerRef`：手动强制通知（改 deep 内容后的补偿开关）；
- `markRaw`（阶段 1 已就位）：打 SKIP 标，永不复代理 —— **与 collection 配合可做 pinia 的 store 防代理**。

### 1.4 customRef / proxyRefs —— 定制与解包
- `customRef(factory)`：把「track/trigger」两把钥匙交给用户自己的 get/set；
- `proxyRefs(obj)`：setup 返回的「全是 ref 的对象」浅解包成裸值视图（`s.count` 而非 `s.count.value`）。

## 2. review gate 参考答案

### Q1：onScopeDispose 在什么时候、以什么顺序执行？
在 `scope.stop()` 时执行；顺序 = **注册顺序**（cleanups 数组按 push 顺序遍历，先注册先执行）。与之对照的是我 stage1 文档里写“后注册先释放”——那不对，真 Vue 就是 push 顺序 = FIFO。组件 unmount 时销毁子树同理（子组件先 unmount 再父组件）。⚠️ 勘误：`docs/01` 里我提过“逆序”，实测源码为顺序，以此为准（`effectScope.ts` 的 stop 循环 `scopes[i].stop()` 先于自身 cleanups）。

### Q2：markRaw 在 pinia 里具体防什么？
pinia 的 store 是 `reactive()` 出来的对象；若把它再放进另一个 reactive 上下文（如 `reactive({ store })` 或作为顶层 state 的深层成员），会被二次代理：**了两个 store 的 `.id`/`$patch` 等属性会变成 proxy 包装**，且“store 的引用身份”不稳定（`getStoreById` 比较失败、插槽判断错乱）。`markRaw(store)` 保证：谁放进 reactive 里都拿不到代理包装，store 永远是它自己。

### Q3：router 的 currentRoute 为什么必须用 shallowRef？
`currentRoute.value` 存的是 route 对象 `{ path, params, matched: [...] , meta, ... }`。若用普通 `ref()`，它会 `toReactive` 深代理整个 route：任何 effect 一旦读了 route 的某个深层属性（如 `route.params.id`），就在整棵树里建立了依赖链 —— 而路由巨头对象的每次导航都会整体替换，深代理除了平白增加包装成本和 `toRaw/身份比较` 的判断开销外毫无收益。`shallowRef` 让 **“换对象(=跳路由)才通知”** 成为语义本身：路由导航的本质就是替换整个 route 对象。
