# 05 · 构建与发布：多格式产物、__DEV__ 与类型声明捆包

> 本篇是系列第五篇，也是收官篇。前置阅读：04 篇的内核补全。产出：一条把七个 TypeScript 源码包变成可消费产物的构建流水线——构建编排、多格式产物命名、`__DEV__` 注入机制、跨包解析与类型声明捆包，最后完成整个系列的链路回顾。

## 引言

前四篇结束时，仓库里是七个包约 8500 行 TypeScript 源码与配套的行为测试。但源码形态只有开发环境可消费：库的最终形态由构建流水线决定。库（library）与业务代码的根本差异在于消费者不可枚举，至少有四类：**打包器（bundler）**——Vite、Webpack 构建链下的业务项目，期望 ES Module 导入；**Node CommonJS 项目**——服务端脚本、旧工具链，用 `require()` 导入；**无构建环境**——`<script>` 直引、在线演示页面，期望挂到全局变量上的单文件；以及 **TypeScript 用户**——不执行任何产物，只消费类型声明（type declarations），即描述模块公开 API 的 `.d.ts` 文件。

官方 `vue` 包的 dist 目录正是按这个格局组织的：`vue.esm-bundler.js`（给打包器）、`vue.cjs.js`（给 Node）、`vue.global.js`（给 script 直引）各司其职。本工程以 `@mini-vue` 为前缀镜像同一格局。本篇解决五个子问题：构建如何编排（第一节）、产物格式如何命名与生成（第二节）、开发态开关 `__DEV__` 如何注入（第三节）、跨包引用如何在构建期解析（第四节）、类型声明如何捆成单文件（第五节）。全部配置经实际构建验证，与仓库当前代码一致。

## 一、构建编排：一份共享配置，逐包注入身份

七个包共享一份 rollup 配置，构建时以「包名」为身份参数逐包执行。编排由 `scripts/build.js` 承担，第一步是收集目标包：

```js
// scripts/build.js（节选，完整实现见仓库）
const PACKAGES_DIR = new URL('../packages/', import.meta.url).pathname
const args = process.argv.slice(2)
const targetArgs = args.filter((a) => !a.startsWith('--'))
const prodOnly = args.includes('--prod')
const NODE_ENV = prodOnly ? 'production' : 'development'
const withTypes = args.includes('--with-types')
const all = args.includes('--all') || targetArgs.length === 0

const targets = readdirSync(PACKAGES_DIR)
  .filter((dir) => {
    try {
      readFileSync(`${PACKAGES_DIR}${dir}/package.json`, 'utf-8')
      return true
    } catch {
      return false
    }
  })
  .filter((t) => all || targetArgs.some((a) => a.startsWith(t)))
```

这段代码区分了两类命令行输入：位置参数按子串匹配包名（`node scripts/build.js dom` 会命中 compiler-dom 与 runtime-dom），`--` 前缀的是模式开关（`--prod`、`--with-types`、`--all`）。包的发现以 `package.json` 存在性为准，`packages/` 之外的内容天然不参与构建。

主循环逐包驱动 rollup，并在每次调用前重建该包的 dist 目录：

```js
// scripts/build.js（节选）
async function main() {
  const started = Date.now()
  for (const t of targets) {
    const distDir = `${PACKAGES_DIR}${t}/dist`
    rmSync(distDir, { recursive: true, force: true })
    mkdirSync(distDir, { recursive: true })
    console.log(`\n[build] ${t} (${NODE_ENV})`)
    await run('npx', ['rollup', '-c', '--environment', `TARGET:${t},NODE_ENV:${NODE_ENV}`])
  }
  if (withTypes) {
    console.log('\n[build:types] 生成声明文件…')
    await run('npx', ['tsc', '-p', 'tsconfig.build.json'])
    for (const t of targets) {
      // rollup 的 --environment 用逗号切 KV，多值会丢，所以逐包传 TARGET
      await run('npx', ['rollup', '-c', 'rollup.dts.config.js', '--environment', `TARGET:${t}`])
    }
  }
}
```

三处设计值得注意。其一，`rmSync` 先删后建，保证 dist 内不混入上一次构建的陈旧文件——同一 dist 目录在 dev 与 prod 模式间切换时尤其重要。其二，调用 rollup 采用 spawn 子进程而非编程 API，参数经 `--environment TARGET:<包>,NODE_ENV:<模式>` 注入，配置文件从 `process.env` 读取这两个变量，与手动在命令行执行的行为一致。其三，`--with-types` 分两步：先跑一次全量 `tsc` 产出声明碎片，再逐包用第二份 rollup 配置捆包（第五节）。根 `package.json` 的 scripts 对此做了收敛：`pnpm build` 即 `node scripts/build.js --with-types`，`pnpm build:prod` 加 `--prod` 切换生产模式。

## 二、多格式产物与命名：从格式名到文件名

rollup 原生支持的产物格式（format，即输出模块的语法类别）有 `es`、`cjs`、`iife` 等，但对外的「格式名」是语义层命名。本工程使用三个格式名，与官方包对齐：**esm-bundler** 是给打包器消费的 ESM，区别于浏览器直用的原生 ESM 之处在于构建期常量的处置——bundler 场景下 `process.env.NODE_ENV` 这类判断可以留给业务侧构建替换（第三节展开）；**cjs** 是给 Node `require()` 的 CommonJS；**global** 是立即调用函数表达式（IIFE）单文件，执行后把导出挂到全局变量上，是唯一无需构建工具的形态。

格式名到文件名的翻译集中在一个函数里：

```js
// rollup.config.js（节选）
const outputName = (f) => {
  const prod = isProd ? '.prod' : ''
  if (f === 'esm-bundler') return `packages/${TARGET}/dist/${pkg.name.replace('@mini-vue/', '')}.esm-bundler${prod}.js`
  if (f === 'cjs') return `packages/${TARGET}/dist/${TARGET}${prod}.cjs`
  if (f === 'global') return `packages/${TARGET}/dist/${TARGET}.global${prod}.js`
}
const outputFormat = { 'esm-bundler': 'es', cjs: 'cjs', global: 'iife' }
```

命名规则有三点。第一，esm-bundler 用包名去掉 scope 前缀（`@mini-vue/shared` → `shared.esm-bundler.js`），与官方 `vue.esm-bundler.js` 的命名一致。第二，cjs 产物用 `.cjs` 扩展名而非 `.js`——这不是风格偏好，而是 Node 解析规则的要求（第六节陷阱一）。第三，prod 模式在中缀插入 `.prod`（`shared.prod.cjs`），dev 与 prod 文件可并存对照。

配置主体按 formats 展开，每个格式一份完整输出：

```js
// rollup.config.js（节选）
const formats = (
  process.env.FORMATS ? process.env.FORMATS.split(',') : buildOptions.formats || ['esm-bundler', 'cjs']
)
const name = buildOptions.name || 'MiniVue'

export default formats.map((f) => ({
  input: `packages/${TARGET}/src/index.ts`,
  output: {
    file: outputName(f),
    format: outputFormat[f],
    exports: 'named',
    name: f === 'global' ? name : undefined,
    banner: `/* mini-vue ${TARGET} v${pkg.version} (${NODE_ENV}) */`,
  },
  plugins: [
    nodeResolve({ exportConditions: ['source'], extensions: ['.ts', '.js'] }),
    esbuild({
      define,
      target: 'es2018',
      minify: isProd,
      treeShaking: true,
    }),
  ],
  onwarn(w, warn) {
    if (w.code && (w.code.startsWith('CIRCULAR') || w.code === 'UNRESOLVED_IMPORT')) return
    warn(w)
  },
}))
```

逐点分析。`formats` 来自各包 `package.json` 的 `buildOptions.formats`：shared 等六个包只有 `['esm-bundler', 'cjs']` 两格式——它们不会脱离打包链路被 script 直引；`vue` 包三格式齐全，因为只有聚合入口面向无构建环境。`exports: 'named'` 让 cjs 与 iife 产物以具名属性导出（`require('...').createApp`），避免默认导出的歧义。`name: 'MiniVue'` 仅对 global 格式生效——IIFE 需要全局变量名承接导出，该值写在 `vue` 包的 `buildOptions.name` 里。esbuild 插件承担转译（TS → es2018）、压缩（minification，即删除空白注释、缩短标识符以减小体积的改写，仅 prod 开启）与树摇；`FORMATS` 环境变量可临时收窄格式，便于调试单个产物。`onwarn` 过滤两类噪声告警：monorepo 内跨包的循环引用（CIRCULAR）与外部依赖的未解析引入（UNRESOLVED_IMPORT）。

## 三、__DEV__：一个构建期开关的真实机制

库源码里散布着「仅开发态需要」的告警与校验，官方实现用 `__DEV__` 常量守护它们。本工程的源码态写法是：

```ts
// packages/shared/src/index.ts（节选）
export const __DEV__ = true

export const EMPTY_OBJ: { readonly [key: string]: any } = __DEV__ ? Object.freeze({}) : {}
export const EMPTY_ARR: readonly any[] = __DEV__ ? Object.freeze([]) : []
```

源码里写死为 `true` 的动机是独立可运行：`tsc` 类型检查与 `vitest` 直接跑源码，无需任何变量注入。runtime-core 另有五个文件（`warning.ts`、`apiCreateApp.ts` 等）各自声明了同名的本地 `__DEV__`，reactivity 等包则经 `import { __DEV__ } from '@mini-vue/shared'` 跨包引用。无论哪种形态，它们都是模块内的具名绑定（named binding）。

构建端准备了与之配套的注入配置：

```js
// rollup.config.js（节选）
const define = {
  __DEV__: isProd ? 'false' : 'true',
  'process.env.NODE_ENV': JSON.stringify(NODE_ENV),
}
```

按预期，esbuild 的 define 会把源码中 `__DEV__` 表达式替换为字面量，prod 产物里告警分支随之消失。实测结果并非如此。对比同一行源码在两份产物中的形态：

```js
// packages/shared/dist/shared.esm-bundler.js（dev，节选）
const __DEV__ = true;
const EMPTY_OBJ = Object.freeze({}) ;

// packages/shared/dist/shared.esm-bundler.prod.js（--prod，节选，压缩改写）
...,M as __DEV__,...                          // 导出表：仍以 __DEV__ 之名导出
M=!0,...                                      // 定义处：压缩为 M，值 !0 即 true
z=Object.freeze({}),w=Object.freeze([]),...   // EMPTY_OBJ / EMPTY_ARR 在 prod 仍被冻结
```

prod 产物中 `__DEV__` 的值仍是 true（压缩把 `true` 改写为 `!0`），`Object.freeze` 照常执行，`__DEV__` 作为字符串只在导出表出现一次（导出名不可改写）。结论：**define 没有生效，当前 dev 与 prod 产物的语义差异实际只来自压缩**。根因在 esbuild define 的替换规则：define 只替换自由标识符（free identifier，即未被任何局部作用域声明的名字），并且是名称解析之后的替换。模块顶层的 `export const __DEV__ = true` 是一个模块级绑定，它遮蔽（shadow）了同名的全局名字；若 esbuild 无视绑定直接按词面替换，任何碰巧叫这个名字的局部变量都会被误伤。这个保守设计在一般场景是正确的，却使「源码里声明过 `__DEV__`」的写法与 define 天然互斥。

官方实现正是绕开了这一点，vuejs/core 的做法分三层：其一，`packages/global.d.ts` 中只写 `declare var __DEV__: boolean`——环境声明（ambient declaration，只向类型系统注册名字、不产生任何运行时绑定），源码里因此不存在 `__DEV__` 的值声明，它在模块里始终是自由标识符；其二，esm-bundler 格式下把 `__DEV__` 替换为表达式 `!!(process.env.NODE_ENV !== 'production')`，把 dev/prod 的决策权移交给消费端的打包器；其三，浏览器直用格式（global / esm-browser）没有转交机会，直接硬编码为 `String(!isProductionBuild)`，因此官方 dist 里 `vue.global.js` 与 `vue.global.prod.js` 成对存在。

本工程保持源码常量写法，代价是告警分支与冻结逻辑保留在 prod 产物中。这是一个已知取舍：换来的是源码零注入即可测试，代价的消除路径也很明确——改为环境声明、走官方的构建期替换。梳理清楚「具名绑定遮蔽自由标识符」这一层后，切换方案只是机械工作。

## 四、跨包解析：source 条件解开构建顺序依赖

`vue` 包聚合五个兄弟包（runtime-dom、runtime-core、compiler-dom、compiler-core、shared）。构建 `vue` 时，rollup 遇到 `import ... from '@mini-vue/runtime-dom'`，解析目标有两个候选：兄弟包的 `dist` 产物，或它的 `src/index.ts` 源码。若解析到 dist，构建顺序就成为硬约束——必须先建好五个依赖包，而它们又依赖 shared，任何单包构建都不可行。

解法在每个包的 `exports` 字段里。导出条件（export conditions）是 `package.json` `exports` 中按消费环境逐层匹配的字段，解析方从上到下取第一个命中的分支：

```json
// packages/vue/package.json（exports 字段）
{
  "exports": {
    ".": {
      "types": {
        "source": "./src/index.ts",
        "default": "./dist/vue.d.ts"
      },
      "source": "./src/index.ts",
      "import": "./dist/vue.esm-bundler.js",
      "default": "./dist/vue.cjs"
    }
  }
}
```

四个条件分层各有所指。`types`（带嵌套子条件）服务 TypeScript：支持 source 时连类型都指向源码，否则回落 `dist/vue.d.ts`。`source` 指向源码入口。`import` 命中 ESM 场景的打包产物，`default` 兜底 CommonJS 与旧解析器。`main` / `module` / `types` 旧字段仍保留在不感知 `exports` 的工具链里作兜底；`sideEffects: false` 告知打包器本包模块无副作用、可安全按需加载（tree-shaking）。

`exportConditions: ['source']` 是构建侧的钥匙——它让 rollup 解析跨包说明符时优先命中 `source` 分支，直接吃兄弟包的 `src/index.ts` 源码，与对方的 dist 是否存在无关（该行已在第二节配置主体中出现）。实测 `vue.esm-bundler.js` 产物中 `@mini-vue` 说明符出现零次：五个依赖包被完整内联进单一 bundle（156 KB）。构建顺序依赖随之消失，任意一个包都可以独立构建。`extensions` 补充了 `.ts`，使无扩展名的源码引入也能解析。

## 五、类型声明两段式：tsc 产碎片，rollup 捆单文件

TypeScript 消费者需要的不是碎片，而是一个入口 `.d.ts`。`tsc` 按「每个源文件一份声明」产出，直接发布会把包内文件结构泄漏给消费者。本工程采用与官方相同的两段式。

第一段，`tsc` 只发声明、不产 JS：

```json
// tsconfig.build.json（全文）
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": {
    "declaration": true,
    "emitDeclarationOnly": true,
    "declarationDir": "temp/types",
    "noEmit": false,
    "allowImportingTsExtensions": false
  },
  "include": ["packages/*/src/**/*.ts"]
}
```

`emitDeclarationOnly` 把输出限制为声明文件；`noEmit: false` 显式覆盖基座配置的 `noEmit: true`（开发态检查不落盘）；声明落在中间目录 `temp/types`，不与源码或 dist 混放。

第二段，`rollup-plugin-dts` 把碎片捆成单文件：

```js
// rollup.dts.config.js（节选）
const TARGET = process.env.TARGET
if (!TARGET) throw new Error('rollup.dts 需要 TARGET（经 scripts/build.js 逐包传入）')

export default {
  input: `temp/types/${TARGET}/src/index.d.ts`,
  output: { file: `packages/${TARGET}/dist/${TARGET}.d.ts`, format: 'es' },
  plugins: [dts()],
}
```

输入是该包声明碎片的入口，输出是 `dist/<包名>.d.ts`。两段式各取所长：tsc 产出忠于源码的碎片零风险，捆包阶段再折叠成干净的单入口。实测 `vue.d.ts` 为 20 行，其中跨包导出保持为 `export * from '@mini-vue/runtime-dom'` 这样的再导出——与 JS 产物的全内联不同，类型不必内联：消费端经 workspace 依赖解析到兄弟包的 `d.ts`，结果等价且体积更小（对应配置中 `onwarn` 对跨包 `UNRESOLVED_IMPORT` 的放行注释）。

## 六、工程陷阱三则

**陷阱一：`"type": "module"` 下 CJS 产物的扩展名。** 现象：早期版本把 CJS 产物命名为 `vue.js`，Node 消费失败——旧版本 Node 直接抛 `ERR_REQUIRE_ESM`；在 Node 22（本机 v22.22.2 实测）下则是更隐蔽的形态：`require()` 返回一个空命名空间对象，`exports.foo = 1` 这类赋值被静默丢弃，调用 `createApp` 时得到的只是 `undefined`。根因：Node 按离文件最近的 `package.json` 的 `type` 字段解释 `.js` 文件，子包全部声明了 `"type": "module"`，`.js` 因此按 ESM 解析；`.cjs` 扩展名则显式指定 CommonJS，不受 `type` 字段影响。修复：`outputName` 中 cjs 格式固定输出 `.cjs` 后缀（第二节代码）。

**陷阱二：`--environment` 的逗号语义。** 现象：曾试图用一条命令传递含多值的变量（形如 `TARGETS:vue,shared`），结果只有第一个值生效。根因经实测确认（rollup 4.63.4）：`--environment` 以逗号分隔多个「键:值」对，`TARGETS:vue,shared` 被切分为 `TARGETS=vue` 与 `shared=true` 两个独立变量，值中的逗号无法存活。修复：多个变量写成多个键值对（`TARGET:x,NODE_ENV:y`，这正是 build.js 的现行写法）；需要「多个包」语义时不走环境变量，改由编排脚本逐包 spawn——每次只传一个值，逗号问题不复存在。

**陷阱三：漏配 source 条件导致解析到不存在的 dist。** 现象：有一版配置的 nodeResolve 未带 `exportConditions: ['source']`，单独构建 `vue` 时 rollup 按 `exports` 的常规顺序命中 `import` 条件，指向 `./dist/vue.esm-bundler.js` 一类的产物路径，而依赖包彼时尚未构建、dist 为空目录，解析失败刷出大量 `UNRESOLVED_IMPORT`，产物断链。根因：第四节所述的解析双候选默认落在 dist 一侧，构建顺序依赖重新成立。修复：补回 `exportConditions: ['source']`；同时在 `onwarn` 中过滤 CIRCULAR 与 UNRESOLVED_IMPORT 两类告警，让日志只保留真正的错误。

## 七、与官方实现的差异

以下差异均以 `third_party/vue-core`（v3.5.x）当前源码与本仓库配置的核对为准：

- **格式集合**：官方 `rollup.config.js` 定义七种格式（cjs、esm-bundler、global、global-runtime、esm-browser、esm-bundler-runtime、esm-browser-runtime），含浏览器直用 ESM 与 runtime-only 变体；本工程三种，覆盖主要消费形态，`FORMATS` 机制留了扩展位。
- **dev/prod 产物布局**：官方仅对浏览器直用格式生成 `.prod.js` 伴随文件，esm-bundler 保留 `process.env.NODE_ENV` 判断交由消费端决定；本工程 `--prod` 以整套重建 dist 的方式切换，dev 与 prod 不共存于同一次输出。
- **`__DEV__` 的处置**：官方为环境声明加分格式替换（第三节三层方案）；本工程为源码常量的已知取舍。
- **编排能力**：官方 build.js 以 `runParallel(cpus().length, ...)` 按核数并行构建，banner 注入 git commit 哈希，发布流程附体积报告（size-report）；本工程串行 for-await——全量构建（七包加类型声明）实测约 4.7 秒，并行的复杂度暂无收益。
- **插件面与包筛选**：官方配置使用 replace、json、commonjs、polyfill-node、alias、inline-enums、swc 压缩等一组插件，全量构建时跳过 `private` 包；本工程只保留 node-resolve 与 esbuild 两个插件，七包均为 private（只做本地消费、不发布 npm），按 `package.json` 存在性全部构建。

## 小结

本篇补上系列的最后一块：编排脚本扫描包目录、重建 dist、逐包 spawn rollup 注入 `TARGET` 与 `NODE_ENV`；共享配置按 `buildOptions.formats` 把每个包翻译成 esm-bundler / cjs / global 三种产物，global 挂 `MiniVue`；`__DEV__` 因「具名绑定遮蔽自由标识符」而未被 define 替换，dev/prod 的现行差异只来自压缩，官方的环境声明方案是明确的改进路径；`exports` 的 source 条件配合 `exportConditions: ['source']` 让跨包解析直接吃兄弟包源码，构建顺序依赖消失；类型声明经「tsc 碎片 → rollup-plugin-dts 捆包」两段式产出单入口。

至此五篇串成完整链路：响应式系统（01）用两层登记表与 track/trigger 决定「何时重渲染」；渲染器（02）以 vnode 协议、组件副作用与调度队列把重渲染变成批量差量更新；编译器（03）把模板解析、变换并生成渲染函数；内核补全（04）在两端之间补上 Options API 兼容、过渡、缓存与编译优化协同；本篇把这一切从源码变成打包器、Node 与 script 直引三类消费者都能加载的产物。从 `state.count = 1` 触发 trigger，到微任务队列中的 patch 走补丁标记快速路径、最终落到一次 DOM 操作——链路上的每一环，现在都有了实现、测试与交付形态。
