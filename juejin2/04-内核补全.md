# 04 · 内核补全：两种 API 的共存、内置组件与编译优化

> 本篇是系列第四篇。前置阅读：01 篇的响应式系统、02 篇的渲染器与组件、03 篇的模板编译器。产出：补全内核的三组能力——选项式 API 与组合式 API 的共存（含 v-model 表单输入绑定）、Transition 与 KeepAlive 两个内置组件、编译器与渲染器之间的性能契约（补丁标记、区块、缓存静态内容），并逐项说明与官方实现的差异。

## 引言

前三篇分别实现了响应式系统、渲染器与编译器，「模板进、DOM 出、状态变更触发更新」的闭环已经成立。以日常使用的标准衡量，内核还缺三组能力。其一，书写面：`data`/`computed`/`methods`/`watch` 与生命周期选项构成的选项式 API（Options API，Vue 2 时代的组件书写方式）必须能与 `setup` 所在的组合式 API（Composition API）共存，表单输入绑定 v-model 属于同一批使用面能力。其二，内置组件：Transition 的动画时序嵌在挂载与卸载流程里，KeepAlive 要求组件「变为不活跃状态而不是被卸载」，两者都需要渲染器开放协作点。其三，性能：03 篇的编译器尚未把「哪里会变」传递给渲染器，补丁标记、区块与缓存静态内容正是这份契约的三个条款。三组的实现方式同源——都在既有内核上开小口，不推翻已有结构。

## 一、Options API 与组合式 API 的共存

### 1.1 执行顺序：setup 先，applyOptions 后

两种书写方式的共存由一个固定的执行顺序保证，落点在 `setupStatefulComponent`：

```ts
// packages/runtime-core/src/component.ts（setupStatefulComponent，节选；proxy 在 setup 前创建）
const { setup } = Component
if (setup) {
  setCurrentInstance(instance)
  const setupResult = callWithErrorHandling(setup, instance, ErrorCodes.SETUP_FUNCTION, [instance.props, setupContext])
  unsetCurrentInstance()
  handleSetupResult(instance, setupResult)   // 函数→render；对象→proxyRefs 后成为 setupState
}

// Options API 追加：setup（Composition）之后合并 data/computed/methods/watch/生命周期选项
if (isOptionComponent(Component)) {
  applyOptions(instance, Component)
}
```

这段代码确定三件事。公共实例代理（public instance proxy，组件向模板与自身代码暴露的 `this`）在 `setup` 之前创建，选项里的函数因此都以它为 `this`。`setup` 同步执行、返回值先行归一化。`isOptionComponent` 检测到任一选项存在时，`applyOptions` 在 `setup` 之后执行——官方实现同序（`applyOptions` 在 `finishComponentSetup` 内调用，位于 `handleSetupResult` 之后，见 `vuejs/core` 的 `runtime-core/src/component.ts`），因此选项式的 `beforeCreate`/`created` 实际晚于 `setup` 执行。

### 1.2 同一命名空间与代理读取优先级

`applyOptions` 把三类选项统一落进 `instance.data` 一个命名空间：

```ts
// packages/runtime-core/src/componentOptions.ts（applyOptions，节选，
// 完整实现见同文件）
if (options.data) {
  instance.data = reactive(options.data.call(proxy, proxy) as Data)
} else if (!instance.data) {
  instance.data = {}   // 无 data 也保持容器，method/computed 挂载用
}
// methods：instance.data[key] = options.methods[key].bind(proxy)
// computed：instance.data[key] = computed(getter[, setter])，this 经闭包绑到 proxy
```

三个要点：`data` 以工厂函数调用并经 `reactive` 包装；`methods` 逐个绑定 `proxy` 后挂入 `data`，方法体内的 `this.count` 走完整的代理读取链；`computed` 转为计算属性后同样挂入 `data`，读取时由 reactive 容器对 ref 的解包语义返回裸值。模板与选项代码读取 `this.count`，全部经过公共实例代理：

```ts
// packages/runtime-core/src/componentPublicInstance.ts（get 拦截，节选）
// 访问优先级：setupState → props → data → ctx → $内建 → globalProperties
if (setupState !== EMPTY_OBJ && hasOwn(setupState, key)) {
  return setupState[key]
} else if (props !== EMPTY_OBJ && hasOwn(props, key)) {
  return props[key]
} else if (data !== EMPTY_OBJ && hasOwn(data, key)) {
  return data[key]
} else if (ctx !== EMPTY_OBJ && hasOwn(ctx, key)) {
  return ctx[key]
}
```

优先级 setupState → props → data → ctx 之后才是 `$slots` 等内建属性与 `globalProperties`。同名冲突因此有确定语义：`setup` 返回值中的 `count` 遮蔽 `data` 中的同名 `count`，模板读到前者。用 `hasOwn` 而非 `in` 判断，避免原型链属性意外命中；`set` 拦截按同一优先级回写，保证写入落点与读取一致。

### 1.3 watch 选项与生命周期选项

这两类选项不建新设施，复用组合式 API 的既有机制。`watch` 选项的键名可能是路径（`'a.b.c'`），`createPathGetter` 把它编译为按段取值的 getter，普通键直接读代理属性；函数形式与 `{ handler, immediate, deep }` 对象形式最终都落到与 `watch()` 相同的 `doWatch`，调度与深层语义不重复实现（`packages/runtime-core/src/componentOptions.ts`）。生命周期选项分两类：`beforeCreate`/`created` 没有对应的渲染时机，在 `applyOptions` 内同步执行；其余经 `injectHook('m' as any, options.mounted.bind(proxy), instance)` 这类调用显式指定实例为目标，登记进实例的钩子数组——与 `setup` 中 `onMounted` 等 API 写入同一个数组（`packages/runtime-core/src/lifecycle.ts`），混用组件里两种写法的同名钩子按注册顺序先后执行。

### 1.4 表单输入绑定：v-model 的编译期展开

官方文档把 v-model 定义为按元素类型分派的「元素-属性-事件」组合：文本类元素绑定 `value` 监听 `input`，checkbox/radio 绑定 `checked` 监听 `change`，select 绑定 `value` 监听 `change`；`.lazy` 把同步时机改为 `change` 事件之后，`.number` 用 `parseFloat` 转换（无法处理时返回原始值），`.trim` 去掉两端空格。这份矩阵在编译期展开，文本形态由 `transformElement` 内联为一对属性（`packages/compiler-core/src/transforms/transformElement.ts`），产物可以直接验证：

```js
// compile('<input v-model.lazy.number="msg" />').code（实测产物）
const { looseToNumber: _looseToNumber, createElementVNode: _createElementVNode,
        openBlock: _openBlock, createElementBlock: _createElementBlock } = Vue
return function render(_ctx, _cache) {with (_ctx) {
    return _openBlock(), _createElementBlock("input", {value: msg, onChange: ($event) => (msg = _looseToNumber($event.target.value))}, null, 8)
  }
}
```

`.lazy` 把 `onInput` 换成 `onChange`；`.number` 在取值表达式外包一层 `_looseToNumber`（`parseFloat`，失败返回原值）；`.trim` 追加 `.trim()`。checkbox/radio/select 不做内联，编译为 `withDirectives` 包裹的运行时指令（`packages/runtime-dom/src/directives/vModel.ts`）：指令的 `updated` 钩子在每次更新时把 `props.checked`/`props.value` 同步给元素，`change` 事件反向回写模型，`el._assigning` 标记区分程序化赋值与用户输入以防止循环。组件上的 v-model（官方展开为 `:modelValue` 与 `@update:modelValue`）不在本实现范围内，见第五节。

## 二、Transition：渲染器的三个开放点

进入动画有一个结构性矛盾：起始样式必须在元素插入文档之前生效，切换到终态又必须等到插入之后的下一帧——时序完全嵌在渲染器的挂载流程里。解法是把时序知识放进组件、把时机关口开放给渲染器。Transition 本身不渲染任何东西，其渲染函数只做一件事：取插槽的唯一元素子节点并挂上钩子，多节点与组件子节点不处理（`packages/runtime-core/src/components/Transition.ts` 的 `setup`：`el.transition = createTransitionHooks(props)`）。渲染器只在三个时机读取 `vnode.transition`：

```ts
// packages/runtime-core/src/renderer.ts（mountElement 与 unmount 的过渡开放点，节选）
// 挂载：insert 前挂起始类
vnode.transition && vnode.transition.beforeEnter(el)
hostInsert(el, container, anchor)
// 挂载：insert 后触发进入动画
vnode.transition && vnode.transition.enter(el)

// 卸载：动画结束后才真正移除
if (vnode.transition && vnode.transition.leave) {
  vnode.transition.leave(vnode.el, () => {
    invokeDirectiveHook(vnode, null, parentComponent, 'unmounted')
    hostRemove(vnode.el)
  })
}
```

`mountElement` 在 `insert` 前调用 `beforeEnter`（元素尚不在文档中，起始类已生效）、`insert` 后调用 `enter`；`unmount` 调用 `leave(el, done)`，真正的 `hostRemove` 推迟到 `done`——动画结束前元素保留在文档中。钩子内容与官方文档的六个类名一一对应：`beforeEnter` 添加 `v-enter-from` 与 `v-enter-active`（均为插入前添加）；`enter` 在下一帧移除 `v-enter-from`（插入后下一帧移除）、添加 `v-enter-to`，动画结束后三者全部清除（`v-enter-active` 保持到动画完成）。离开侧对称：`leave` 触发时立即添加 `v-leave-from` 与 `v-leave-active`，一帧后移除 `v-leave-from`、添加 `v-leave-to`，结束后清类并调用 `done`。结束检测是「事件优先、超时兜底」：`whenTransitionEnds` 同时登记根元素的 `transitionend` 监听与 `duration` 超时定时器，`resolved` 标记保证两者只生效一次、先到者摘掉另一个（`packages/runtime-core/src/components/BaseTransition.ts`）。兜底是必要的：测试运行在 jsdom（无浏览器布局的 DOM 实现）中，不会派发真实的 `transitionend`，缺少超时兜底则 `done` 永远不被调用、DOM 永远不被移除。同理，官方以双 `requestAnimationFrame` 表达「下一帧」（同文件 `nextFrame`），本实现用双 `setTimeout` 近似。

## 三、KeepAlive：隐藏代替卸载

官方文档对 KeepAlive 的描述是「缓存组件实例……组件切换时会被缓存，变为不活跃状态而不是被卸载」。卸载在渲染器里意味着副作用停止、DOM 移除、状态清空，这条语义因此同样需要组件与渲染器的契约。KeepAlive 用一个缓存 Map 与两个私有标记达成：

```ts
// packages/runtime-core/src/components/KeepAlive.ts（setup，节选）
setup(_props: Record<string, any>, { slots }: any) {
  const cache = new Map<any, any>() // key → 缓存的 vnode（含 component 实例）
  return () => {
    let child = slots.default && slots.default()[0]   // 取唯一子节点（省略归一化）
    const key = child.key != null ? child.key : child.type
    const cachedVNode = cache.get(key)
    if (cachedVNode && cachedVNode.component) {
      // 回魂：返回缓存 vnode（同一实例），标记为「需要激活」
      child = cachedVNode
      child._activate = true
    } else {
      cache.set(key, child)
    }
    // 若被换掉 → 隐藏（renderer 读 _deactivate 拦截卸载）
    child._deactivate = true
    return child
  }
}
```

子组件以 key（显式 `key` 优先，否则组件类型）为身份入缓存；再次渲染时若缓存命中且实例仍在，返回缓存的同一个 vnode 并置激活（activate）标记；当前子组件一律带停用（deactivate）标记。两个标记由渲染器解释：

```ts
// packages/runtime-core/src/renderer.ts（processComponent 与 unmount 的 KeepAlive 分支，
// 节选）
if (n1 == null) {
  // KeepAlive 回魂：缓存实例还在 → 显示 + 刷新，不重跑 setup
  if ((n2 as any)._activate && n2.component) {
    const instance = n2.component
    const rootEl = instance.subTree && instance.subTree.el
    if (rootEl) hostShowNode(rootEl)
    instance.update()   // _activate 标记随即可复位
    return
  }
  mountComponent(n2, container, anchor, parentComponent)
}
// unmount 内：
if ((vnode as any)._deactivate && vnode.component) {
  const rootEl = vnode.component.subTree && vnode.component.subTree.el
  if (rootEl) hostHideNode(rootEl)
  return
}
```

`unmount` 看到 `_deactivate` 且实例存在，取组件根元素执行 `hostHideNode`（runtime-dom 注入的 `display: none` 切换）后直接返回——副作用不停止、DOM 不移除。切回时 `processComponent` 的挂载入口看到 `_activate`，显示根元素并调用 `instance.update()` 重新渲染子树。关键在于这是「显示 + 刷新」而不是重新挂载：实例对象还是缓存中的那一个，`setup` 不会执行第二次，内部状态原样保留。测试的断言是：切走后根元素 `display` 为 `none`，切回后内容与状态均与切走前一致（`packages/runtime-dom/__tests__/transitionKeepAlive.spec.ts`）。

官方实现还提供 include/exclude（按组件 `name` 过滤缓存）、max（超限时销毁最久未访问的实例，类似 LRU——最近最少使用淘汰策略），以及 activated/deactivated 两个钩子（首次挂载与从缓存重新插入时触发前者，从 DOM 移除进入缓存与卸载时触发后者）；停用子树被移入一个脱离文档的存储容器而非仅设 `display: none`（`vuejs/core` 的 `runtime-core/src/components/KeepAlive.ts`）。这些是本实现明确裁剪的部分，保留的是「缓存实例对抗卸载」的核心链路。

## 四、编译优化三件套：编译器生产、渲染器消费

三件套构成一份性能契约：编译器在产物中编码「哪里会变、以何种方式变」，渲染器据此跳过确定不变的部分。先看一份实测产物：

```js
// 模板 <div id="a"><span>ok</span><b>{{ n }}</b></div> 的编译产物（换行略作整理）
const { createElementVNode: _createElementVNode, toDisplayString: _toDisplayString,
        openBlock: _openBlock, createElementBlock: _createElementBlock } = Vue
const _hoisted_1 = _createElementVNode("span", null, "ok", -1)
return function render(_ctx, _cache) {with (_ctx) {
    return _openBlock(), _createElementBlock("div", {id: "a"}, [_hoisted_1, _createElementVNode("b", null, _toDisplayString(n), 1)], -1)
  }
}
```

四个特征：根节点是 `_openBlock() + _createElementBlock(...)`；静态子树被提取为 render 作用域顶部的 `const _hoisted_1`；动态文本 `<b>{{ n }}</b>` 带标记 `1`（TEXT）；根节点整体的 `-1` 表示可提升。

### 4.1 补丁标记：位掩码与动态名单

补丁标记（patch flags）是记录在 vnode 创建调用里的位掩码（bitmask，每个二进制位独立表达一个语义的整数）——官方文档的表述是补丁标记「在 vnode 创建调用中编码每个元素所需的更新类型」，如 CLASS 为 2、STABLE_FRAGMENT 为 64，多个标记可合并为一个数字、运行时以位运算检查。本工程的取值定义在 `packages/shared/src/index.ts` 的 `PatchFlags` 枚举（TEXT=1、CLASS=2、STYLE=4、PROPS=8、FULL_PROPS=16、STABLE_FRAGMENT=64、HOISTED=-1、BAIL=-2）。生产端在 `transformElement` 扫描属性时逐个累计：`:class`/`:style` 占特定位（高频且不走名单）；其余动态属性——含事件与 `v-html` 展开的 `innerHTML`——进 PROPS 位并记入动态属性名单（dynamicProps，编译期确定的动态属性名数组）；属性名本身是变量（`:[name]="x"`）时名单无法静态确定，升级为 FULL_PROPS；插值文本补 TEXT 位；全静态且无指令的元素整体置 `-1`。消费端在 `patchElement`：

```ts
// packages/runtime-core/src/renderer.ts（patchElement 的 props 动态路径，节选）
const hasDynamicFlag = patchFlag & (PatchFlags.CLASS | PatchFlags.STYLE | PatchFlags.PROPS | PatchFlags.FULL_PROPS)
if (patchFlag === PatchFlags.BAIL || !hasDynamicFlag) {
  // 无优化标记：朴素全量 diff（回退路径，遍历新旧 props 全键）
} else {
  if (patchFlag & PatchFlags.PROPS) {
    const keys = dynamicProps || EMPTY_ARR
    for (const key of keys) {
      if (key === 'class' || key === 'style') continue
      if (newProps[key] !== oldProps[key]) {
        hostPatchProp(el, key, oldProps[key], newProps[key])
      }
    }
  }
  // CLASS / STYLE 位各比对一个属性，FULL_PROPS（键并集）同法按位分发
}
```

快速路径按位分发：CLASS 位只比对 `class`，PROPS 位只遍历名单内的键，比对范围从「全部属性」收缩到「编译期已知会变的属性」。无标记或 BAIL（手写渲染函数未经编译）时回退全量比对，快速路径因此是纯增量收益。

### 4.2 区块与树结构打平

区块（block）在官方文档中的定义是「内部结构稳定的一个部分」，它追踪其中所有带补丁标记的后代——不只是直接子节点。由此得到树结构打平（tree flattening）：每个区块把后代中的动态节点收进一个数组，更新时遍历数组而非递归整棵树。收集机制是两个模块级变量加一个栈：

```ts
// packages/runtime-core/src/vnode.ts（block 树，节选；
// createElementBlock 即 createVNode(..., isBlockNode=true) 后接 setupBlock）
export function openBlock() {
  blockStack.push((currentBlock = []))
}

// createBaseVNode 内的收集条件：
if (!isBlockNode && currentBlock && (vnode.patchFlag > 0 || vnode.shapeFlag & ShapeFlags.COMPONENT)) {
  currentBlock.push(vnode)
}
```

`openBlock` 压入新的收集数组；此后所有 vnode 创建调用中，`patchFlag > 0` 或组件类型的节点被推入 `currentBlock`，静态节点的创建只是一次普通函数调用、不进块。块根经 `setupBlock` 把这段收集结果挂为自己的 `dynamicChildren`。更新时的守卫值得细看：

```ts
// packages/runtime-core/src/renderer.ts（patchChildrenAndBlock，节选）
if (
  n1.dynamicChildren &&
  n2.dynamicChildren &&
  (n2.dynamicChildren as any[]).length > 0 &&
  (n1.dynamicChildren as any[]).length === (n2.dynamicChildren as any[]).length
) {
  patchBlockChildren(n1, n2, el, parentComponent)
  return
}
```

条件是「非空且新旧等长」才走块路径。非空约束来自一个具体场景：`<div>{{ x }}</div>` 这类根节点自身带 TEXT 位、却没有独立动态子节点的模板，`dynamicChildren` 为空，径直走块路径会漏掉根自己的文本更新——官方实现不受此影响，它把根自身的 TEXT 位放在块处理之后的按位分发里单独执行。等长约束是结构变化的防御：`v-for` 列表长度变化等情形会使动态节点数改变，回退全量比对保证正确；官方对「新旧长度不等」同样强制回退（`vuejs/core` 渲染器中标记为 #6385 的守卫）。

### 4.3 缓存静态内容

缓存静态内容（官方文档亦称静态提升，static hoisting）解决的是重复创建与重复比对：纯静态子树首次渲染时缓存 vnode，重渲染时跳过差异比对。实现是 codegen 的一个预扫描：

```ts
// packages/compiler-core/src/codegen.ts（collectHoistedNodes，节选）
const hoistable =
  node.patchFlag === -1 &&
  !node.isComponent &&
  !node.isBlock &&
  !node.dirs?.length &&
  node.tag && typeof node.tag === 'string' &&
  // children 只能是纯静态形态：JS 调用（如 renderSlot）依赖 _ctx，提升会移出
  // with 作用域 → ReferenceError；多 children 数组保守不升
  (node.children == null ||
    typeof node.children === 'string' ||
    node.children.type === NodeTypes.TEXT_CALL) &&
  // props 必须全静态（动态值在 with 外引用会 ReferenceError）
  isStaticProps(node.props)
if (hoistable) {
  ;(node as any)._hoistedId = out.length + 1
  out.push(node)
  return
}
```

提升的判定刻意保守，原因在 03 篇的取舍：渲染函数包裹在 `with (_ctx)` 中，提升会把节点表达式移到 render 顶层的 `const` 声明里、脱离 `with` 块——子树内一旦出现依赖 `_ctx` 的调用或动态工具函数（如 `_looseToNumber(...)`），运行时直接抛 `ReferenceError`。因此 children 只允许纯文本形态、props 必须全是静态字面量，多个子节点保守不提升。渲染器一侧的配合是 `patch` 开头的 `if (n1 === n2) return`：提升节点跨渲染是同一个对象，回退全量比对时新旧节点恒等、整个比对被短路；块路径下静态节点根本不进入遍历。官方文档提到的进一步优化（大量连续静态内容存为纯 HTML 字符串、经 `innerHTML` 挂载）依赖连续静态节点计数，本实现未做。

## 五、与官方实现的差异

以下差异均已核对 `vuejs/core` 源码（v3.5.x）后列出：

- **选项合并**：官方的读取优先级是 setupState → data → props → ctx，且以 accessCache 记忆每个键的来源、省去重复 `hasOwn`（`runtime-core/src/componentPublicInstance.ts`）；本实现为 setupState → props → data → ctx，无缓存。官方 methods 挂在 ctx、computed 经 `Object.defineProperty` 定义到 ctx（`runtime-core/src/componentOptions.ts`）；本实现统一挂入 reactive 化的 `instance.data`，computed 读取靠容器的 ref 解包。官方另有 mixins/extends 与全局 mixin 的选项合并策略，本实现未做。
- **Transition**：仅支持单元素子节点与 `name`/`duration` 两个属性；无 appear、mode（out-in/in-out）与 JS 钩子（官方的 `@enter`/`@leave` 接收 `(el, done)`，纯 JS 动画必须调用 `done`）；结束检测只监听 `transitionend`，不监听 `animationend`，也不读取 CSS 计算出的实际时长；「下一帧」以双 `setTimeout` 近似官方的双 rAF。
- **KeepAlive**：无 include/exclude/max（LRU）与 activated/deactivated 钩子；以 `display: none` 隐藏，官方把停用子树移入脱离文档的存储容器。
- **编译优化**：v-if/v-for 不创建新区块（实测产物中分支是普通 `_createElementVNode`，官方文档说明二者会创建新的区块节点），结构变化由守卫回退全量比对；无 v-memo/v-once；静态提升不生成纯 HTML 字符串形态。
- **v-model**：文本形态打 PROPS 位但未把 `value`/事件名记入 dynamicProps 名单，「模型程序化变更 → 输入框回显」方向因此不生效（实测：修改 `msg.value` 后输入框仍显示旧值；用户输入 → 模型的方向有测试锚定）。官方先把 v-model 重写为普通的绑定与事件（`compiler-dom/src/transforms/vModel.ts`），再由统一的属性扫描登记名单，两个方向都完整。组件 v-model（`:modelValue` + `@update:modelValue`）未实现。

```ts
import { createApp, ref } from '@mini-vue/vue'

const container = document.createElement('div')
createApp({
  setup() {
    const count = ref(999)               // setupState：优先级最高
    return { count }
  },
  data() {
    return { count: 0, other: 'x' }      // 同名 count 被 setupState 遮蔽
  },
  computed: {
    label() { return this.other + '!' }, // this 走公共代理 → 读到 data.other
  },
  template: `<p>{{ count }}:{{ other }}:{{ label }}</p>`,
}).mount(container)
// container.innerHTML === '<p>999:x:x!</p>'
```

预期输出 `<p>999:x:x!</p>`：`count` 命中 setupState 分支，`other` 与 `label` 落到 data 分支，`label` 内的 `this.other` 经公共代理读到 `data.other`。对应断言见 `optionsApi.spec.ts` 的「mixes with setup」用例。

## 小结

内核补全的三组能力各以一种方式挂在既有结构上。Options API 靠固定执行顺序与统一命名空间：`setup` 先执行、`applyOptions` 随后把 data/computed/methods 落进 `instance.data`，公共实例代理以 setupState → props → data → ctx 的优先级裁决同名冲突，watch 与生命周期选项复用组合式 API 的容器。Transition 与 KeepAlive 靠渲染器在硬节点上的开放点：挂载前后的两个钩子、卸载时推迟移除的 `leave(el, done)`、卸载分支上的隐藏代替卸载与挂载分支上的显示加刷新。编译优化三件套是一份单向契约：补丁标记以位掩码收缩属性比对范围，区块以打平的动态后代数组取代递归遍历，静态提升让纯静态子树跨渲染复用——编译器生产标记，渲染器消费标记，未经编译的路径随时可回退全量比对。
