# 02 · 渲染器与组件：从 vnode 到最少移动的 DOM 更新

> 本篇实现 `packages/runtime-core` 与 `packages/runtime-dom`。前置阅读：00 篇的数据流总览、01 篇的副作用执行模型与 scheduler 选项。产出：一个平台无关的渲染器——vnode 协议与宿主操作集、shapeFlag 位图与 patch 分发、组件实例（渲染副作用 + 作用域 + 调度队列）、键控子节点比对与最长递增子序列、事件缓存，并逐项说明与官方实现的差异。

## 引言

00 篇的结论之一：声明式框架的内部必然存在一个命令式层。本篇实现这个命令式层——渲染器（renderer），接收 vnode 树、将其转换为真实宿主节点，并在依赖变化后计算差异、把必要操作应用到宿主。官方文档将渲染管线概括为三个阶段：编译（模板编译为渲染函数）、挂载（渲染器执行渲染函数、创建真实 DOM）、更新（依赖变化后副作用重新运行，比对并应用差异）。01 篇补齐了「何时重跑」的半边，并留下文档的一句话作为本篇的实现规格：「每个组件实例创建一个响应式副作用来渲染和更新 DOM」。本篇依次解决五个子问题：用什么数据结构让渲染核心不依赖平台 API；渲染入口如何常数成本分发；组件实例如何装配为异步更新单元；两组子节点比对如何把 DOM 移动压到最少；事件处理函数频繁更换时如何避免反复解绑重绑。

## 一、vnode 与宿主操作集

官方文档将虚拟 DOM 定义为：将目标所需的 UI 通过数据结构「虚拟」地表示出来，保存在内存中。落到代码，虚拟节点（virtual node，vnode）是对「目标 UI 的一格」的纯数据描述，字段见 `packages/runtime-core/src/vnode.ts` 的 `VNode` 接口：`type` 记节点种类（元素名字符串、组件定义、或 `Text`/`Comment`/`Fragment` 三个独立 Symbol）；`props`/`key`/`children` 记属性、身份与子节点；`shapeFlag` 是类型位图（第二节）；挂载后 `el` 指向真实节点、组件 vnode 另有 `component` 指向实例，`anchor` 是 Fragment 的尾部锚点——后三者是渲染结果回写 vnode 的通道。整个接口不含任何平台 API。

「纯数据」是跨平台的前提。渲染器通过依赖注入（dependency injection）——由调用方提供底层操作、框架只编写编排逻辑——获得全部宿主（host）能力：`createRenderer(options)` 的 `options` 即宿主操作集，`renderer.ts` 的 `RendererOptions` 接口列出全部要求——`createElement`/`createText`/`createComment` 创建节点，`insert`（语义是「插到 anchor 之前」）与 `remove` 移动移除，`setText`/`setElementText` 写文本，`parentNode`/`nextSibling` 做结构查询，`patchProp` 为属性打补丁。`baseCreateRenderer` 在开头把它们解构为 `hostCreateElement` 一类内部别名，函数体从此只见别名、不见平台。

浏览器一侧的组装在 `packages/runtime-dom`：`nodeOps.ts` 提供基于 `document` 的全部操作（`insert` 即 `parent.insertBefore(child, anchor || null)`），`patchProp.ts` 分发 class/style/事件/属性，两者以 `const rendererOptions = { ...nodeOps, patchProp }` 合并后注入 `createRenderer`，并以惰性单例缓存（`ensureRenderer`），不调用 `createApp` 就不创建渲染器。渲染器回吐两件东西：底层 `render(vnode, container)` 与应用工厂 `createApp`（`apiCreateApp.ts` 的 `createAppAPI(render)` 闭包绑定 render，`app.mount` 把根组件包成 vnode 交给 render）。`render` 在容器上记忆 `container._vnode`：入参非空时以它为旧树调 patch，入参为空时卸载旧树——更新与卸载共用一个入口。替换宿主操作集即可对接其他环境，`runtime-core` 全程不认识 `document`。

## 二、shapeFlag 位图与 patch 分发

vnode 的 `type` 有五类取值，逐个做类型比较来分流，分支数与可读性都差。Vue 的方案是位图（bitmap）——用一个整数的每个二进制位表示一种属性，多种属性用「位或」组合、用「位与」查询。建 vnode 时按 type 编码：字符串命中 `ELEMENT`（`1 << 0`），对象或函数命中 `STATEFUL_COMPONENT`（`1 << 2`，位值见 `packages/shared/src/ShapeFlags.ts`）；随后 `normalizeChildren` 按子节点形态以 `vnode.shapeFlag |= type` 追加 `TEXT_CHILDREN`（`1 << 3`）、`ARRAY_CHILDREN`（`1 << 4`）或 `SLOTS_CHILDREN`（`1 << 5`）。「带数组子节点的元素」于是就是 `ELEMENT | ARRAY_CHILDREN` 一个字段：读一次、判两类属性，查询是常数时间的位与。

分发中心是 patch（比对，patch/diff）——对新旧 vnode 做同层比较并应用差异的入口：

```ts
// packages/runtime-core/src/renderer.ts —— patch（节选）
function patch(n1, n2, container, anchor = null, parentComponent = null, isSVG = false) {
  if (n1 === n2) return
  const { type, shapeFlag } = n2
  // 类型或 key 变了 → 丢弃旧节点整树，当新节点处理
  if (n1 && !isSameVNodeType(n1, n2)) {
    anchor = getNextHostNode(n1)
    unmount(n1, parentComponent)
    n1 = null
  }
  switch (type) {
    case Text:
      processText(n1, n2, container, anchor)
      break
    case Fragment: // Comment 分支同构，略
      processFragment(n1, n2, container, anchor, parentComponent)
      break
    default:
      if (shapeFlag & ShapeFlags.ELEMENT) {
        processElement(n1, n2, container, anchor, parentComponent, isSVG)
      } else if (shapeFlag & ShapeFlags.COMPONENT) {
        processComponent(n1, n2, container, anchor, parentComponent)
      }
  }
}
```

五路分发由两段判断组成：`Text`/`Comment`/`Fragment` 是独立 Symbol，被 `switch(type)` 直接命中；元素与组件走 default，以一次位与分流（`COMPONENT` 是 `STATEFUL | FUNCTIONAL` 的组合位）。Fragment 承接模板的多根节点：挂载时创建首尾两个注释节点把内容围起来（`processFragment` 分别写入 `n2.el` 与 `n2.anchor`），一棵 Fragment 子树因此恰好占位一个出口，卸载与移动只需处理两个锚点。第一行以引用相等挡住同一节点与自身的空比对。

第三段是本节的关键顺序。`isSameVNodeType` 要求 type 与 key 都相同才视为同一节点，不成立时旧子树整体作废、`n1` 置空走全新挂载。顺序是先 `getNextHostNode(n1)` 取锚点（anchor——`insert` 的参照节点，新节点将插到它之前）、再 `unmount(n1)`，不可颠倒：卸载会把旧节点从文档摘除，之后再对它做 `nextSibling` 查询必然落空，运行期抛 `NotFoundError`——仓库实现注释明确记录了这个易错点，官方实现同样先取锚点。`getNextHostNode` 对组件递归下钻到 `subTree`、对 Fragment 取尾部锚点（`hostNextSibling(vnode.anchor || vnode.el)`），保证拿到的是紧跟这棵子树之后的第一个宿主节点。

## 三、组件实例：渲染副作用 + 作用域 + 调度器

组件是「带状态的子树」。挂载分三步（`mountComponent`）：`createComponentInstance` 创建实例 → `setupComponent` 执行 setup → `setupRenderEffect` 建立渲染副作用。实例（`component.ts` 的 `ComponentInternalInstance`）是组件的运行时载体：`uid` 单调递增；`props`/`slots`/`setupState`/`render` 构成数据面；`subTree` 记最近一次渲染结果；`next` 暂存父级驱动更新带来的新 vnode；`scope` 是实例专属的作用域（effect scope，把一批副作用的生命周期捆绑为整体停止，01 篇第八节）。作用域的接线在 `currentInstance.ts`：`setCurrentInstance` 设指针的同时调用 `instance.scope.on()`，setup 执行窗口内创建的副作用与 computed 由 01 篇的自动登记机制收进实例名下；卸载时 `unmountComponent` 调 `instance.scope.stop()`，setup 期的全部副作用随组件一次停止。

核心装配是 `setupRenderEffect`：

```ts
// packages/runtime-core/src/renderer.ts —— setupRenderEffect（节选）
const componentUpdateFn = () => {
  if (!instance.isMounted) {
    invokeHooks(instance, 'bm')                              // beforeMount
    const subTree = (instance.subTree = renderComponentRoot(instance))
    patch(null, subTree, container, anchor, instance)
    initialVNode.el = subTree.el
    queuePostRenderEffect(() => invokeHooks(instance, 'm'))  // mounted 走 post 队列
    instance.isMounted = true
  } else {
    if (instance.next) applyPreUpdate(instance, instance.next) // 父级驱动的 props/slots 更新
    const prevTree = instance.subTree
    const nextTree = renderComponentRoot(instance)
    instance.subTree = nextTree
    invokeHooks(instance, 'bu')                              // beforeUpdate
    patch(prevTree, nextTree, hostParentNode(prevTree.el!), getNextHostNode(prevTree), instance)
    queuePostRenderEffect(() => invokeHooks(instance, 'u'))
  }
}
const update: SchedulerJob = (instance.update = effect(componentUpdateFn, {
  scheduler: () => queueJob(update),   // 依赖变 → 入队，而非同步重渲染
  allowRecurse: true,
}) as any)

update.id = instance.uid
```

`componentUpdateFn` 的双分支覆盖文档那句话的两个动词：未挂载时 `renderComponentRoot` 以实例代理为 this 调用 render 并归一化返回值，`patch(null, subTree, ...)` 完成挂载；已挂载时若 `instance.next` 非空，先由 `applyPreUpdate` 把父级传入的新 props/attrs/slots 并入实例，再渲染新树、以旧树为 n1 调 patch。`onMounted`/`onUpdated` 经 `queuePostRenderEffect` 进入 post 队列，执行时 DOM 必然已经就位。末五行是「渲染副作用」的落点：渲染函数读过的响应式状态都成为该副作用的依赖（01 篇的 track）；依赖变化不直接重跑，而是经 scheduler 把 `update` 送进调度队列（scheduler queue）。`allowRecurse` 允许「更新过程中又改了自身依赖」的场景重入；`update.id = instance.uid` 为排序做准备。

调度队列（`packages/runtime-core/src/scheduler.ts`）解决两个问题：同一组件在一个刷新周期内只更新一次；多个组件按父子顺序更新。

```ts
// packages/runtime-core/src/scheduler.ts —— queueJob（节选）
export function queueJob(job: SchedulerJob) {
  if (!(job.flags! & QUEUED)) {          // 同一作业已在队列（含正在执行的）→ 跳过
    job.flags = (job.flags || 0) | QUEUED
    const jobId = getId(job)
    const last = queue[queue.length - 1]
    if (!last || jobId >= getId(last)) {
      queue.push(job)                    // 尾部快速路径
    } else {
      // 二分（从 flushIndex + 1 起搜）找插入位后 splice，保证队列 id 升序
    }
    queueFlush()
  }
}
```

两个关键点。`QUEUED` 位去重：入队即在 `job.flags` 打位，已在队列或正在执行则跳过——同一轮同步代码里改十次状态，更新函数只入队一次。按 id 二分插序：`uid` 按创建顺序分配，父组件必然小于子组件，队列保持 id 升序、父组件先重渲染。官方 `scheduler.ts` 对这个排序的注释给出两条动机：父总先于子创建因而 id 更小；父组件更新期间卸载的子组件，其排队中的作业可以被跳过。二分从 `flushIndex + 1` 起搜，保证不插到已执行区之前。

入队后 `queueFlush` 以 `isFlushing`/`isFlushPending` 双开关保证一轮只安排一次刷新，并把 `currentFlushPromise = resolvedPromise.then(flushJobs)` 排进微任务（microtask）——同步代码里的多次状态修改全部合并到这一条微任务里。刷新本体：

```ts
// packages/runtime-core/src/scheduler.ts —— flushJobs（节选）
function flushJobs() {
  isFlushPending = false
  isFlushing = true
  flushPreFlushCbs()                    // 1. pre 作业（渲染前的 watch 回调等）
  try {
    for (flushIndex = 0; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex]
      if (job) {
        job.flags! &= ~QUEUED           // 清位：允许执行中途再次被 queueJob
        job()
      }
    }
  } finally {
    flushIndex = -1
    queue.length = 0
    flushPostFlushCbs()                 // 2. post 作业（onMounted/onUpdated 等）
    isFlushing = false
    currentFlushPromise = null
    if (queue.length || pendingPostFlushCbs.length || pendingPreFlushCbs.length) {
      flushJobs()                       // 3. 刷新中又来了新作业 → 再来一轮
    }
  }
}
```

循环条件里的 `queue.length` 是活引用：执行某个组件的更新时又触发其他组件，`queueJob` 直接 push 进同一个数组，本轮循环继续消费——flush 期间入队的作业同轮跑完。执行前清掉 `QUEUED` 位，作业因此在执行中可以再次入队。`finally` 中清空主队列后执行 post 队列（生命周期钩子在此），若又积压了新作业则递归再来一轮，直到队列稳定。`nextTick` 与这一切共用同一条流水，实现只有一行本质：`const p = currentFlushPromise || resolvedPromise; return fn ? p.then(fn) : p`——无刷新排队时回退为已 resolve 的 promise，回调立即排入微任务；有刷新时回调排在 `flushJobs` 之后。「同步改状态，nextTick 里拿到的一定是更新后的 DOM」由此得到机制保证。

## 四、子节点比对：五步与最长递增子序列

元素子节点的更新先按形态分流（`patchChildren`）：新为文本则卸载数组、设置文本；数组对数组进入键控子节点比对（keyed diff）——以 key 为身份标识对新旧两组子节点做配对与差异应用的算法；其余情形退化为清空重挂。数组对数组是性能敏感路径，`patchKeyedChildren` 分五步，前四步消化规律情形：同步前缀（从头 patch type 与 key 都相同的节点，遇差异停下）；同步后缀（从尾对称进行）；旧节点耗尽（`i > e1`，剩余新节点为纯新增，以右邻节点为锚点批量挂载）；新节点耗尽（`i > e2`，剩余旧节点批量卸载）。第 5 步处理中间乱序区，先为新 children 建 `keyToNewIndexMap`（key → 新下标），再遍历旧 children 配对：

```ts
// packages/runtime-core/src/renderer.ts —— patchKeyedChildren 第 5.2 步（节选）
const toBePatched = e2 - s2 + 1
let patched = 0
let moved = false
let maxNewIndexSoFar = 0
// newIndexToOldIndexMap[newIndex-s2] = oldIndex+1（+1 是为了 0 表示「新节点」）
const newIndexToOldIndexMap = new Array(toBePatched)
for (i = 0; i < toBePatched; i++) newIndexToOldIndexMap[i] = 0
for (i = s1; i <= e1; i++) {
  const prevChild = c1[i]
  if (patched >= toBePatched) {         // 新节点已全部对上，剩余旧节点只能删除
    unmount(prevChild, parentComponent)
    continue
  }
  let newIndex
  if (prevChild.key != null) {
    newIndex = keyToNewIndexMap.get(prevChild.key)
  } // 无 key：在新区里顺序找「同型且还没被占位」的（循环体从略）
  if (newIndex === undefined) {
    unmount(prevChild, parentComponent)
  } else {
    newIndexToOldIndexMap[newIndex - s2] = i + 1
    if (newIndex >= maxNewIndexSoFar) {
      maxNewIndexSoFar = newIndex
    } else {
      moved = true
    }
    patch(prevChild, c2[newIndex] as VNode, container, null, parentComponent)
    patched++
  }
}
```

要点有四。`toBePatched = e2 - s2 + 1` 是乱序区新节点数，`patched` 计已配对数，达到上限后剩余旧节点只剩卸载。有 key 走 Map 查表；无 key 退化为按索引顺序找「同型且未被占位」的新节点——这就是无 key 列表按位置复用的来源：比对按位置配对，DOM 节点留在原位、内容被改写，列表项的本地状态（输入框的值、展开态）跟着位置而不是跟着数据走。配对成功写入 `newIndexToNewIndexMap[newIndex - s2] = i + 1`：存旧下标加一，0 保留为哨兵值，表示该新节点没有旧对应、待挂载。`maxNewIndexSoFar` 记录目前最大的新下标，配对序列的新下标一旦回退即说明相对顺序被打乱，`moved` 置真；顺序未乱时整段都不需要移动，第 5.3 步的 LIS 也无需计算。

配对完成后，第 5.3 步从后往前统一挂载与移动：

```ts
// packages/runtime-core/src/renderer.ts —— patchKeyedChildren 第 5.3 步（节选）
// 移动 + 挂载：只有 moved 才算 LIS；从后往前，用「后一个已就位的节点」当锚点
const increasingNewIndexSequence = moved ? getSequence(newIndexToOldIndexMap) : EMPTY_ARR
j = increasingNewIndexSequence.length - 1
for (i = toBePatched - 1; i >= 0; i--) {
  const nextIndex = s2 + i
  const nextChild = c2[nextIndex] as VNode
  const anchor = nextIndex + 1 < l2 ? (c2[nextIndex + 1] as VNode).el : parentAnchor
  if (newIndexToOldIndexMap[i] === 0) {
    // 新节点 → 挂载
    patch(null, nextChild, container, anchor, parentComponent)
  } else if (moved) {
    // 不在 LIS 里的节点才需要移动
    if (j < 0 || i !== increasingNewIndexSequence[j]) {
      move(nextChild, container, anchor)
    } else {
      j--
    }
  }
}
```

三种情况：映射值为 0（新节点）执行 `patch(null, ...)` 挂载；下标在 LIS 中则不动、`j--`；不在 LIS 中才 `move`（对组件递归移动其 subTree，对 Fragment 依次移动首锚点、子节点、尾锚点）。锚点取 `c2[nextIndex + 1].el`——新序列中右邻节点的真实 DOM，它在此前一轮已就位，`insert` 把当前节点放到它之前；最右侧节点没有右邻，退回父级锚点 `parentAnchor`。

最长递增子序列（longest increasing subsequence, LIS）为什么使移动最少，可以严格表述：保持不动的节点必须维持原有相对顺序，它们在 `newIndexToOldIndexMap` 中对应的旧下标序列必须严格递增；反过来，任何递增子序列都可以整体不动。设乱序区共 n 个节点、选出长度 k 的递增子序列保持不动，需要移动的是 n − k 个；k 取到最大（即 LIS）时移动数取到最小。`getSequence`（`packages/runtime-core/src/sequence.ts`）是耐心排序（patience sorting）思想的 O(n log n) 实现：`result` 数组维护「每种长度的递增子序列的最小尾元素下标」，天然递增；新元素大于尾则追加并记前驱 `p[i]`，否则二分定位第一个不小于它的位置替换——替换只让同长度的尾更小，为后续元素留出扩展机会；`result` 经替换后不再对应一条真实子序列，最后沿 `p` 前驱链回溯还原。`arrI !== 0` 跳过哨兵值：新节点没有旧下标，不参与「旧相对顺序」的计算。这份实现与官方逐行一致——官方 3.5 将它内联在 `runtime-core/src/renderer.ts` 的 `getSequence`，更早版本位于独立的 `sequence.ts`。

遍历为什么从后往前：`insert` 的锚点语义是「插到 anchor 之前」，依赖右邻节点已经就位。从后往前时 `c2[nextIndex + 1]` 恰是上一轮处理完的节点；从前往后则锚点自身尚未移动，插入位置会错。第 3 步纯新增的挂载同理取「下一个节点」作锚点。

## 五、事件缓存：invoker

事件处理函数是 props 中更新最频繁的一类：每次渲染都生成新的内联箭头函数，引用每次都不同。朴素做法是 patch 时先 `removeEventListener` 旧函数、再 `addEventListener` 新函数，每次更新两次 DOM 调用。事件缓存（event invoker cache）把「真正注册的监听器」与「用户的处理函数」分离：监听器只注册一次，更换的只是它被调用时取哪个函数。

```ts
// packages/runtime-dom/src/patchProp.ts（节选）
const veiKey = '__vei'
function patchEvent(el: any, rawName: string, _prevValue: unknown, nextValue: unknown) {
  const invokers = el[veiKey] || (el[veiKey] = {})
  const existingInvoker = invokers[rawName]
  if (nextValue && existingInvoker) {
    existingInvoker.value = nextValue    // patch：只换值，零 DOM 操作
  } else {
    const name = parseName(rawName)
    if (nextValue) {
      const invoker = (invokers[rawName] = createInvoker(nextValue))
      el.addEventListener(name, invoker)
    } else if (existingInvoker) {        // remove
      el.removeEventListener(name, existingInvoker)
      invokers[rawName] = undefined
    }
  }
}
function createInvoker(initialValue: unknown) {
  const invoker: any = (e: Event) => {
    const value = invoker.value          // 调用时永远拿最新版 handler
    if (isArray(value)) value.forEach((h) => h && h(e))  // 数组 = 多个监听器
    else if (value) value(e)
  }
  invoker.value = initialValue
  return invoker
}
```

机制的关键在引用与读取的时机。`el.__vei`（vue event invokers）是缓存在元素上的调用器表，按原始属性名（如 `onClick`）索引；首次绑定时创建 invoker 并注册，此后 patch 命中 `existingInvoker` 分支只做 `existingInvoker.value = nextValue`——纯内存赋值，零 DOM 调用。invoker 被事件触发时才读取 `invoker.value`，永远拿到最近一次 patch 的版本；值可以是数组，对应合并出的多个处理函数，逐个调用。新值为空且存在旧 invoker 时才真正解绑并把表项置 `undefined`。该机制与官方 `packages/runtime-dom/src/modules/events.ts` 的实现同构，差异见下节。

## 六、与官方实现的差异

- **Teleport/Suspense 未实现**：`patch` 的 switch 没有对应分支，`ShapeFlags` 保留了 `TELEPORT`/`SUSPENSE` 位但无消费者；官方为两者实现了完整的挂载与更新协议。
- **无 hydration**：`createRenderer` 只产出客户端渲染路径；官方另有 `createHydrationRenderer`，在服务端渲染产出的 DOM 上做复用式挂载。
- **调度细节**：官方 3.5 把 pre 作业并入主队列、以 `PRE` 位与渲染作业统一排序（保证同一组件的 pre watcher 紧贴其更新执行），本工程用独立的 `pendingPreFlushCbs` 数组；官方组件作业绑定 `effect.runIfDirty`（结合副作用脏检查做二次去重），并带 `RECURSION_LIMIT = 100` 递归上限与以 `DISPOSED` 位跳过已废弃作业的机制，本工程仅保留 `QUEUED` 位去重。
- **渲染副作用的归属**：官方在 `setupRenderEffect` 中以 `instance.scope.on()/off()` 包裹渲染副作用的创建，使其登记在实例作用域下；本工程的渲染副作用创建于作用域激活窗口之外，卸载时 `scope.stop()` 只停止 setup 期创建的副作用。
- **patchProp 的组织**：官方拆分为 `modules/` 下五个文件，事件名解析支持 `.capture`/`.passive` 等修饰符并缓存解析结果（作为 `addEventListener` 第三参）；本工程单文件实现，`parseName` 简化为去 `on` 前缀转小写，不支持修饰符，`__vei` 键为字符串而非 Symbol。
- **LIS 无简化**：`sequence.ts` 的 `getSequence` 与官方实现逐行一致。

一个可运行的最小验证（浏览器环境，页面已有 `<div id="app"></div>`）：

```ts
import { createApp, h, ref } from '@mini-vue/runtime-dom'

const App = {
  setup() {
    const list = ref([{ k: 1, t: 'A' }, { k: 2, t: 'B' }, { k: 3, t: 'C' }, { k: 4, t: 'D' }])
    const rotate = () => { list.value = [...list.value.slice(1), list.value[0]] }
    return { list, rotate }
  },
  render(ctx: any) {
    return h('div', [
      h('button', { onClick: ctx.rotate }, 'rotate'),
      h('ul', ctx.list.map((item: any) => h('li', { key: item.k }, `${item.t}-${item.k}`))),
    ])
  },
}
createApp(App).mount('#app')
```

预期行为：点击按钮，列表由 `A-1 B-2 C-3 D-4` 变为 `B-2 C-3 D-4 A-1`，更新经调度队列在微任务中完成。观察分两步：先在 DevTools 中给第一个 `li` 设置 `el.setAttribute('data-mark', '1')`，点击 rotate 后带 `data-mark` 的节点出现在列表末尾——该节点被移动而非销毁重建，此例中 keyed diff 恰好只对 A 执行一次 `move`，B、C、D 原地不动。作为对照，去掉 `h('li', ...)` 的 `key` 后重复操作：四个 `li` 全部原地保留、文本被逐个改写，节点身份跟随位置而非数据——列表项一旦携带本地状态（如输入框的值）就会错位，这正是官方文档要求 `v-for` 必须提供 key 的原因。

## 小结

渲染器是声明式框架内部的命令式层：vnode 以纯数据描述 UI、充当跨平台协议，`createRenderer` 以依赖注入接收宿主操作集，`runtime-dom` 只是用 `nodeOps` 与 `patchProp` 组装出浏览器实现。分发靠 shapeFlag 位图与五路 switch；类型或 key 不匹配时先取锚点再卸载，保证参照节点在卸载后仍然有效。组件实例把渲染副作用（`instance.update = effect(componentUpdateFn, { scheduler })`）、实例作用域（setup 期副作用随卸载整体停止）、调度队列（`QUEUED` 去重、uid 升序保证父先于子、微任务批量 flush、活引用消费执行期间的新作业）装配为一体，`nextTick` 直接挂在这条刷新 promise 上。键控比对五步消化前缀、后缀与纯增删，乱序区以 `newIndexToOldIndexMap`（旧下标加一、0 为哨兵）与 moved 判定收敛问题，LIS 把必须移动的节点数压到下限，从后往前的遍历让插入始终有就位的锚点。事件缓存以 invoker 换值不换监听器，把最高频的一类 props 更新变成纯内存操作。
