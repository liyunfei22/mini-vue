# 12 · 内置能力补全：Options API、Transition、KeepAlive 与 v-model

11 篇结尾把编译器的闭环收了口：补丁标记、区块、静态提升，模板里「哪里会变」已经能一路传进 patch。到这里，三条主线全部打通，内核只剩最后一批「日常可用」的能力，本章一次补齐。

先摆出四个问题。Vue 2 写法的 data/computed/methods 怎么和 setup 共存，同名时听谁的？动画的起始样式必须在元素插入前生效、终态又要等下一帧，这两个时机嵌在渲染器的哪里？组件切走又切回，内部状态凭什么还在？一行 `<input v-model="msg">` 里到底发生了什么？四组能力的实现方式同源：都在既有内核上开小口，不推翻已有结构。

## 12.1 Options API：另一种书写面

先看目标形态，一个两种 API 混用的组件：

```ts
// 导入均来自 @mini-vue/vue（template 选项依赖聚合包注册的运行时编译器，jsdom 环境）
import { createApp, ref } from '@mini-vue/vue'
const container = document.createElement('div')
createApp({
  setup() {
    const count = ref(999)                // setupState：组合式一侧
    return { count }
  },
  data() {
    return { count: 0, other: 'x' }       // data：选项式一侧，count 同名
  },
  computed: {
    label() { return this.other + '!' },  // this 走公共代理，读到 data.other
  },
  template: `<p>{{ count }}:{{ other }}:{{ label }}</p>`,
}).mount(container)
// 实测：container.innerHTML === '<p>999:x:x!</p>'
```

三处读取各有来路：count 命中 setupState，other 与 label 落到 data，label 里的 this.other 经代理转回 data。两套 API 互不打架，靠的是固定执行顺序加统一命名空间，顺序的落点在 setupStatefulComponent：

```ts
// packages/runtime-core/src/component.ts —— setupStatefulComponent（节选）
instance.proxy = new Proxy(instance.ctx, PublicInstanceProxyHandlers)
// ……（setup 先执行并归一化返回值，08 篇已走读）

// Options API 追加：setup（Composition）之后合并 data/computed/methods/watch/生命周期选项
if (isOptionComponent(Component)) {
  applyOptions(instance, Component)
}
```

proxy 在 setup 之前创建，选项里的函数因此都以它为 this。isOptionComponent 检测到任一选项存在才调 applyOptions，这个顺序带来一个反直觉的事实：选项式的 beforeCreate 与 created 在 applyOptions 内执行，实际晚于 setup。

这张快照只有 data 与 computed，把 methods 与 watch 也接进来凑一张全家福（实测）：

```ts
// 沿用上面那份组件扩展，导入均来自 @mini-vue/vue（jsdom 环境）
const watched: string[] = []
createApp({
  setup() {
    const count = ref(999)                 // setupState 一侧
    return { count }
  },
  data() {
    return { count: 0, other: 'x' }        // data 一侧，count 同名
  },
  computed: {
    label() { return this.other + '!' },   // this.other 经代理读 data
  },
  methods: {
    upperOther() { return this.other.toUpperCase() },  // 挂进 data、绑定 proxy
    rename() { this.other = 'y' },         // set 拦截：落点与读取同链
  },
  watch: {
    other(v: string, ov: string) { watched.push(`${ov}->${v}`) },
  },
  template: `<p @click="rename">{{ count }}:{{ other }}:{{ label }}:{{ upperOther() }}</p>`,
}).mount(container)
// 实测：container.innerHTML === '<p>999:x:x!:X</p>'
// 点击 p 再 nextTick：container.innerHTML === '<p>999:y:y!:Y</p>'，watched === ['x->y']
```

逐条走读这次多出来的两条通道。methods 在 applyOptions 里逐个 `bind(proxy)` 后挂进 instance.data，模板里的 `upperOther` 经代理的 data 级命中，方法体里的 this.other 再走一遍同一条 get 链——setupState 里那个 999 的 count 全程没被碰到。`rename` 写 `this.other = 'y'`，set 拦截沿 setupState、data、ctx 找落点：setupState 只有 count，other 落到 data，reactive 容器随即触发更新。watch 选项最终订阅的 getter 是 `() => proxy['other']`，改值时回调收到 `'x->y'`——数组里旧值在前只是拼接顺序，参数序仍是新值在前，与组合式 watch 一致。computed 的 label 依赖 data.other，改值后重算为 'y!'。四条通道一次点击全部联动，没有一条推翻 setup 打下的结构。

写入这条路的源码只有几行，与 get 拦截同住一个文件：

```ts
// packages/runtime-core/src/componentPublicInstance.ts —— set 拦截（节选）
set({ _: instance }, key: string, value): boolean {
  const { ctx, setupState, data } = instance

  if (setupState !== EMPTY_OBJ && hasOwn(setupState, key)) {
    setupState[key] = value
    return true
  } else if (data !== EMPTY_OBJ && hasOwn(data, key)) {
    data[key] = value
    return true
  } else if (ctx !== EMPTY_OBJ && hasOwn(ctx, key)) {
    ctx[key] = value
  }
  return true
}
```

两处细节读出来。其一，set 的候选链没有 props——props 对消费者只读，写入不会静默落到 props 上，最多悄悄落到 ctx 或干脆丢弃。其二，get 与 set 的链基本对称，`rename` 里的 this.other 读与写命中同一格 data.other；假如名字换成 count，读会命中 setupState 的 ref、写也命中 setupState，999 与 0 两个同名值各自守着自己的领地，读写不会串门。

那怎么合并？最朴素的想法是把选项直接 Object.assign 进 setupState。很明显，这样做还差得远：data 没有 reactive 化，改了不触发更新；methods 的 this 是 undefined，方法体里读 this.count 当场报错；computed 与 watch 没人处理，同名键靠并序互相覆盖，谁赢全凭书写顺序。仓库版 applyOptions 逐条解决：

```ts
// packages/runtime-core/src/componentOptions.ts —— applyOptions（节选）
// ---- data：reactive 化（无 data 也保持容器，method/computed 挂载用）----
if (options.data) {
  instance.data = reactive(options.data.call(proxy, proxy) as Data)
} else if (instance.data === EMPTY_OBJ) {
  // EMPTY_OBJ 是共享冻结空对象，不能往上面挂 method/computed（dev 下写会抛 TypeError、
  // 非 dev 下会把所有无 data 组件的方法写进同一个单例造成跨组件串数据）；
  // 这里换成每实例独立的空对象。
  instance.data = {}
}

// ---- methods：绑定 this=proxy ----
// ……（逐个 instance.data[key] = options.methods[key].bind(proxy)，
//      方法体里的 this.count 因此走完整代理链）

// ---- computed：转换进 instance.data（读时解包由 reactive getter 完成）----
// ……（getter/setter 经闭包绑到 proxy 后挂入 instance.data，读取靠 reactive 容器
//      对 ref 的解包返回裸值；watch/生命周期分支见源码）
```

这段守卫还记着一次真实的崩溃。instance.data 的初始值是共享的冻结空对象 EMPTY_OBJ：组件不写 data() 选项时，methods 会往这个冻结对象上挂方法，dev 下当场 TypeError。非 dev 下更糟，所有无 data 组件的方法写进同一个单例，跨组件串数据。修法就是上面那个 else if，发现 data 还是 EMPTY_OBJ 就换成每实例独立的新对象，optionsApi.spec.ts 的 no frozen EMPTY_OBJ crash 一例锚定着修复结果。

模板读 this.x 走公共代理，get 拦截按固定优先级裁决：

```ts
// packages/runtime-core/src/componentPublicInstance.ts —— get 拦截（节选）
// 访问优先级：setupState → props → data → ctx → $内建 → app.config.globalProperties
if (setupState !== EMPTY_OBJ && hasOwn(setupState, key)) {
  return setupState[key]
} else if (props !== EMPTY_OBJ && hasOwn(props, key)) {
  return props[key]
} else if (data !== EMPTY_OBJ && hasOwn(data, key)) {
  return data[key]
} else if (ctx !== EMPTY_OBJ && hasOwn(ctx, key)) {
  return ctx[key]
}
// ……（$slots/$attrs/$emit 等内建与 globalProperties 分支见源码）
```

四级依次是 setupState、props、data、ctx，之后才是内建与 globalProperties。同名冲突因此有确定语义：setup 返回的 count 遮蔽 data 的同名 count，开头示例里的 999 正是这么来的。为什么用 hasOwn 而不是 in？因为 in 会命中原型链，把 Object.prototype 的键也当成组件状态。set 拦截沿同一条链回写（props 不可写），写入落点与读取一致。

watch 与生命周期选项不再建新设施。watch 的键名可能是 'a.b.c' 这类路径，createPathGetter 把它编译成按段取值的 getter，最终与组合式的 watch() 落进同一个 doWatch，immediate 与 deep 原样透传。生命周期选项里，beforeCreate 与 created 没有对应的渲染时机、当场同步执行；其余经 injectHook 登记进实例钩子数组，与 setup 里 onMounted 写的是同一个数组。

书写面补齐了。下一节把目光从「怎么写」移到「什么时候写」：动画的两个关键时机，恰好卡在渲染器最敏感的节点上。

## 12.2 Transition：渲染器开的三个时机

进入动画有一个结构性矛盾。起始样式（比如 opacity 为 0）必须在元素插入文档之前生效，否则浏览器先渲染一帧终态，动画从第二帧才开始。而切换到终态又必须等插入之后的下一帧：元素还没站稳就移除起始类，浏览器会把两次变更合并成一次，过渡直接跳过。一个时机在插入前、一个在插入后，全都嵌在渲染器的挂载流程里。

组件自己进不去渲染器，那就反过来让渲染器开口。Transition 是一个不渲染任何东西的包装组件：setup 取插槽的唯一元素子节点，把钩子挂上 vnode.transition 字段就原样返回它。渲染器只在三处读这个字段：

```ts
// packages/runtime-core/src/renderer.ts —— mountElement 与 unmount 的过渡开放点（节选）
// Transition：insert 前挂 enter-from 类
vnode.transition && vnode.transition.beforeEnter(el)
hostInsert(el, container, anchor)
// Transition：insert 后触发 enter 动画
vnode.transition && vnode.transition.enter(el)

// unmount 的元素分支：
if (doRemove) {
  if (vnode.transition && vnode.transition.leave) {
    // Transition：动画结束后才真正移除
    vnode.transition.leave(vnode.el, () => {
      invokeDirectiveHook(vnode, null, parentComponent, 'unmounted')
      hostRemove(vnode.el)
    })
  } // 无 transition 字段时直接 hostRemove
}
```

挂载侧两个口夹住 hostInsert：beforeEnter 在插入前调用，类挂在尚未进文档的元素上，插入瞬间起始样式已经生效；enter 在插入后调用，负责切终态。卸载侧一个口：leave(el, done) 把真正的 hostRemove 推迟到 done 回调，动画结束前元素一直留在文档里。vnode 上没有 transition 字段时三处都是空操作，普通挂载零成本。

钩子内部做什么？六个类名的添加与移除全在 createTransitionHooks：

```ts
// packages/runtime-core/src/components/Transition.ts —— createTransitionHooks（节选）
const classNames = {
  enterFrom: `${prefix}-enter-from`,
  enterActive: `${prefix}-enter-active`,
  enterTo: `${prefix}-enter-to`,
  // ……（leave 侧三个类名对称）
}
return {
  beforeEnter(el: HTMLElement) {
    el.classList.add(classNames.enterFrom, classNames.enterActive)
  },
  enter(el: HTMLElement) {
    // ……（done：动画结束后清掉三个类）
    nextFrame(() => {
      el.classList.remove(classNames.enterFrom)
      el.classList.add(classNames.enterTo)
      whenTransitionEnds(el, done, duration)
    })
  },
  // ……（leave 对称：立即加 leaveFrom/leaveActive，nextFrame 后切 leaveTo，结束后清类并调 done）
}
```

prefix 取 props.name（默认 'v'），duration 取 props.duration（默认 300 毫秒）。对照官方文档的时序表：

| 类名 | 添加时机 | 移除时机 |
|---|---|---|
| `v-enter-from` | 元素插入前 | 插入后的下一帧 |
| `v-enter-active` | 元素插入前 | 过渡或动画结束 |
| `v-enter-to` | 插入后的下一帧 | 过渡或动画结束 |
| `v-leave-from` | 离开触发时 | 下一帧 |
| `v-leave-active` | 离开触发时 | 过渡或动画结束 |
| `v-leave-to` | 离开触发的下一帧 | 过渡或动画结束 |

beforeEnter 对应前两行的添加列，enter 里 nextFrame 之后的两行对应「移除 from、添加 to」，与表格逐格对上。

**一次 enter 从头到尾逐帧实测。** 时序表是文档视角，再补一张机器视角的表。条件取 `duration="30"`，挂载 `<div><Transition :duration="30"><p v-if="show">x</p></Transition></div>`，在各时间点读元素的 className（实测；打点方式见章末「动手验证」）：

| 时刻 | 元素的 class（实测） | 此刻挂着的定时器与回调（对照源码） |
|---|---|---|
| insert 之前 | `v-enter-from v-enter-active` | beforeEnter 已执行、元素尚未进文档，enter 还没被调 |
| 挂载同步返回（t0） | 同上 | enter 已执行：nextFrame 排下双 setTimeout，from 与 to 都还没动 |
| 双 setTimeout 跑完 | `v-enter-active v-enter-to` | from 已移除、to 已加上；transitionend 监听与 30ms 超时在等 done |
| 超时触发后（实测 t0+70ms 已完成） | 空 | done 已执行：三个类一起移除，无遗留定时器 |

前两行的 class 相同、含义不同：从 beforeEnter 到 hostInsert 之间，类挂在离体元素上，插入瞬间起始样式已经生效，浏览器画的第一帧就是 from 态。第三行是「下一帧」语义的兑现：双 setTimeout 对齐官方的双 requestAnimationFrame，表达「等起始帧画完再切终态」；同帧内既加 from 又移 from，浏览器会把两次变更合并成无过渡，nextFrame 隔开的就是这一步。末行的收尾在源码里是一句 `el.classList.remove(enterTo, enterActive, enterFrom)`：正常路径 from 早已不在，那个 enterFrom 是给异常路径的兜底。jsdom 没有真实过渡，实测全程靠 30ms 超时触发 done；真实浏览器里通常先等来 transitionend，超时只是保险。

动画什么时候算结束？官方文档说结束检测监听根元素的 transitionend 与 animationend；本实现只监听 transitionend，再加超时兜底：

```ts
// packages/runtime-core/src/components/BaseTransition.ts —— nextFrame（节选）
export function nextFrame(cb: () => void) {
  // jsdom 无真实 rAF 压力：统一用双 setTimeout 近似「下一帧」
  setTimeout(() => {
    setTimeout(cb, 0)
  }, 0)
}
// 同文件 whenTransitionEnds：transitionend 监听与 duration 超时双保险，resolved 只生效一次
```

兜底为什么必须有？因为测试跑在 jsdom 里，没有真实的 CSS 过渡，transitionend 永远不来；没有超时，done 就永远不被调用、元素永远不被移除。nextFrame 的双 setTimeout 同理：官方用双 requestAnimationFrame 表达「下一帧」，jsdom 没有真实帧率，双 setTimeout 是可用的近似。

下一节处理更极端的「移除」：不是延迟移除，而是根本不移除。

## 12.3 KeepAlive：隐藏代替卸载

官方文档对 KeepAlive 的描述是「缓存组件实例」，被切换掉的组件「变为不活跃状态而不是被卸载」。卸载在 08 篇意味着什么？scope.stop() 停掉全部副作用、DOM 移除、状态清空。KeepAlive 要对抗的正是这条路径。

先看朴素做法的边界。v-if 切走即卸载，状态丢失；把状态搬到组件外面确实保得住：

```js
// —— 手写朴素版，仅用于演示 ——
const saved = { count: 0 }            // 状态搬到外面
const A = {
  data() { return saved },            // 借 data 还原
  template: `<p>{{ count }}</p>`,
}
// 状态保住了，但它离开了组件：谁都能改、回收靠自觉；缓存十个组件就得备十个盒子
```

很明显，这不是机制，是手工搬运。仓库版用一个缓存 Map 加两个私有标记，把「卸载」改写成「隐藏」：

```ts
// packages/runtime-core/src/components/KeepAlive.ts —— setup（节选）
export const KeepAlive = {
  name: 'KeepAlive',
  setup(_props: Record<string, any>, { slots }: any) {
    const cache = new Map<any, any>() // key → 缓存的 vnode（含 component 实例）

    return () => {
      // ……（取插槽首个子节点并归一化得 child）
      const key = child.key != null ? child.key : child.type
      const cachedVNode = cache.get(key)

      if (cachedVNode && cachedVNode.component) {
        // 回魂：返回缓存 vnode（同一实例），标记为「需要激活」
        child = cachedVNode
        child._activate = true
      } else {
        cache.set(key, child)
      }
      // 当前渲染的这个子组件，若被换掉 → 隐藏（renderer 读 _deactivate 字段拦截卸载）
      child._deactivate = true
      return child
    }
  },
}
```

先走读这个渲染函数：当前子组件以 key 为身份入缓存，key 取显式的 vnode.key，缺省用组件类型；再次渲染时缓存命中且实例还在，就返回缓存中的同一个 vnode 并置 _activate；不管命中与否，当前孩子一律挂 _deactivate。两个标记由渲染器解释：

```ts
// packages/runtime-core/src/renderer.ts —— processComponent 与 unmount 的 KeepAlive 分支（节选）
// processComponent 的挂载入口：
if (n1 == null) {
  // KeepAlive 回魂：缓存实例还在 → 显示 + 刷新，不重跑 setup
  if ((n2 as any)._activate && n2.component) {
    const instance = n2.component
    const rootEl = instance.subTree && instance.subTree.el
    if (rootEl) hostShowNode(rootEl)
    ;(n2 as any)._activate = undefined
    instance.update()
    return
  }
  mountComponent(n2, container, anchor, parentComponent)
} // else 走 updateComponent（08 篇）

// unmount 的组件分支：
if (shapeFlag & ShapeFlags.COMPONENT) {
  // KeepAlive：带 _deactivate 标记 → 隐藏而非卸载
  if ((vnode as any)._deactivate && vnode.component) {
    const rootEl = vnode.component.subTree && vnode.component.subTree.el
    if (rootEl) hostHideNode(rootEl)
    return
  }
  unmountComponent(vnode.component!, parentComponent)
}
```

unmount 见到 _deactivate，取组件根元素执行 hostHideNode 后直接 return，unmountComponent 与它的 scope.stop() 整个被跳过，DOM 留在原地；hostHideNode 由 runtime-dom 注入，实现是 style.display 置 'none'。切回时 processComponent 见到 _activate：显示根元素、复位标记、调 instance.update() 刷新。关键在这是「显示加刷新」而不是重新挂载：实例还是缓存里的那一个，setup 不执行第二次，data 与内部状态原样保留。

为什么不重跑 setup 也能刷新？因为渲染副作用当初只是被藏了起来、从未停止，instance.update() 拉它重跑，子树照常重建。transitionKeepAlive.spec.ts 的断言钉住两端：切到 B 后 A 的根元素 display 为 'none'；切回 A 后 span 文本仍是切走前的 1，display 复原。

**A 到 B 再回 A，三次渲染逐次列账。** A 内部带 data 计数与自增按钮，B 是另一个组件，外层 `<KeepAlive><component :is="cur"/></KeepAlive>`。逐次实测（取 child vnode 的路径是 `container._vnode.component.subTree.component.subTree`，即根组件 → KeepAlive → 它渲染的 child）：

| 渲染次 | cur | child vnode 身份 | data() 调用数（A/B） | A 的 display | A 的 span | 容器 DOM 摘要（实测） |
|---|---|---|---|---|---|---|
| 第 1 次 | A | 新建 vnode，以 A 为 key 进缓存 | 1 / 0 | ''（可见） | 0 | 只有 A 的 div |
| （点击 +） | A | — | 1 / 0 | '' | 1 | A 内部更新，缓存无感 |
| 第 2 次 | B | 新建 vnode，B 以自身为 key 进缓存 | 1 / 1 | 'none' | 1 | A 的 div 带 display:none 在前，B 的 div 在后 |
| 第 3 次 | A | 与第 1 次同一个 vnode 对象 | 1 / 1 | ''（复原） | 1 | A 复原在前，B 变成 display:none 在后 |

表里有三条证据链。其一，data() 调用数停在 1/1：A 回魂没有创建新实例，applyOptions 与 data 初始化都不再执行，setup 同理只跑一次——「隐藏代替卸载」省掉的就是这一整套重建。其二，第 3 次的 child vnode 与第 1 次是同一个对象（实测严格相等为 true），这正是「缓存命中返回 cachedVNode」的直接体现；B 的 vnode 是另一个对象，与 A 的永不相等。其三，A 的根 DOM 元素跨三次渲染是同一个节点（实测同引用），display 在 none 与空串之间摆动，DOM 从未离开容器，状态自然一分不少。

两个私有字段在表外的读数也实测过：每次渲染后 child 的 `_deactivate` 都是 true（KeepAlive 每渲染一个孩子就挂一次），`_activate` 在任何渲染完成后读到都是 undefined——它只在命中缓存的渲染瞬间为 true，渲染器消费完立刻复位。想亲眼看这个瞬间，得在 processComponent 的激活分支里打断点，字段的生命周期比一次渲染还短。

最后一节拆开那行最常用的语法糖。

## 12.4 v-model：编译期展开的语法糖

v-model 在官方文档里是一张矩阵：按元素类型分派「绑定属性 + 监听事件」。不用指令也能写，`<input :value="msg" @input="msg = $event.target.value" />` 就是完整展开式。问题在形态各异：checkbox 要绑 checked，select 要监听 change，每个输入都写两遍且容易记错矩阵。v-model 把矩阵挪进编译器，书写面收敛成一行：

| 元素 | 绑定属性 | 监听事件 |
|---|---|---|
| 文本类 `input` / `textarea` | `value` | `input` |
| `checkbox` / `radio` | `checked` | `change` |
| `select` | `value` | `change` |

文本形态在编译期内联，先看两份实测产物：

```js
// compile('<input v-model="msg" />').code（实测产物，换行略作整理）
const { createElementVNode: _createElementVNode, openBlock: _openBlock,
        createElementBlock: _createElementBlock } = Vue
return function render(_ctx, _cache) {with (_ctx) {
    return _openBlock(), _createElementBlock("input",
      {value: msg, onInput: ($event) => (msg = $event.target.value)},
      null, 8, ["value", "onInput"])
  }
}

// compile('<input v-model.lazy.number="msg" />').code（实测产物，节选）
// {value: msg, onChange: ($event) => (msg = _looseToNumber($event.target.value))}
// 补丁标记同为 8（PROPS 位），名单变为 ["value", "onChange"]
```

v-model 被拆成一对属性：value 绑定模型，onInput 回写；修饰符只改这两个表达式：.lazy 把 onInput 换成 onChange，同步推迟到 change 事件；.number 在取值外包一层 _looseToNumber，内部是 parseFloat，解析失败返回原值；.trim 变成 $event.target.value.trim()，去掉两端空格。名单是内联之外的关键一笔：生产端在 transformElement 的文本分支，把 value 与事件名登进 dynamicProps（源码注释记着漏登的后果——PROPS 位置了却什么都不比，程序化改模型不驱动输入框回显）。为什么程序化改模型也要驱动输入框？因为 v-model 承诺的是双向：用户输入经事件回写模型，程序化改模型经第 11 篇的名单 diff 把输入框回显，名单缺一不可。

三种形态的产物并排对照（每一格都是实测 compile 输出）：

| 形态 | 模板 | 产物核心（实测） | patchFlag / 名单（实测） |
|---|---|---|---|
| 文本 | `<input v-model="msg" />` | `{value: msg, onInput: ($event) => (msg = $event.target.value)}` | 8 / `["value", "onInput"]` |
| checkbox | `<input type="checkbox" v-model="ok" />` | `_withDirectives(_createElementVNode("input", {type: "checkbox", checked: ok}, null, 8), [[_vModelCheckbox, ($event) => (ok = $event), "", ""]])` | 8 / 无名单 |
| select | `<select v-model="sel">`（含两个静态 option） | `_withDirectives(_createElementVNode("select", {value: sel}, [option, option], 8), [[_vModelSelect, ($event) => (sel = $event), "", ""]])` | 8 / 无名单 |

表里藏着一组关键对照：文本形态登记了名单，程序化改模型靠第 11 篇的名单 diff 回显；两种指令形态 patchFlag 同样是 8，名单却是空的——properties 只写了 checked 或 value，名单一个键都没登记。程序化改模型时靠什么同步元素？靠指令的 updated 钩子：渲染器在 patchElement 的末尾调 invokeDirectiveHook('updated')，vModelCheckbox 与 vModelSelect 的 updated 都执行「把 props 写成元素状态」的同步。PROPS 位对着空名单循环零次，同步的活全被指令接管。同一个回显承诺，文本形态走名单、指令形态走钩子，两条路在表里各占一列。

checkbox/radio/select 不内联，编译为 withDirectives 包裹的运行时指令，checkbox 的实测产物是 `_withDirectives(_createElementVNode("input", {type: "checkbox", checked: ok}, null, 8), [[_vModelCheckbox, ($event) => (ok = $event), "", ""]])`。checked 走 props，回写走指令第二项的 assigner。指令本体在 runtime-dom：

```ts
// packages/runtime-dom/src/directives/vModel.ts —— vModelCheckbox（节选）
export const vModelCheckbox: ObjectDirective<any> = {
  created(el, { value: assign }, vnode) {
    el._assigning = true
    el.addEventListener('change', () => {
      if (!el._assigning && assign) {
        // 单一布尔模型：checked 直接回写
        assign(el.checked)
      }
    })
    el._assigning = false
  },
}
// mounted / updated 均调 setChecked：置 _assigning 后把 props.checked/value 写成元素状态
```

_assigning 防的是两条通道打转：程序化写 el.checked 时若浏览器补发 change，handler 见到标记就跳过，回写循环被掐断。radio 的选中判断用 looseEqual 宽松相等，模型 'a' 与 value 1 也能配上；select 同法，value 写入元素、change 读回。四个开头的问题至此全部有答。

## 本章小结

Options API 以固定顺序接入：setup 先执行，applyOptions 把 data/computed/methods 统一落进 reactive 化的 instance.data，公共代理按 setupState→props→data→ctx 裁决同名，setup 赢。Transition 不渲染自身，把钩子挂上 vnode.transition，渲染器在插入前后与卸载三处读它，六类名时序由 transitionend 加超时兜底收尾。KeepAlive 以缓存 Map 与两个私有标记把卸载改写为隐藏，切回时显示并调 instance.update() 刷新，setup 不跑第二次。v-model 是编译期展开的语法糖：文本形态内联为 value 加事件，checkbox/radio/select 走运行时指令双向同步。

## 与官方实现的差距

以下均经 `third_party/vue-core`（v3.5.x）源码核对：

- **代理优先级与缓存**：官方读取顺序是 setupState → data → props → ctx，且以 accessCache 记忆每个键的来源、省去重复 hasOwn（`runtime-core/src/componentPublicInstance.ts` 的 get，注释自称渲染热点）；本实现是 setupState → props → data → ctx，无缓存。官方 methods 挂在 ctx、computed 经 Object.defineProperty 定义到 ctx（`runtime-core/src/componentOptions.ts`）；本实现统一挂入 reactive 化的 instance.data，computed 读取靠容器的 ref 解包。
- **beforeCreate 时机**：官方在 applyOptions 一开头、data 初始化之前调用 beforeCreate（源码注释引 #2791：钩子可能改写选项），初始化序为 inject → methods → data → computed → watch；本实现先做 data/methods/computed/watch 再调 beforeCreate，钩子里已能读到 this.count。
- **expose**：本实现的 setupContext.expose 是空函数（component.ts），官方会装配实例的暴露面并影响模板 ref 的访问。
- **KeepAlive**：无 include/exclude（按组件 name 过滤）与 max（超限销毁最久未访问的缓存，类 LRU），也无 activated/deactivated 钩子（官方语义：前者在首次挂载与从缓存重新插入时触发，后者在移入缓存与卸载时触发）；官方把停用子树 move 进脱离文档的 div 存储容器，本实现原地 display:none。
- **Transition**：仅单元素子节点与 name/duration 两个属性；无 mode（out-in/in-out）、appear 与 JS 钩子（官方 @enter/@leave 接收 (el, done)）；官方经 getComputedStyle 检出动画类型后监听对应的 transitionend/animationend 并读真实时长，本实现只监听 transitionend、超时用 props.duration 兜底；「下一帧」官方是双 rAF，本实现双 setTimeout 近似。
- **v-model**：官方先经 `compiler-dom/src/transforms/vModel.ts` 把 v-model 重写为普通绑定与事件、再由统一的属性扫描登记，本实现在 transformElement 内分流内联，形态不同结果一致；组件上的 v-model（展开为 :modelValue 与 @update:modelValue）本实现未做。
