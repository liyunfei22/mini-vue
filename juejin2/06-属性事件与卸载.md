# 06 · 属性、事件与卸载：打对补丁，清干净旧账

05 篇末留了三笔欠账：props 还只是「挂载时一口气设满」；事件处理函数每渲染一次都是新引用，朴素绑定会越绑越多；旧节点退场时，除了摘掉 DOM 还有一摊子账没清。本章逐一还账，主角是 05 篇埋下的那行 `hostPatchProp`——`runtime-dom` 侧实现它的 `patchProp.ts`。先把问题摆出来：**`<input disabled>` 和 `el.disabled = true` 是一回事吗？事件处理函数每次渲染都是新函数，为什么监听器不会越绑越多？卸载一个节点，除了摘掉 DOM 还欠着什么？** 做法照旧：先写朴素版，看它翻车，再看仓库如何演进。

## 1.1 属性：attribute 还是 property

05 篇 `mountElement` 的 props 循环里，每个键都调 `hostPatchProp(el, key, null, props[key])`，当时把这行原样略过。现在补上它欠的问题：这一行该怎么把 `key/value` 落到元素上？最直觉的答案是 `setAttribute` 一把梭：

```js
// —— 手写朴素版，仅用于演示 ——
function mountProps(el, props) {
  for (const key in props) {
    el.setAttribute(key, props[key])   // 全部当 attribute 设
  }
}
```

挂在静态元素上没毛病，拿输入框一试就翻车。下面这段在浏览器与 jsdom 里结果一致（本章实验均已验证）：

```js
// —— 手动实验，可直接进控制台 ——
const input = document.createElement('input')
input.setAttribute('value', 'foo')   // 挂载：setAttribute 一把梭
input.value                          // 'foo'：初次 attribute 会同步进 property
input.value = 'user typed'           // 模拟用户输入
input.getAttribute('value')          // 'foo'：attribute 没跟着动
input.setAttribute('value', 'bar')   // 状态变了，再打一次补丁
input.value                          // 'user typed'——property 拒绝回写

const btn = document.createElement('button')
btn.setAttribute('disabled', false)  // false 被转成字符串 'false'
btn.disabled                         // true——attribute 在，就是禁用
```

走读第一段。初次 `setAttribute` 后 property 确实变成 `'foo'`，通道看着是通的；但用户输入改过 property 后，再改 attribute，property 纹丝不动——HTML 规范给 `value` 设了脏值标记（dirty value flag）：交互改过之后，attribute 到 property 的回写被挡住，朴素版的 `:value` 绑定从用户敲第一个字符起失效。第二段是反方向翻车：布尔 attribute 的语义是「出现即生效」，字符串 `'false'` 也算「出现」，元素照样禁用；而 property 赋 `false` 时浏览器会顺手移除 attribute。两条通道的语义完全不对称。

两个实验指向同一组概念。HTML attribute（HTML 属性），写在标签上的名值对，浏览器解析标签时用它**初始化** DOM 对象；DOM property（DOM 属性），DOM 对象身上的 JavaScript 属性，是**活值**，随交互与赋值实时变化。关系基本单向：attribute 多数只同步一次 property，`value` 还带脏值标记；property 变化一般不回写，布尔类是例外。正确的分流因此是：能作为 property 表示的键（`value`、`checked` 这类活值）直接赋值，不能的走 `setAttribute`。仓库的总分发：

```ts
// packages/runtime-dom/src/patchProp.ts —— patchProp 总分发
export const patchProp = (
  el: Element,
  key: string,
  prevValue: any,
  nextValue: any,
) => {
  switch (key) {
    case 'class':
      patchClass(el, nextValue)
      break
    case 'style':
      patchStyle(el, prevValue, nextValue)
      break
    default:
      if (isOn(key)) {
        patchEvent(el, key, prevValue, nextValue)
      } else if (shouldSetAsProp(el, key, nextValue)) {
        patchDOMProp(el, key, prevValue, nextValue)
      } else {
        patchAttr(el, key, nextValue)
      }
  }
}
```

四路分发：`class` 与 `style` 各有专门处理（本节末带过）；`isOn`（`shared` 的工具，判 `on` 后跟大写字母）把事件摘出去交给下一节；剩下的键由 `shouldSetAsProp` 判定走哪路：

```ts
// packages/runtime-dom/src/patchProp.ts —— shouldSetAsProp / patchDOMProp（拼合节选）
function shouldSetAsProp(el: Element, key: string, value: any): boolean {
  return key in el || (domPropsRE.test(key) && value != null)
}

function patchDOMProp(el: Element, key: string, prevValue: any, nextValue: any) {
  try {
    let value = nextValue
    // 布尔 DOM 属性（disabled/selected/muted/multiple…）：空串 → true、null/undefined → false。
    // `<input disabled>` 编译成 disabled: ""，直接赋值会把布尔属性设成 false（对齐真 Vue includeBooleanAttr）
    if ((value === '' || value == null) && typeof (el as any)[key] === 'boolean') {
      value = value === '' ? true : false
    }
    ;(el as any)[key] = value == null ? '' : value
  } catch (e) {
    console.warn(`[mini-vue] error setting prop ${key}`, e)
  }
}
```

`key in el` 沿原型链查：`input` 上查得到 `value`，所以 `:value` 走赋值；`data-id` 查不到，落 attribute；正则 `domPropsRE`（含大写字母的键与五个表单布尔属性）是兜底。为什么 `key in el` 就够用？因为「元素身上有这个 property」等价于「这个键存在活值通道」，赋值即生效。

但「等价」有例外：property 存在，不代表它可写。`'form' in input` 是 true，`form` 却是只读的——第三组实验：

```js
// —— 手动实验，控制台与 jsdom 语义一致 ——
const input = document.createElement('input')
'form' in input             // true：原型链查得到 → shouldSetAsProp 会判它走 property
input.form = 'not-a-form'   // 控制台（宽松模式）静默失败；ES 模块（严格模式）抛 TypeError
input.form                  // null：两种模式下都读回原值，赋值从未生效
```

经 patchProp 走一遍更能看清后果。挂载 `h('input', { form: 'x' })` 时，`shouldSetAsProp` 因 `'form' in input` 命中而选了 `patchDOMProp`，赋值那行在严格模式下抛 TypeError；好在函数体包着 try/catch（上面的节选里就有），实测只打一条 `[mini-vue] error setting prop form` 的警告，attribute 上什么也没落下（`getAttribute('form')` 为 null）。官方实现因此没有把 `key in el` 一条道走到黑：`shouldSetAsProp` 为 `form` 写了显式特判，让它恒走 `setAttribute`（差距节有对照）。

`patchDOMProp` 的布尔归一是第二个实验的教训：`<input disabled>` 编译成 `disabled: ''`，直接赋 `el.disabled = ''` 会被转成 `false`，所以先探测布尔类型再转换；`patchAttr` 最简单——`null`/`false` 移除、`true` 设空串、其余 `setAttribute`。挂载路径 `prevValue` 恒为 `null`，更新路径在 `patchElement`：它对新旧两张 props 表做全量 diff，新表里值变了的键打补丁，旧表里消失的键补 `null`：

```ts
// packages/runtime-core/src/renderer.ts —— patchElement 的 props 更新（节选：删除路径）
        for (const key of Object.keys(oldProps)) {
          if (key !== 'key' && key !== 'ref' && !(key in newProps)) {
            hostPatchProp(el, key, oldProps[key], null)
          }
        }
```

`patchAttr` 的移除、下一节 `patchEvent` 的解绑都靠这个 `null` 触发；编译器的 `patchFlag` 快速路径（第 11 篇）只是让这对循环少跑几圈。`class` 与 `style` 一段带过：取值形态多（字符串/数组/对象混用），`shared/src/index.ts` 的 `normalizeClass`/`normalizeStyle` 先归一，`patchClass` 写 `className`、`patchStyle` 先删「新里没有的旧键」再逐键赋值。

style 值得把「一段带过」兑现成一次完整对照——「字符串切对象」这个方向在仓库开发时真实翻过车。先看全貌：

```ts
// packages/runtime-dom/src/patchProp.ts —— patchStyle（完整）
function patchStyle(el: Element, prev: any, next: any) {
  const style = (el as HTMLElement).style
  if (next == null) {
    el.removeAttribute('style')
  } else {
    const nextStyle = normalizeStyle(next)
    if (typeof nextStyle === 'string') {
      if (nextStyle !== (el as any).__styleString) {
        style.cssText = nextStyle
        ;(el as any).__styleString = nextStyle
      }
      return
    }
    // 对象形态：先删「新里没有的旧键」，再赋新值。prev 是字符串时也解析成对象统一清。
    if (prev) {
      const prevStyle = normalizeStyle(prev) as Record<string, any>
      for (const key in prevStyle) {
        if (!(key in nextStyle)) {
          style.removeProperty(key)
        }
      }
    }
    for (const key in nextStyle) {
      const value = nextStyle[key]
      if (value != null) {
        style.setProperty(key, String(value))
      } else {
        style.removeProperty(key)
      }
    }
  }
}
```

两形态两套路数。next 归一后是字符串，`cssText` 整串替换，`__styleString` 记下本串、同串再写直接跳过；是对象，先删后赋，删除的依据是 prev 归一后的键集。翻车点就在「prev 归一」这一步：修复提交（f84f896）之前这里写的是 `if (prev && typeof prev !== 'string')`，prev 是字符串时整个删除循环被跳过——字符串形态遗留的旧样式原样残留。

实测一次完整往返（jsdom，临时 spec 已验证）：

```ts
const mode = ref('str')
createApp({
  render: () => h('div', {
    style: mode.value === 'str' ? 'color:red;font-size:12px' : { color: 'blue' },
  }, 'x'),
}).mount(container)
mode.value = 'obj';  await nextTick()   // 字符串 → 对象
mode.value = 'str';  await nextTick()   // 对象 → 字符串
```

```text
挂载（字符串）   style="color: red; font-size: 12px;"   ← cssText 一次写入
切对象后        style="color: blue;"                    ← font-size 被删掉
切回字符串后    style="color: red; font-size: 12px;"   ← 整串替换，蓝色自然消失
```

中间一行正是修复的功劳。`normalizeStyle` 对字符串走 `parseStringStyle`（`shared/src/index.ts`），把 `'color:red;font-size:12px'` 拆成键值对象，删除循环这才看得见 `font-size` 这个旧键。反方向（对象切字符串）从来不出事，因为 `cssText` 是整串覆盖，不存在残留一说。jsdom 会把 style 序列化成展开形式，浏览器控制台里键值相同。

属性的正确落点齐了，但 props 里还有一类更新最频繁、也最特别的键——`onClick` 这样的监听器，它的「值」是个函数，下一节专门处理。

## 1.2 事件：invoker

事件处理函数有个特点：模板里写成内联箭头函数时，**每次渲染产出的都是新引用**。朴素版照搬「先解后绑」：

```js
// —— 手写朴素版，仅用于演示 ——
function patchEventNaive(el, key, prevValue, nextValue) {
  const name = key.slice(2).toLowerCase()    // onClick → click
  if (prevValue) el.removeEventListener(name, prevValue)
  if (nextValue) el.addEventListener(name, nextValue)
}
```

它能工作，但每次更新要调两次 DOM API。为什么不能像普通属性那样「引用没变就跳过」？因为内联 handler 的引用几乎必然每次都变，跳过条件形同虚设。仓库的解法叫 invoker（调用器，挂在元素上的转发函数）：把「真正注册的监听器」与「用户的 handler」分离——监听器只注册一次，handler 换了，只改 invoker 身上的一个字段。

```ts
// packages/runtime-dom/src/patchProp.ts —— patchEvent
function patchEvent(el: any, rawName: string, _prevValue: unknown, nextValue: unknown) {
  const invokers = el[veiKey] || (el[veiKey] = {})
  const existingInvoker = invokers[rawName]

  if (nextValue && existingInvoker) {
    // patch：只换值
    existingInvoker.value = nextValue
  } else {
    const [name, options] = parseName(rawName)
    if (nextValue) {
      // add
      const invoker = (invokers[rawName] = createInvoker(nextValue))
      el.addEventListener(name, invoker, options)
    } else if (existingInvoker) {
      // remove
      el.removeEventListener(name, existingInvoker, options)
      invokers[rawName] = undefined
    }
  }
}
```

`el.__vei`（vei = vue event invokers，仓库注释语）是缓存在元素上的调用器表，按原始属性名（如 `onClick`）索引。三个分支对应三种命运：首次绑定时 `createInvoker` 造出转发函数、连同 handler 存进表并注册；更新时新旧 handler 都在，只做 `existingInvoker.value = nextValue`——纯内存赋值、零 DOM 调用，这就是对朴素版两次 DOM 调用的回答；解绑时新值为空（props 循环补的 `null`）才真正 `removeEventListener`，表项置 `undefined`，下次探测等价于不存在。转发函数本体：

```ts
// packages/runtime-dom/src/patchProp.ts —— createInvoker
function createInvoker(initialValue: unknown) {
  const invoker: any = (e: Event) => {
    // handler 每次 patch 时会更新到 invoker.value 上，调用时永远是最新版
    const value = invoker.value
    if (isArray(value)) {
      for (let i = 0; i < value.length; i++) {
        const handler = value[i]
        if (handler) handler(e)
      }
    } else if (value) {
      value(e)
    }
  }
  invoker.value = initialValue
  return invoker
}
```

最关键的一行在函数体第一句：`const value = invoker.value`。事件触发那一刻才读当前值，读到的必然是最近一次 patch 存进去的 handler。patch 时存、触发时取，两个时机错开，「引用每次都变」就不再是问题；`value` 是数组时逐个调用，对应「一个事件挂一组 handler」的写法。

三次渲染能把 `el.__vei` 的三种命运连成一条时间线。实验让 handler 在「函数 A / 空 / 函数 B」之间切换，每步记录调用器表与监听器计数（jsdom 实测）：

```ts
const phase = ref(0)
const handlers = [() => {}, null, () => {}]
createApp({ render: () => h('button', { onClick: handlers[phase.value] }, 'x') })
  .mount(container)
phase.value = 1;  await nextTick()   // 置空
phase.value = 2;  await nextTick()   // 再绑
```

| 时刻 | __vei.onClick | add('click') 累计 | remove('click') 累计 | 本步 DOM 调用 |
|------|---------------|-------------------|---------------------|----------------|
| 挂载（A） | invoker（value = A） | 1 | 0 | add 一次 |
| 渲染 2（置空） | undefined | 1 | 1 | remove 一次 |
| 渲染 3（再绑 B） | 新 invoker（value = B） | 2 | 1 | add 一次 |

表里两处值得停。置空那步走 remove 分支：props diff 发现 `onClick` 从函数变 null，`hostPatchProp(el, 'onClick', fn, null)` 进来，`removeEventListener(name, existingInvoker, options)` 真正解绑、表项置 undefined；options 由同一个 rawName 再算一遍，与 add 时必然一致——上一段末那句「解绑不会失败」的证据就在这行。再绑那步的 invoker 是新造的函数：旧表项已清空，add 分支重新 `createInvoker`，add 计数因此再涨一格。至于「换 handler 不置空」的情形，表里根本没有对应的行——patch 全程只做 `invoker.value = nextValue` 的内存赋值，零 DOM 调用；章末加强版实验连换三次 handler，add 计数停在 1。

还剩第三参。`onClickCapture`（捕获）、`onClickPassive`（被动）、`onClickOnce`（一次即解绑）都要靠 `addEventListener` 的 options 表达。同文件的 `parseName(rawName)` 剥掉后缀、映射成 `{ once: true }` 一类选项，返回 `[name, options]` 展开进第三参。那解绑会不会失败？不会：`removeEventListener` 对照函数引用与第三参，invoker 的引用从未换过，options 又出自同一个 `rawName`，必然一致。朴素版若 add 传了 `{ capture: true }` 而 remove 没传，监听器就永远解不掉。测试锚定在 `rendererAdvanced.spec.ts` 的两例：重渲染后永远用最新 handler、每个事件名只绑定一次监听器，章末动手验证再给加强版。

属性与事件都能打对补丁了，还剩最后半章：节点退场。挂在元素上的不只是 DOM 与监听器——组件子树里还住着渲染副作用，卸载不做干净，它们会回来。下一节处理。

## 1.3 卸载：不是 innerHTML = ''

05 篇的 `render` 有个卸载分支：入参为 `null` 时 `unmount(container._vnode)`。为什么绕这么大一圈，直接清空容器不行吗？朴素版试试：

```js
// —— 手写朴素版，仅用于演示 ——
function render(vnode, container) {
  if (vnode == null) {
    container.innerHTML = ''    // 一把梭：直接清空
  } else {
    patch(container._vnode || null, vnode, container)
  }
  container._vnode = vnode
}
```

DOM 层面毫无问题——容器确实空了。翻车在 DOM 之外：组件挂载时 `setupRenderEffect` 已把渲染函数注册成响应式副作用，`innerHTML = ''` 只擦掉副作用**产出过的结果**，副作用本身还挂在账本上。

```ts
// renderer.spec.ts「unmounted component stays gone when shared state changes」的骨架
const shared = ref(0)
const show = ref(true)
const Child = { render: () => h('p', 'child:' + shared.value) }
const App  = { render: () => (show.value ? h(Child) : null) }
// show 置 false → 容器空了；此时 shared.value = 1
// 正确实现：容器保持空；朴素实现：'child:1' 被 patch 回容器——组件「复活」
```

Child 渲染时读过 `shared`，登记还在账上。`shared` 一改，`instance.update` 重跑，整棵子树挂回容器——仓库注释管这叫「僵尸复活」。此外 `onBeforeUnmount`/`onUnmounted` 永不触发，指令的 `unmounted` 钩子不跑，而这些正是用户放清理逻辑的地方。为什么副作用停不掉？因为它的生命周期登记在组件实例的 effectScope（第 4 篇），`innerHTML` 根本碰不到那一层。

正确的 `unmount` 是一次递归的还账之旅：

```ts
// packages/runtime-core/src/renderer.ts —— unmount（节选：KeepAlive 隐藏、Transition 离场分支从略）
  function unmount(
    vnode: VNode,
    parentComponent: ComponentInternalInstance | null = null,
    doRemove = true,
  ) {
    const { shapeFlag } = vnode

    if (shapeFlag & ShapeFlags.COMPONENT) {
      // ……（KeepAlive _deactivate：隐藏而非卸载，第 12 篇）
      unmountComponent(vnode.component!, parentComponent)
    } else {
      if (vnode.type === Fragment) {
        unmountFragment(vnode, parentComponent)
      } else {
        if (doRemove) {
          if (vnode.transition && vnode.transition.leave) {
            // ……（Transition：动画结束后才真正移除，第 12 篇）
          } else {
            invokeDirectiveHook(vnode, null, parentComponent, 'unmounted')
            hostRemove(vnode.el)
          }
        }
      }
    }
  }
```

按 shapeFlag 分流三路。组件交给 `unmountComponent`，账目最深的一路；Fragment 交给 `unmountFragment`，先递归卸掉每个孩子、再摘首尾两个注释锚点——05 篇说「整组卸载只需处理两个锚点」，兑现处；普通元素先跑指令的 `unmounted` 钩子（v-model 等靠它清理）再 `hostRemove`。组件那一路是「僵尸复活」的正解：

```ts
// packages/runtime-core/src/renderer.ts —— unmountComponent
  function unmountComponent(
    instance: ComponentInternalInstance,
    parentComponent: ComponentInternalInstance | null = null,
  ) {
    // beforeUnmount 钩子（unmounted 走 post flush）
    invokeHooks(instance, 'bum')
    void 0
    // 停止实例 scope：连带停掉 setup 期创建的 effect/computed
    instance.scope.stop()

    const { subTree, um } = instance
    unmount(subTree, instance)

    if (um && um.length) {
      queuePostRenderEffect(() => invokeHooks(instance, 'um'))
    }

    instance.isMounted = false
  }
```

顺序本身就是语义。`beforeUnmount` 先跑，此刻 DOM 还在，用户还能读到「卸载前最后一眼」（`renderer.spec.ts` 专门测了这一点）；接着 `instance.scope.stop()`，第 4 篇的 effectScope 在这里收账，实例名下的渲染副作用、setup 里建的 `watch` 与 `computed` 一次性停止——渲染副作用是挂载时经 `effect(..., { scope: instance.scope })` 显式登记进来的（装配细节第 8 篇）；最后递归 `unmount(subTree)` 清 DOM，`unmounted` 排进 post 队列等刷新收尾执行。

这段四行的顺序值得逐帧推演。实验造一棵「App 下挂 L、R 两个组件」的树：渲染函数返回数组，normalizeVNode 会把它包成 Fragment（05 篇的形态）；四个钩子与摘 DOM 各记一笔，然后整应用卸载。

```ts
const order: string[] = []
const makeComp = (name: string) => ({
  setup() {
    onBeforeUnmount(() => order.push(name + ':bum'))
    onUnmounted(() => order.push(name + ':um'))
    return () => h('p', name)
  },
})
const app = createApp({
  setup() {
    onBeforeUnmount(() => order.push('App:bum'))
    onUnmounted(() => order.push('App:um'))
    return () => [h(makeComp('L')), h(makeComp('R'))]
  },
})
app.mount(container)
app.unmount()
await nextTick()
```

实测顺序（jsdom）：

```text
["App:bum", "L:bum", "DOM-L", "R:bum", "DOM-R", "L:um", "R:um", "App:um"]
```

逐帧对照。第 1 帧 App:bum：根组件的 beforeUnmount 先跑，此刻整棵 DOM 还在。第 2 帧起进入 `unmount(subTree)`：subTree 是 Fragment，`unmountFragment` 按下标循环孩子，L 先完整还账——L 自己的 bum、`L.scope.stop()`（账面动作，无日志）、`hostRemove` 摘掉 L 的 p——然后才轮到 R 的同样三步，最后摘掉 Fragment 的首尾两个注释锚点。三个 um 全在 post 队列里：各自 unmountComponent 时排入，序为 L、R、App，flushJobs 收尾统一派发。

两个容易想错的点。其一，为什么 L 整体先于 R，而不是「先跑完所有 bum 再统一摘 DOM」？因为递归的粒度是组件不是阶段：每个 unmountComponent 把「钩子、停账、摘 DOM」当一次完整还账，做完一个再做下一个。其二，父的 `scope.stop()` 停不掉子的 scope——mini 里每个实例的 scope 都创建在「无活跃 scope」的窗口（父的 setup 早已 off），彼此是独立的根 scope；连带停止靠的正是这趟递归，每个组件各自停各自的账。

对照实验能看见漏网的后果。把 L、R 放进普通元素 `h('div', [h(L), h(R)])` 再卸载：mini 的 unmount 对普通元素不递归孩子，直接 hostRemove 整个 div。实测 L、R 的四个钩子一个不响；更糟的是 L 的账没清，卸载后共享状态再变，L 的渲染函数仍会再跑一次（实测渲染计数从 1 变 2）——产物写进了已脱落的 div，容器看不见，副作用与内存却在漏。官方实现对普通元素的数组孩子同样递归卸载（`third_party/vue-core` 的 unmount 里 unmountChildren 一支），差距节补记。

接下来是本章埋得最深的一个坑，05 篇按下不表：`patch` 里类型不匹配的替换顺序。

```ts
// packages/runtime-core/src/renderer.ts —— patch（节选）
    // 类型或 key 变了 → 丢弃旧节点整树，当新节点处理
    // 关键：先在「旧节点的位置」算出锚点再卸载 —— 卸载后旧节点已从 DOM 摘除，
    // 拿它的 nextSibling/el 做 anchor 会抛 NotFoundError（真 Vue 同样先取 anchor）
    if (n1 && !isSameVNodeType(n1, n2)) {
      anchor = getNextHostNode(n1)
      unmount(n1, parentComponent)
      n1 = null
    }
```

场景是 `div` 换 `span` 这类整树替换。新树要挂到「旧树原来所在的位置」，参照物是紧跟旧树之后的兄弟节点——`insert` 的锚点语义（05 篇）。这两行为什么不能颠倒？卸载把旧节点从文档摘除，之后再查它的 `nextSibling` 只能得到 null，参照物失效；若拿旧节点自身当参照，`insertBefore` 对不在文档里的节点直接抛 `NotFoundError`。仓库注释记录了这个坑，官方实现同样先取锚点。

取锚点的工具也有讲究：

```ts
// packages/runtime-core/src/renderer.ts —— getNextHostNode
  /** 找「prevTree 后面紧邻的宿主锚点」：组件递归下钻，片段取 anchor */
  function getNextHostNode(vnode: VNode): any {
    if (vnode.shapeFlag & ShapeFlags.COMPONENT) {
      return getNextHostNode(vnode.component!.subTree)
    }
    // 返回「紧随其后的兄弟节点」而非自身 —— 因为调用方要先取 anchor 再卸载旧节点，
    // 旧节点卸载后自已已不在 DOM，兄弟节点才仍然有效（真 Vue 同逻辑）
    return hostNextSibling((vnode.anchor || vnode.el)!)
  }
```

组件要递归下钻：组件自己不占 DOM，占位的是 `subTree` 的根，可能还套着组件；Fragment 取尾部锚点，普通元素取 `nextSibling`。为什么返回「兄弟」而非节点自身？因为调用方拿到锚点之后才卸载旧节点——自身马上要被摘掉，兄弟才是卸载之后仍然有效的参照。至此，挂载、属性与事件补丁、卸载三件事闭环。但界面里更新最多的是**一组**子节点：列表增删、排序、反转，两组子节点怎么比、DOM 怎么复用，是下一章的主场。

## 本章小结

属性补丁的分水岭是 attribute 与 property：attribute 是解析期初始值，property 是活值，`key in el` 负责分流。事件以 invoker 解耦「注册的监听器」与「用户的 handler」：监听器只注册一次，patch 只换 `invoker.value`，触发时闭包取最新版。卸载是一次递归还账：组件先跑 `beforeUnmount` 再 `scope.stop()` 停掉全部副作用，元素摘 DOM、跑指令钩子。整树替换必须先 `getNextHostNode` 取锚点再 `unmount`，颠倒会让参照物失效。

## 与官方实现的差距

以下均对照 `third_party/vue-core`（v3.5.43）核对：

- **组织**：官方按类型拆成 `runtime-dom/src/modules/` 下五文件（`attrs`/`class`/`events`/`props`/`style`），分发留在 `patchProp.ts`；本仓库单文件实现。
- **invoker 键与防御**：官方 `veiKey` 是 `Symbol('_vei')`（unique symbol），本仓库是字符串 `'__vei'`。官方 invoker 记挂载时间戳并与事件时间戳比对，防「冒泡途中换 handler、同一事件触发两次」（core 注释引 vue#6566，书 8.8 议题），本仓库未做。
- **事件名解析**：官方 `parseName` 用 `while` 剥多重修饰符、支持 `on:custom-event`，事件名经 `hyphenate` 转连字符（`hyphenate` 在 `shared/src/general.ts` 经 `cacheStringFunction` 缓存）；本仓库只认单个后缀、`toLowerCase`。
- **shouldSetAsProp 特判**：官方约 60 行——SVG 多数键走 attribute、`spellcheck`/`draggable` 等枚举属性恒走 attribute、`form` 只读、`list` 配 INPUT、`type` 配 TEXTAREA、嵌入式标签的 `width`/`height` 等，兜底同为 `key in el`。本仓库一行判定加正则，`form` 这类只读 property 会被误判（赋值静默失败）。
- **value 专案**：官方 `patchDOMProp` 对 `value` 单独处理（存 `el._value`、checkbox 空值设 `'on'`、`OPTION` 比对属性值），null/undefined 按目标类型归一并补 `removeAttribute`；签名还多 `namespace`/`parentComponent` 两参并跳过 v-model 监听。本仓库只做布尔归一。
- **元素孩子的递归卸载**：官方 unmount 对普通元素的 `ARRAY_CHILDREN` 走 unmountChildren（非优化路径），嵌在元素下的组件会走完整的 unmountComponent；本仓库 unmount 只递归组件与 Fragment 两类，普通元素直接 hostRemove——元素内组件的 beforeUnmount/unmounted 不触发、scope 不停止（本章对照实验实测：钩子零触发、卸载后渲染计数照涨）。

预期 6 个测试文件、65 个用例全部通过。再给一个加强版实验——「换了三次 handler 引用，监听器仍只有一个」，临时存成 `packages/runtime-dom/__tests__/` 下任意 `.spec.ts`：

```ts
// @vitest-environment jsdom
import { expect, it, vi } from 'vitest'
import { createApp, h, nextTick, ref } from '../src'

it('三次重渲染换新 handler，click 监听器仍然只有一个', async () => {
  const addSpy = vi.spyOn(EventTarget.prototype, 'addEventListener')
  const n = ref(0)
  const container = document.createElement('div')
  createApp({ render: () => h('button', { onClick: () => n.value++ }, String(n.value)) })
    .mount(container)

  for (let i = 0; i < 3; i++) { n.value++; await nextTick() }  // 每次都是新箭头函数

  expect(addSpy.mock.calls.filter(c => c[0] === 'click')).toHaveLength(1)
  addSpy.mockRestore()
})
```

预期：通过。spy 只在首次挂载时捕获一次 `click` 注册，此后三次换 handler 全是 `invoker.value` 的内存赋值。注意别在断言前调 `container.querySelector`：jsdom 会借此懒注册一批 Window 级内部监听（含一个 `click`），把计数搅浑。1.1 节的翻车实验则可直接抄进浏览器控制台复现。1.3 的卸载顺序实验同法可跑：挂上 makeComp 树之后 `app.unmount()`，日志应依次为 App:bum、L:bum（随即摘 L 的 DOM）、R:bum（随即摘 R 的 DOM）、L:um、R:um、App:um；再把两子包进 `h('div', ...)` 对照，钩子应当全部沉默。
