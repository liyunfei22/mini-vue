# 03 · 模板编译器：从模板字符串到渲染函数

> 本篇实现 `packages/compiler-core`、`packages/compiler-dom` 与 `packages/vue` 的运行时编译入口。前置阅读：00 篇的「运行时与编译时」分工、02 篇的 vnode 与补丁标记。产出：一条完整的编译流水线——解析、变换、代码生成，以及把产物实例化为渲染函数的最后一跳；并逐项说明与官方实现的差异。

## 引言

00 篇把渲染管线概括为三个阶段：编译、挂载、更新。前两篇实现了后两个阶段的支撑系统——响应式系统判定「何时重新执行」，渲染器执行「如何把 vnode 变成 DOM」；本篇补上第一阶段。官方文档对模板与渲染函数的对比给出了编译器存在的理由：渲染函数更灵活，但模板具有确定的语法，更容易做静态分析——补丁标记（patch flags）、静态提升（static hoisting）等优化全部建立在这个前提上。

浏览器并不认识模板语法，`<div>{{ msg }}</div>` 对引擎而言只是一段字符串。编译器的职责是把它翻译成渲染器已经能执行的渲染函数。本篇按流水线顺序解决四个子问题：解析（parse）——模板字符串如何变成抽象语法树（AST，Abstract Syntax Tree，模板的结构化表示）；变换（transform）——声明式的语法树如何改写成可生成代码的形状；代码生成（codegen）——改写后的树如何拼出函数源码字符串；实例化——源码字符串如何变成可调用的渲染函数并接入运行时。

## 一、编译管线总览

编译编排集中在一个函数里：解析产出语法树，变换改写语法树，代码生成消费语法树。

```ts
// packages/compiler-core/src/compile.ts（节选）
export function baseCompile(template: string | any, options: CompilerOptions = {}) {
  const onError = options.onError || ((e: any) => { throw e })
  let ast = isStringTemplate(template) ? baseParse(template, options) : template

  transform(ast, extend({}, options, {
    nodeTransforms: [transformIf, transformFor, transformExpression,
      transformSlotOutlet, transformElement, transformText,
      ...(options.nodeTransforms || [])],
  }))

  return generate(ast, options)
}
```

两处编排细节值得注意。其一，`baseCompile` 允许传入已解析的 AST（`isStringTemplate` 为假时跳过 parse），解析与编译可以分属不同入口。其二，`nodeTransforms` 的注册顺序是语义的一部分：结构变换（transformIf、transformFor）在前、元素化变换（transformElement）居中、文本合并（transformText）收尾，第三节会看到这个顺序与退出钩子的逆序执行共同决定正确性。平台差异也在编排层注入：`compiler-dom` 的 `compile` 在此之上叠加浏览器解析选项（`isNativeTag`、`isVoidTag` 等，见 `packages/compiler-dom/src/parserOptions.ts`），`compiler-core` 本身不认识任何具体标签。

## 二、parse：滚动源状态机

**滚动源与 advanceBy。** 解析器不依赖正则整体匹配，而是一个状态机。核心状态只有一个：`ParserContext` 中始终指向「尚未解析部分」的滚动源字符串 `source`（辅以 `options` 与错误定位用的 `offset`）。所有解析函数的协议都是「读 `source` 开头、吃掉一段、推进光标」，推进统一经过一个入口：

```ts
// packages/compiler-core/src/parse.ts（节选）
function advanceBy(context: ParserContext, numberOfCharacters: number): void {
  const { source } = context
  context.source = source.slice(numberOfCharacters)
  context.offset += numberOfCharacters
}
```

`advanceBy` 只做两件事：切短滚动源、累加偏移量。任何直接修改 `source` 的旁路都会让 offset 与内容失去同步；`offset` 供 `getCursor` 换算行列用于错误定位（本实现省略了官方的完整 source map）。

**parseChildren 主循环：看开头字符分流。** 每次迭代只检查滚动源开头的一两个字符，就足以决定当前节点类型：

```ts
// packages/compiler-core/src/parse.ts —— parseChildren 主循环（节选）
while (!isEnd(context, ancestors)) {
  const s = context.source
  let node: TemplateChildNode | undefined
  if (mode === TextModes.DATA || mode === TextModes.RCDATA) {
    if (s[0] === '<') {
      // ……s[1] === '!'：注释 / DOCTYPE，定位结束符后 advanceBy 跳过（略）
      if (s[1] === '/') {
        break                 // </：父级结束标签，本层 children 到此为止
      } else {
        node = parseElement(context, ancestors)  // 标签：递归下沉
      }
    }
  }
  if (!node) node = parseInterpolation(context, mode) || parseText(context, mode)
  if (node) children.push(node)
}
```

分派规则：`<` 打头交给元素解析，`{{` 打头交给插值解析，其余按当前语法模式的结束符切成文本。循环终止条件 `isEnd` 检查两件事：滚动源耗尽，或出现了与某个祖先对应的 `</标签` 序列——后者正是嵌套结构的回收机制。元素解析是递归的：`parseTag` 读出标签名与属性后，`parseElement` 把自己压进 `ancestors` 数组，带着新语法模式递归调用 `parseChildren` 生成 children，弹出，再消费结束标签；结束标签缺失时抛出 `X_MISSING_END_TAG` 编译错误（见 `parseElement` 与 `packages/compiler-core/src/errors.ts`）。插值解析中则有一个必须警惕的下标陷阱：`closeIndex` 是在**尚未推进**的源串上计算的，`advanceBy` 吃掉 `{{` 之后滚动源已变短，直接 `slice(0, closeIndex)` 会多出两个字符，源码的写法是回扣开定界符长度——`context.source.slice(0, closeIndex - open.length)`。这类「推进后再用旧下标」的错位在状态机解析中反复出现，判别方法只有一个：每个下标都要明确它属于哪一次推进之前的源串。

**TextModes：语法模式分档。** 不同区域的语法规则不同：`<textarea>` 里的 `<` 是普通字符但 `{{ }}` 仍是插值，`<script>` 里则一切都是纯文本。解析器用 TextModes 标注当前区域：

```ts
// packages/compiler-core/src/parse.ts（节选）
const enum TextModes { DATA, RCDATA, RAWTEXT, CDATA, ATTRIBUTE_VALUE }

function getRawTextOrRcDataMode(tag: string): TextModes | undefined {
  if (tag === 'textarea' || tag === 'title') return TextModes.RCDATA
  if (tag === 'style' || tag === 'script') return TextModes.RAWTEXT
  return undefined
}
```

实际生效的是三档：DATA（普通 HTML 区域，`<` 与 `{{` 都有语法含义）、RCDATA（可转义文本区域，仅 `{{` 有效）、RAWTEXT（原始文本区域，直到关闭标签前全部是文本）。模式的消费点有两处：parseChildren 只在 DATA/RCDATA 下进入 `<` 分支；parseInterpolation 同样拒绝 RAWTEXT——`<script>` 中的 `{{ }}` 因此是纯文本。剩下两档是官方为浏览器边角场景预留的档位：CDATA 对应 SVG/MathML 等外来内容语境，ATTRIBUTE_VALUE 对应属性值内部的实体解码语境；本实现的模板解析不会进入这两种语境，枚举成员仅为对齐官方而保留。

**parseAttribute：指令的识别与拆分。** 属性解析要把 `v-on:click.once`、`:class`、`@click`、`#title` 拆成统一的指令节点，识别依据是首字符或 `v-` 前缀（`directiveRE = /^v-([a-zA-Z0-9-_]+)/`）：

```ts
// packages/compiler-core/src/parse.ts —— parseAttribute 中指令的拆分（节选）
const isDirective =
  name[0] === ':' || name[0] === '@' || name[0] === '#' || directiveRE.test(name)

if (isDirective) {
  let dirName: string
  let argContent = ''
  let modifiers: string[] = []

  if (name[0] === ':') {            // @ → on、# → slot 两个分支同构（略）
    dirName = 'bind'
    argContent = name.slice(1)
  } else {
    const m = directiveRE.exec(name)!
    dirName = m[1]
    // ……（略）从剩余部分拆 arg 与 modifiers：v-on:click.once → arg 'click'、modifiers ['once']
  }
  // ……（略）构造 DIRECTIVE 节点 { name, exp, arg, modifiers }
}
```

缩写前缀展开为全名：`:` 是 bind、`@` 是 on、`#` 是 slot；`v-` 后先取指令名，剩余部分按「冒号取参数（arg）、点号切修饰符（modifiers）」拆解。至此 parse 的产出齐备：ELEMENT 节点携带 props 数组，普通属性是 ATTRIBUTE 节点、指令是 DIRECTIVE 节点，后者的 `name` 已是 `if`/`for`/`bind`/`on` 这样的规范化名称——transform 阶段不再需要关心语法糖。

## 三、transform：双阶段变换管线

**进入钩子与退出钩子。** parse 产出的 AST 是声明性的：`<p v-if="ok">` 只是一个带指令属性的元素，代码生成需要的是可执行的形状。变换管线的核心是把每个变换拆成「进入钩子」与「退出钩子」两段：

```ts
// packages/compiler-core/src/transform.ts —— traverseNode（节选）
export function traverseNode(node: any, context: TransformContext) {
  context.currentNode = node
  const { nodeTransforms } = context
  const exitFns: Array<() => void> = []

  for (let i = 0; i < nodeTransforms.length; i++) {
    const onExit = nodeTransforms[i](node, context)
    if (onExit) exitFns.push(onExit)
    if (!context.currentNode) return   // 节点已被 removeNode
    node = context.currentNode         // 结构变换可能替换了节点，后续变换跟新节点走
  }

  switch (node.type) { /* ……（略）按类型分发 traverseChildren、登记 helper */ }

  let i = exitFns.length
  while (i--) {
    if (!context.currentNode) context.currentNode = node
    exitFns[i]()                       // 逆序执行退出钩子
  }
}
```

三处设计相互咬合。**进入阶段可替换节点**：transformIf 把元素替换成 IF 节点后，`node = context.currentNode` 让注册在其后的变换作用于新节点——结构先定稿，元素化后进行。**退出钩子逆序执行**：这等价于把变换数组当作一层嵌套作用域，先进入的最后退出；具体收益在注册顺序上——transformText 排在 transformElement 之后，其退出钩子（合并相邻文本/插值）就先于 transformElement 的退出钩子（读取 children 构造 vnode 调用）执行，元素收编 children 时文本已合并完毕。**退出钩子承担延迟操作**：v-else 对原元素的摘除必须等到 transformElement 给该元素建好 `codegenNode`，因此被包成退出钩子。`traverseChildren` 在遍历每个孩子前设置 `context.parent` 与 `context.childIndex`，这是下一小节回链查找的数据基础；孩子被移除时回退下标（`i--`）重新对齐数组。

**v-if：折叠为 branches 的 IF 节点。** v-if 是结构指令（structural directive）——改变模板结构的指令。一串相邻分支在 AST 层面被折叠成单个 IF 节点：

```
<div v-if="a"/><div v-else-if="b"/><p v-else/>
  → IF { branches: [{ condition: a, children: [div] }, { condition: b, children: [div] },
                     { condition: undefined, children: [p] }] }   // v-else 无条件
```

v-if 分支的处理是「替换」：构造 IF_BRANCH（condition 取自指令表达式）与 IF 节点后，`context.replaceNode(ifNode)` 把当前元素换成语义等价的容器，原元素降级为分支的 children。v-else / v-else-if 则是「回链追加」：

```ts
// packages/compiler-core/src/transforms/transformIf.ts —— processIf 的 v-else 分支（节选）
const parent = context.parent
const prevSibling = parent!.children[context.childIndex - 1] as any
if (prevSibling && prevSibling.type === NodeTypes.IF) {
  prevSibling.branches.push({
    type: NodeTypes.IF_BRANCH,
    loc: node.loc,
    condition: dir.name === 'else-if' ? dir.exp : undefined,
    children: [node],
    userKey: undefined,
  })
  // 摘除延迟到退出阶段：等 transformElement 给这个元素建好 codegenNode 后再摘。
  // 用「身份查找」而非 childIndex —— 内层遍历（子节点）会污染 childIndex。
  return () => {
    const list = context.parent!.children
    const index = list.indexOf(node)
    if (index > -1) { list.splice(index, 1); context.currentNode = null }
  }
}
// ……（略）前一个兄弟不是 IF 时：console.warn 提示 v-else 缺少相邻的 v-if
```

两个关键决策。其一，回链只认「前一个兄弟是 IF 节点」：v-else 与 v-if 的配对关系在 AST 层面显式校验，配不上时给出警告而非静默丢弃。其二，摘除用 `indexOf(node)` 身份查找而绝不使用 `childIndex`：进入钩子之后、退出钩子之前，该元素的整棵子树都被遍历过，`context.childIndex` 已被子节点的遍历覆盖，按陈旧下标 splice 会删错兄弟——身份查找在任何时刻都指向正确的节点。折叠完成后，`genIf` 把 branches 展开为嵌套三元表达式；最后一个分支若仍带条件（没有 v-else 兜底），补一个 `_createCommentVNode("v-if", true)` 占位，与官方产物一致。

**v-for：别名剖分与 FOR 节点。** v-for 的结构变换与 v-if 同构：`processFor` 用 FOR 节点替换原元素、登记 `RENDER_LIST` helper、把原元素收进 `children`。差异在于表达式要先剖分——`(item, i) in list` 的两侧语义不同：

```ts
// packages/compiler-core/src/transforms/transformFor.ts —— parseForExpression（节选）
const forAliasRE = /([\s\S]*?)\s+(?:in|of)\s+([\s\S]*)/    // 位于本文件顶部

export function parseForExpression(input: string) {
  const [, lhs, rhs] = input.match(forAliasRE)!    // 不匹配时的防御分支（略）
  const source = createSimpleExpression(rhs.trim(), false)
  // (item, index) 解构
  const params = lhs.trim().replace(/^\(|\)$/g, '')
  const [first, second, third] = params.split(',').map((s) => s.trim())
  return {
    source,
    value: first ? createSimpleExpression(first, false) : undefined,
    index: second ? createSimpleExpression(second, false) : undefined,
    key: third ? createSimpleExpression(third, false) : undefined,
  }
}
```

一条正则按 `in`/`of` 把表达式切成两侧：右侧是数据源表达式（source），左侧剥掉括号后按逗号拆出别名序列，依次映射为 value、index、key 三个可选别名，FOR 节点携带 `{ source, valueAlias, indexAlias, keyAlias, children }`。别名次序与官方有一处命名差异：官方拆分结果是 `{ value, key, index }`（第三位是 index），本实现第三位命名为 key；对 `(item, index)` 这一最常用形态两者行为一致。

## 四、codegen：拼出函数源码

**generate 骨架。** 代码生成的本质是按节点类型分发的字符串拼接，产物是函数**源码字符串**。骨架决定产物的整体形状：

```ts
// packages/compiler-core/src/codegen.ts —— generate（节选）
const usedHelpers = (ast as any).helpers || []
if (usedHelpers.length) {
  const destructure = usedHelpers
    .map((h: symbol) => `${helperNameMap[h]}: _${helperNameMap[h]}`)
    .join(', ')
  push(`const { ${destructure} } = Vue`)   // newline 分行（略）
}

// 静态提升：收集可提升的静态子树，逐个生成 const（渲染期只创建一次）
const hoistedNodes: any[] = []
collectHoistedNodes(ast.codegenNode, hoistedNodes)
// ……（略）逐个生成 const _hoisted_N：生成本体时先揭掉提升标记再挂回，
//          防止 genVNodeCall 短路成 _hoisted_N = _hoisted_N 自引用

push(`return function render(_ctx, _cache) {`)
indent()
push(`with (_ctx) {`)
// ……（略）return 语句按 codegenNode 逐节点拼接，块根前置 _openBlock(),
```

产物结构自上而下三段：helper 解构、提升常量、渲染函数体。**helper 解构**——transform 阶段登记的运行时助手统一输出为 `const { renderList: _renderList, ... } = Vue`，这是编译器与运行时的全部耦合：编译器只产出符号名（`packages/compiler-core/src/runtimeHelpers.ts`），运行时提供同名函数即可，两侧没有任何导入关系。**`with (_ctx)` 方案**——模板表达式（`msg`、`item`、`ok ? a : b`）不做任何改写，原样输出进 `with (_ctx) { }` 块内，运行期靠 `with` 的作用域规则把裸标识符命中到渲染上下文上；这是本实现最大的取舍，代价与官方替代方案的对比见第七节，`transformExpression` 在本工程因此是显式的空操作（no-op，见 `packages/compiler-core/src/transforms/transformExpression.ts`），保留入口以便切换方案。**静态提升的衔接**——`collectHoistedNodes` 预扫描出「全静态」的子树（patchFlag 为 -1、无指令、非组件、children 与 props 均为纯静态形态），提升为渲染函数外的 `const _hoisted_N`，跨渲染复用同一个 vnode，渲染器见到 `n1 === n2` 直接跳过比对。另一处防御：含动态 props 或依赖 `_ctx` 的调用一律不提升，否则表达式会在 `with` 作用域之外求值，直接 ReferenceError。提升策略与区块（block）机制的完整分析留给 04 篇。

**实际产物。** 下面是仓库的真实编译输出（`compile` 的 `code` 字段，格式与编译器产出一致），覆盖单根区块、静态提升与 v-for：

```js
// compile('<div id="app"><p class="t">static</p><li v-for="(item, i) in list" :key="i">{{ item }}</li></div>').code
const { createElementVNode: _createElementVNode, renderList: _renderList, toDisplayString: _toDisplayString, openBlock: _openBlock, createElementBlock: _createElementBlock } = Vue
const _hoisted_1 = _createElementVNode("p", {class: "t"}, "static", -1)
return function render(_ctx, _cache) {with (_ctx) {
    return _openBlock(), _createElementBlock("div", {id: "app"}, [_hoisted_1, _renderList(list, (item, i) => _createElementVNode("li", {key: i}, _toDisplayString(item), 9, ["key"]))], -1)
  }
}
```

产物中可以直接读出前两节的全部变换结果：静态 `<p>` 提升为 `_hoisted_1`（patchFlag 为 -1，即 HOISTED）；v-for 变成 `_renderList(list, (item, i) => ...)`，别名成为回调参数；插值包裹 `_toDisplayString`；`<li>` 的补丁标记是 9（TEXT | PROPS 的位组合），动态 props 名单 `["key"]` 一并列出，渲染器据此只比对列名的属性；单根模板被标记为区块，前置 `_openBlock(), `；表达式 `list`、`item` 原样出现——`with (_ctx)` 方案的直接证据。v-if 链的产物同构：`genIf` 输出 `(a) ? A : (b) ? B : C` 形态的嵌套三元，链尾无 v-else 时以 `_createCommentVNode("v-if", true)` 兜底（验证一节的示例可直接复现）。

## 五、compileToFunction：最后一跳

源码字符串距离可调用的渲染函数只差实例化。聚合包 `vue` 的编译入口完成这一跳，并把编译能力登记进运行时：

```ts
// packages/vue/src/index.ts
export function compileToFunction(template: string, options?: CompilerOptions & { onError?: (e: any) => void }) {
  const { code } = compile(template, options)
  const render = new Function('Vue', code)(runtimeDom)

  ;(render as any)._rc = true // 标记为编译产物（供调试/测试识别）
  return render
}

// 注册运行时编译器：让 `template: "..."` 选项可用（与真 Vue 的 config.compiler 语义一致）
registerRuntimeCompiler(compileToFunction)
```

`new Function('Vue', code)` 构造一个形参为 `Vue` 的匿名函数并立即以整个 `runtime-dom` 聚合模块调用它——产物顶部的 `const { ... } = Vue` 解构正是在消费这个形参，helper 依赖因此从「编译期符号」落地为「运行时模块的具名导出」，不需要任何打包期的模块拼接。`registerRuntimeCompiler` 的接线横跨三个包：`runtime-core` 用模块级变量持有编译器（`packages/runtime-core/src/apiCreateApp.ts`），创建应用上下文时把它填进 `config.compiler`；组件安装时 `finishComponentSetup` 发现 `template` 选项且 `config.compiler` 存在，就现场编译出 `instance.render`（`packages/runtime-core/src/component.ts`）。依赖方向由此保持单向：runtime-core 不 import 任何编译器包，编译能力由聚合包在初始化时注入——这也解释了 00 篇分包表中 `vue` 包「运行时 + 运行时编译器」的定位。

## 六、编译期与运行期的分工边界

流水线走完后，可以精确回答「哪些工作被上提到了编译期」。**能上提的**：语法糖的展开（v-if 折叠为条件表达式、v-for 包装为 renderList 调用、v-model 拆解为 props 与回写事件）、静态性盘点（补丁标记、动态 props 名单、静态提升）、标签类型判定（组件或元素，`resolveComponent` 调用的插入）——这些只依赖模板文本即可确定。**必须留在运行期的**：响应式依赖的收集（表达式何时执行、执行时读到什么，只有运行期知道）、新旧 vnode 树的比对与 DOM 操作、生命周期与指令的运行时半边（如 checkbox 形态 v-model 的 DOM 同步）、组件实例的解析上下文（`resolveComponent` 要查当前实例的组件注册表）。分界线两侧通过 helper 协议对话：编译器产出符号名单，运行时补齐同名实现；渲染器消费补丁标记与提升 vnode 的方式（02 篇）就是这条边界的运行时一侧。

## 七、与官方实现的差异

**表达式方案：`with (_ctx)` 与 prefixIdentifiers**。官方编译器在构建期场景（compiler-sfc / module 模式）启用 prefixIdentifiers：借 babel 解析能力把每个裸标识符改写为 `_ctx.foo`（`packages/compiler-core/src/transforms/transformExpression.ts`），产物不含 `with`，函数体可运行在严格模式与 CSP 环境，表达式可静态分析，与上下文无关的常量还能进一步提升。值得注意的是官方的浏览器运行时编译器**同样退回 `with (_ctx)`**（`packages/compiler-core/src/codegen.ts` 中 `useWithBlock = !prefixIdentifiers && mode !== 'module'`）——`with` 是该场景的官方方案而非权宜。本实现的差异在于只有这一条路：transformExpression 是空操作，产物永远依赖 `with` 与 `new Function`，两者都被严格 CSP 禁止；官方的应对是把编译整体前移到构建期。

**无 compiler-sfc 与 SSR 编译**。官方仓库另有 compiler-sfc（`.vue` 单文件组件：script/template/style 块解析、scoped 样式、模板预编译）与 compiler-ssr；本工程只有 compiler-core 与 compiler-dom，`.vue` 文件的编译不在范围内（00 篇已列为明确简化）。**解析器结构与错误恢复**——官方 3.5 把解析拆成 tokenizer + parser 两个文件，带完整的实体解码、错误恢复与 source map；本实现是单文件状态机，错误处理从简：结束标签缺失直接抛错（官方记录错误并尝试恢复继续解析）、HTML 实体不解码（`decodeEntities` 恒等返回，见 `packages/compiler-dom/src/parserOptions.ts`）、注释节点解析后直接丢弃。此外 v-for 别名第三位的命名与官方不同（v-for 一节末尾）。以上各项均以本地 `third_party/vue-core`（v3.5.x）源码核对为准。

## 验证与复现

编译器的行为由两组测试锚定：`npx vitest run packages/compiler-core`（10 个用例，parse/transform/codegen 的产物断言）与 `npx vitest run packages/vue`（15 个用例：`packages/vue/__tests__/compileToFunction.spec.ts` 的 10 个覆盖「编译 → 挂载 → 更新」端到端闭环——插值、属性绑定、v-if/v-else、v-for、事件、v-model、插槽、provide/inject；`optimization.spec.ts` 的 5 个断言补丁标记与静态提升的运行时效果）。实测两个命令分别 10、15 个用例全绿。一个覆盖主线的最小验证（工程根目录、Node ESM 环境，已实测）：

```ts
import { compile, compileToFunction } from '@mini-vue/vue'

// ① 看产物：v-if 变三元、表达式原样直出
const { code } = compile('<div v-if="ok">{{ msg }}</div><p v-else>none</p>')
console.log(code)   // 产物含：(ok) ? _createElementVNode("div", ...) : ...

// ② 直接调用：compileToFunction 返回可执行的 render
const render = compileToFunction('<p class="t">{{ msg }}</p>')
const vnode = render({ msg: 'hello' }, [])   // 第一参是 _ctx，第二参是 _cache
// vnode.type === 'p'；vnode.props === { class: 't' }；vnode.children === 'hello'
```

第二步返回的 vnode 与 02 篇渲染器手工构造的 vnode 同构——把 `{ msg }` 换成 setup 返回的 `ref`、交给 `createApp` 挂载，响应式更新链路（01 篇）即自动接上。端到端断言见 `packages/vue/__tests__/compileToFunction.spec.ts`。

## 小结

编译器是一条三段流水线：parse 以「滚动源 + 光标」的状态机把模板滚成 AST，语法模式（DATA/RCDATA/RAWTEXT）划定各区域的解析规则；transform 以进入/退出双阶段遍历完成结构改写——v-if 折叠为 branches 的 IF 节点、v-for 剖分别名后替换为 FOR 节点，退出钩子的逆序执行保证「先定结构、后建 codegenNode、末了摘除」，v-else 的卸载以身份查找规避陈旧下标；codegen 把树拼成源码字符串，helper 解构 `const { ... } = Vue` 是与运行时的全部耦合，`with (_ctx)` 让表达式零改写直出；compileToFunction 以 `new Function('Vue', code)` 完成实例化，registerRuntimeCompiler 把编译能力注入运行时使 `template` 选项可用。与官方的核心差异集中在表达式方案——官方构建期用 prefixIdentifiers 换来 CSP 兼容与可静态分析，浏览器运行时编译器则与本实现同样使用 `with`。
