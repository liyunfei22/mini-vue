# 13 · 从源码到产物：构建流水线收官

上一章补齐 Options API、Transition 与 KeepAlive 之后，内核在功能意义上已经完整：七个包、全套行为测试、源码可以直接被 vitest 跑起来。但源码能跑，不等于能被消费——仓库里躺着的仍是七个 TypeScript 源码目录，而库的消费者不可枚举，谁也不会陪着本仓库跑 vitest。

这最后一章解决「交付」：源码要变成什么形态，打包器、Node 脚本、`<script>` 直引页面、TypeScript 用户才能各取所需？`__DEV__` 明明写进了构建配置的 define，为什么生产产物里它还是 true？七个包互相 import，先构建谁、还是根本不需要顺序？类型声明怎么从每文件一份的碎片变成一个入口？过程中我们会实测翻一次车，再顺着根因把官方的三层方案看懂。

## 13.1 四类消费者与三种格式

先看四段消费代码。同样是「用一下 mini-vue」，四类消费者写法各不相同：

```js
// 消费者一：打包器项目（Vite/Webpack 业务代码）——期望 ES Module
import { createApp, reactive } from '@mini-vue/vue'

// 消费者二：Node 脚本（CommonJS）——期望 require 得到具名导出
const { createApp } = require('@mini-vue/vue')

// 消费者三：无构建环境（在线演示页）——期望单文件挂全局变量
<script src="https://example.com/vue.global.js"></script>
<script>MiniVue.createApp({...}).mount('#root')</script>

// 消费者四：TypeScript 用户——不执行任何 JS，只读类型声明
import type { App } from '@mini-vue/vue'
```

前三种各对应一种产物格式（format，即输出文件的模块语法类别）：**esm-bundler** 给打包器、**cjs** 给 Node 的 `require()`、**global** 是 IIFE（立即调用函数表达式）单文件，执行后把导出挂到全局变量上。第四种不产 JS，产 `.d.ts`，留到 13.5。这套命名与官方 `vue` 包的 dist 一一对应：`vue.esm-bundler.js`、`vue.cjs.js`、`vue.global.js`。

格式名到文件名的翻译，集中在共享配置的一个函数里：

```js
// rollup.config.js（节选）
const outputName = (f) => {
  const prod = isProd ? '.prod' : ''
  if (f === 'esm-bundler') return `packages/${TARGET}/dist/${pkg.name.replace('@mini-vue/', '')}.esm-bundler${prod}.js`
  if (f === 'cjs') return `packages/${TARGET}/dist/${TARGET}${prod}.cjs`
  if (f === 'global') return `packages/${TARGET}/dist/${TARGET}.global${prod}.js`
  return `packages/${TARGET}/dist/${TARGET}.${f}.js`
}
const outputFormat = { 'esm-bundler': 'es', cjs: 'cjs', global: 'iife' }
```

命名规则有三点。第一，esm-bundler 的文件头取包名去掉 scope 前缀，`@mini-vue/shared` 产出 `shared.esm-bundler.js`，与官方 `vue.esm-bundler.js` 同构。第二，cjs 产物用 `.cjs` 扩展名而非 `.js`——这不是风格偏好，而是 Node 解析规则的硬要求（13.6 陷阱一）。第三，prod 模式在中缀插入 `.prod`，`shared.prod.cjs` 与 dev 产物可并存对照。

哪些包出哪些格式，写在各包 `package.json` 的 `buildOptions.formats` 里：shared 等六个包只有 `['esm-bundler', 'cjs']`，`vue` 包三格式齐全。为什么 shared 不出 global？因为被 `<script>` 直引的只会是聚合入口，中间层包永远工作在打包链路内部，没有面向「无构建环境」的义务。下一节看这些格式是怎么被逐包驱动出来的。

## 13.2 编排：一份共享配置逐包跑

七个包不写七份 rollup 配置，只写一份，构建时用环境变量注入「这次构建谁」。编排由 `scripts/build.js` 承担，第一步收集目标包：

```js
// scripts/build.js（节选，行内中文注释为本篇所加）
const args = process.argv.slice(2)
const targetArgs = args.filter((a) => !a.startsWith('--'))   // 位置参数 = 包名
const prodOnly = args.includes('--prod')
const NODE_ENV = prodOnly ? 'production' : 'development'
const withTypes = args.includes('--with-types')
const all = args.includes('--all') || targetArgs.length === 0

const targets = readdirSync(PACKAGES_DIR)
  .filter((dir) => {
    try {
      readFileSync(`${PACKAGES_DIR}${dir}/package.json`, 'utf-8')   // 以 package.json 存在性认包
      return true
    } catch {
      return false
    }
  })
  .filter((t) => all || targetArgs.some((a) => a.startsWith(t)))    // 子串匹配：dom 命中两个包
```

命令行输入分两类：位置参数按子串匹配包名，`node scripts/build.js dom` 会同时命中 compiler-dom 与 runtime-dom；`--` 前缀的是模式开关。主循环逐包驱动 rollup，并在每次调用前重建 dist：

```js
// scripts/build.js（节选，行内中文注释为本篇所加）
for (const t of targets) {
  const distDir = `${PACKAGES_DIR}${t}/dist`
  rmSync(distDir, { recursive: true, force: true })    // 先删净
  mkdirSync(distDir, { recursive: true })
  console.log(`\n[build] ${t} (${NODE_ENV})`)
  await run('npx', ['rollup', '-c', '--environment', `TARGET:${t},NODE_ENV:${NODE_ENV}`])
}
if (withTypes) {
  await run('npx', ['tsc', '-p', 'tsconfig.build.json'])            // 第一步：全量产声明碎片
  for (const t of targets) {
    await run('npx', ['rollup', '-c', 'rollup.dts.config.js', '--environment', `TARGET:${t}`])
  }                                                                   // 第二步：逐包捆 d.ts
}
```

三处设计值得停一下。其一，先删后建保证 dist 不混入上一次构建的陈旧文件——dev 与 prod 切换时尤其要紧。其二，为什么用 spawn 子进程而不是 rollup 的编程 API？因为配置文件从 `process.env.TARGET` 读身份，spawn 加 `--environment` 与手动在命令行执行的行为完全一致，可调试性好。其三，`--with-types` 分两步走，正对应 13.5 的两段式声明捆包。根 `package.json` 把入口收敛成脚本：`pnpm build` 即 `node scripts/build.js --with-types`，`pnpm build:prod` 再加 `--prod`。

配置主体按 formats 展开，每个格式一份完整输出：

```js
// rollup.config.js（节选，行内中文注释为本篇所加）
const entry = `packages/${TARGET}/src/index.ts`

export default formats.map((f) => ({
  input: entry,
  output: {
    file: outputName(f),
    format: outputFormat[f],
    exports: 'named',                                // cjs/iife 以具名属性导出
    name: f === 'global' ? name : undefined,         // IIFE 的全局变量名，vue 包为 MiniVue
    sourcemap: false,
    banner: `/* mini-vue ${TARGET} v${pkg.version} (${NODE_ENV}) */`,
  },
  plugins: [
    // exportConditions:['source'] → 跨包 @mini-vue/x 从兄弟包 exports.source 吃源码
    nodeResolve({ exportConditions: ['source'], extensions: ['.ts', '.js'] }),
    esbuild({
      define,
      target: 'es2018',
      minify: isProd,
      treeShaking: true,
      sourcemap: false,
    }),
  ],
  onwarn(w, warn) {
    if (w.code && (w.code.startsWith('CIRCULAR') || w.code === 'UNRESOLVED_IMPORT')) return
    warn(w)
  },
}))
```

`exports: 'named'` 让 `require('@mini-vue/vue').createApp` 直接可用；esbuild 插件承担 TS 转译、prod 压缩与树摇；`onwarn` 滤掉 monorepo 跨包循环引用的噪声告警。配置里还有一个 `define`，它引出了本章最好的一课。

## 13.3 __DEV__：define 为什么没替换它

库源码里散布着「仅开发态需要」的告警分支，用 `__DEV__` 常量守护。本仓库的写法是把源码态直接写死为 true：

```ts
// packages/shared/src/index.ts（节选，类型标注从原文件保留）
export const __DEV__ = true

export const EMPTY_OBJ: { readonly [key: string]: any } = __DEV__ ? Object.freeze({}) : {}
export const EMPTY_ARR: readonly any[] = __DEV__ ? Object.freeze([]) : []
```

为什么敢写死？因为源码形态下永远需要 dev 检查：`tsc` 类型检查与 vitest 都直接跑 src，不经过任何变量注入，写死 true 让源码零配置即可测试。runtime-core 另有五个文件（`warning.ts`、`apiCreateApp.ts` 等）各自声明同名的本地 `__DEV__`，reactivity 经 `import { __DEV__ } from '@mini-vue/shared'` 跨包引用。注意这个细节：无论哪种形态，它们都是**模块内的具名绑定**。

构建端准备了配套的注入配置，预期把 `__DEV__` 按模式替换成字面量：

```js
// rollup.config.js（节选）
const define = {
  __DEV__: isProd ? 'false' : 'true',
  'process.env.NODE_ENV': JSON.stringify(NODE_ENV),
}
```

按朴素预期：esbuild 的 define 会把源码里的 `__DEV__` 表达式替换掉，prod 产物中它变成 `false`，`__DEV__ ? freeze : {}` 退化成 `{}`，告警分支被树摇清空。实测结果并非如此。对比同一行源码在两份产物里的真实形态（本机构建，Node v22.22.2 / rollup 4.63.4）：

```js
// packages/shared/dist/shared.esm-bundler.js（dev 构建，第 33 行起）
const __DEV__ = true;
const EMPTY_OBJ = Object.freeze({}) ;
const EMPTY_ARR = Object.freeze([]) ;

// packages/shared/dist/shared.esm-bundler.prod.js（--prod 构建，压缩单行，节选）
…const y=!0,f=Object.proto…      // 定义处：__DEV__ 被压缩改名为 y，值 !0 即 true
…export{… y as __DEV__ …}        // 导出表：仍以 __DEV__ 之名导出（全文件仅此一处出现）
…Object.freeze({})…Object.freeze([])…   // prod 里 EMPTY_OBJ 仍被冻结
```

三个证据钉死结论：prod 产物里 `__DEV__` 的值仍是 true（压缩只是把 `true` 改写成 `!0`）；`Object.freeze` 照常执行——若 define 生效，这里应是空对象字面量；`__DEV__` 字样全文件仅剩导出表一处，因为导出名不可改写。**define 没有生效，当前 dev 与 prod 产物的语义差异只来自压缩**。

把两份产物的同一块代码完整并排摆一次（shared 包实测；dev 是 `dist/shared.esm-bundler.js`，prod 是 `--prod` 构建的 `dist/shared.esm-bundler.prod.js`，压缩单行，以下摘出相关片段）：

```js
// —— dev：__DEV__ 定义处（第 33 行）——
const __DEV__ = true;

// —— dev：EMPTY_OBJ / EMPTY_ARR（第 173–174 行）——
const EMPTY_OBJ = Object.freeze({}) ;
const EMPTY_ARR = Object.freeze([]) ;

// —— dev：导出表（第 178 行，列名有删节）——
export { EMPTY_ARR, EMPTY_OBJ, NOOP, PatchFlags, ShapeFlags, __DEV__, camelize, … };

// —— prod：定义处（紧接 PatchFlags 立即调用块之后）——
…(S||{});const y=!0,f=Object.prototype.toString,…

// —— prod：EMPTY_OBJ / EMPTY_ARR（全文件 Object.freeze 恰好出现 2 次）——
B=Object.freeze({}),G=Object.freeze([])

// —— prod：导出表（全文件仅此一处出现 __DEV__ 字样）——
export{G as EMPTY_ARR,B as EMPTY_OBJ,…,y as __DEV__,…}
```

逐格对读。定义处：dev 是具名的 `const __DEV__ = true`，prod 里这个内部名字被压缩器改成 `y`、值 `!0` 仍是 true。EMPTY 两行：prod 的 `Object.freeze` 原样执行，实测全文件恰好出现两次、一次不少。导出表：`y as __DEV__` 说明对外名字纹丝不动——导出名是公共 API，压缩器不敢碰，这也解释了为什么 `__DEV__` 字样恰好只剩这一处。

再补一张假想对照：假如 define 生效，prod 应该长什么样？本仓库产不出来，列的是官方方案的推演形态（替换规则见下一层根因）：

| 位置 | 实测的 prod | 假想的 prod（define 生效时） |
|---|---|---|
| `__DEV__` 的值 | `y=!0`，即 true | 各使用点替换为字面量 `false`；配合环境声明方案，声明本身不存在 |
| EMPTY_OBJ | `B=Object.freeze({})` | `{}`——`false ? Object.freeze({}) : {}` 死代码消除后只剩空对象 |
| EMPTY_ARR | `G=Object.freeze([])` | `[]`，同理 |
| dev 守卫的告警分支 | 保留在产物里 | `false` 前置的分支整段被树摇清掉 |
| dev 与 prod 的关系 | 行为一致，只差体积与可读性 | 行为分化：dev 有告警与冻结，prod 没有 |

假想列并非空想，它就是官方产物的样子。官方 rollup.config.js 的 resolveDefine 里，esm-bundler 格式把 `__DEV__` 替换为 `!!(process.env.NODE_ENV !== 'production')`（第 237 行），浏览器直用格式硬编码为 `String(!isProductionBuild)`（第 205 行）——消费端打包器或构建脚本再据自己的模式定生死。

根因在 esbuild define 的替换规则：define 只替换**自由标识符**（free identifier，未被任何局部作用域声明的名字），且发生在名称解析之后。模块顶层的 `export const __DEV__ = true` 是一个模块级具名绑定，它遮蔽（shadow）了同名的全局名字；此后源码里每一处 `__DEV__` 都解析到这个绑定，而不是 define 注册的那个全局替换项。为什么 esbuild 要这么设计？因为若无视绑定按词面替换，任何碰巧叫 `__DEV__` 的局部变量都会被误伤——保守规则在一般场景是对的，只是让「源码里声明过 `__DEV__`」的写法与 define 天然互斥。

官方实现正是绕开了这一点，方案分三层（均经 `third_party/vue-core` v3.5.x 核对）：

**第一层，环境声明。** `packages/global.d.ts` 只写 `declare var __DEV__: boolean`。环境声明（ambient declaration）只向类型系统注册名字，不产生任何运行时绑定。源码里因此不存在 `__DEV__` 的值声明，它在每个模块里都是自由标识符，define 畅通无阻。

**第二层，esm-bundler 转交决策权。** 该格式下把 `__DEV__` 替换为 `!!(process.env.NODE_ENV !== 'production')`。dev 还是 prod，交给消费端的打包器在业务构建时再定。

**第三层，浏览器直用格式硬编码。** global / esm-browser 没有转交机会，直接替换成 `String(!isProductionBuild)`。所以官方 dist 里 `vue.global.js` 与 `vue.global.prod.js` 成对存在。

本工程保持源码常量写法，代价是告警分支与冻结逻辑保留在 prod 产物里。这是一个已知取舍：换来源码零注入即可测试；改进路径也明确——改为环境声明、走官方的构建期替换，把「具名绑定遮蔽自由标识符」这一层捋清之后，切换只是机械工作。下一节处理另一个「构建期吃源码」的机制，这次是给跨包解析用的。

## 13.4 source 条件：解开先有鸡还是先有蛋

`vue` 包聚合五个兄弟包：`import ... from '@mini-vue/runtime-dom'` 这样的说明符（specifier，即 import 语句里的模块标识字符串）在构建 `vue` 时必须被解析。候选有两个：兄弟包的 dist 产物，或它的 `src/index.ts` 源码。若解析到 dist，构建顺序就成了硬依赖——必须先建好五个依赖包，而它们又依赖 shared，任何「单包构建」都不可行。

解法在每个包 `package.json` 的 `exports` 字段里。导出条件（export conditions）是 `exports` 中按消费环境逐层匹配的分支，解析方从上到下取第一个命中：

```json
// packages/vue/package.json（exports 字段）
{
  "exports": {
    ".": {
      "types": {
        "source": "./src/index.ts",
        "default": "./dist/vue.d.ts"
      },
      "source": "./src/index.ts",
      "import": "./dist/vue.esm-bundler.js",
      "default": "./dist/vue.cjs"
    }
  }
}
```

四个分支各有所指：`types` 服务 TypeScript（支持 source 时连类型都指向源码，否则回落 `dist/vue.d.ts`）；`source` 指向源码入口；`import` 命中 ESM 场景的打包产物；`default` 兜底 CommonJS 与旧解析器。`main` / `module` / `types` 旧字段保留在不感知 `exports` 的工具链里兜底，`sideEffects: false` 告知打包器可安全树摇。

钥匙在 13.2 已出现的这行：`nodeResolve({ exportConditions: ['source'] })`。它让 rollup 解析跨包说明符时优先命中 `source` 分支，直接吃兄弟包的 `src/index.ts`，与对方的 dist 是否存在无关。实测 `node scripts/build.js vue` 之后，`vue.esm-bundler.js`（164 KB）里 `@mini-vue` 说明符出现零次——五个依赖包被完整内联进单一 bundle。构建顺序依赖随之消失，任意一个包都可以独立构建。

这套条件匹配可以用 Node 当场验一遍。站在 `packages/vue` 目录（它的依赖里有 @mini-vue/shared），用 `require.resolve` 与 `import.meta.resolve` 各问一次「这个说明符解析到哪个文件」，加不加 `--conditions=source` 各跑一轮（Node v22.22.2 实测）：

| 问法 | 命令要点 | 解析结果（实测） | 命中的 exports 分支 |
|---|---|---|---|
| require，默认条件 | `node -e "require.resolve('@mini-vue/shared')"` | `…/shared/dist/shared.cjs` | default |
| require，加 source | 前者加 `--conditions=source` | `…/shared/src/index.ts` | source |
| import，默认条件 | `node --input-type=module -e "import.meta.resolve(…)"` | `…/shared/dist/shared.esm-bundler.js` | import |
| import，加 source | 前者加 `--conditions=source` | `…/shared/src/index.ts` | source |

四行读出两条规则。其一，条件按 exports 对象里的书写顺序取第一个命中：`source` 排在 `import` 之前，加上该条件后连 import 场景也改吃源码——Node 的 `--conditions` 与 rollup 的 `exportConditions` 是同一语义的两个入口，实验因此直接验证了构建配置的原理。其二，默认条件下 require 与 import 分别落到 default 与 import 分支，普通消费者拿到的永远是 dist 产物。实验还有个意外收获：某轮实测时 dist 目录只剩 prod 产物，require 照样解析到 `dist/shared.cjs`，随后当场抛 MODULE_NOT_FOUND——解析命中与文件存在是两回事，13.6 陷阱三的「解析到不存在的 dist」就是这个形态。

那业务项目的 Vite 会不会也命中 source、把整套 TS 源码吃进去？不会。`source` 是一个需要消费方显式声明的自定义条件，Vite 按官方条件表匹配 `import` / `module` / `default`，拿到的仍是 dist 产物。本仓库的示例工程则干脆用 alias 直接指到各包 `src/index.ts`（`examples/showcase/vite.config.ts`），走的是另一条路。类型这边还剩最后一问：`.d.ts` 怎么捆？

## 13.5 类型声明两段式：tsc 产碎片，rollup 捆单文件

TypeScript 消费者要的不是碎片，而是一个入口 `.d.ts`。但 `tsc` 按「每个源文件一份声明」产出，直接发布会把包内文件结构泄漏给消费者。本工程采用与官方相同的两段式。第一段，tsc 只发声明、不产 JS：

```json
// tsconfig.build.json（全文）
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": {
    "declaration": true,
    "emitDeclarationOnly": true,
    "declarationDir": "temp/types",
    "noEmit": false,
    "allowImportingTsExtensions": false
  },
  "include": ["packages/*/src/**/*.ts"]
}
```

`emitDeclarationOnly` 把输出限制为声明文件；`noEmit: false` 显式覆盖基座配置的 `noEmit: true`（日常类型检查不落盘）；声明落在中间目录 `temp/types`，不与源码或 dist 混放。第二段，`rollup-plugin-dts` 逐包把碎片捆成单文件：

```js
// rollup.dts.config.js（节选）
export default {
  input: `temp/types/${TARGET}/src/index.d.ts`,
  output: { file: `packages/${TARGET}/dist/${TARGET}.d.ts`, format: 'es' },
  plugins: [dts()],
}
```

输入是该包声明碎片的入口，输出是 `dist/<包名>.d.ts`。两段式各取所长：tsc 产出忠于源码的碎片零风险，捆包阶段再折叠成干净的单入口。

## 13.6 陷阱三则

**陷阱一：`"type": "module"` 下 CJS 产物的扩展名。** 现象：早期版本把 CJS 产物命名为 `vue.js`，Node 消费失败——旧版 Node 直接抛 `ERR_REQUIRE_ESM`；在 Node 22（本机 v22.22.2 实测）下形态更隐蔽：`require()` 返回一个空命名空间对象，属性赋值被静默丢弃，取 `createApp` 得到 undefined。根因：Node 按离文件最近的 `package.json` 的 `type` 字段解释 `.js` 文件，子包声明了 `"type": "module"`，`.js` 就按 ESM 解析；`.cjs` 扩展名则显式指定 CommonJS，不受 `type` 影响。官方包没有这个烦恼，因为 `vuejs/core` 的子包不写 `type` 字段，`.cjs.js` 以 `.js` 结尾自然落到 CommonJS。修复：`outputName` 中 cjs 格式固定输出 `.cjs` 后缀。

**陷阱二：`--environment` 的逗号语义。** 现象：曾试图一条命令传多值变量（形如 `TARGETS:vue,shared`），结果只有第一个值生效。根因经实测确认（rollup 4.63.4）：`--environment` 以逗号分隔多个「键:值」对，`TARGETS:vue,shared` 被切成 `TARGETS=vue` 与 `shared=true` 两个独立变量，值里的逗号无法存活。修复：多个变量写成多个键值对（`TARGET:x,NODE_ENV:y`，即 build.js 的现行写法）；需要「多个包」时不走环境变量，改由编排脚本逐包 spawn，每次只传一个值。

**陷阱三：漏配 source 条件，解析到不存在的 dist。** 现象：有一版配置的 nodeResolve 未带 `exportConditions: ['source']`，单独构建 `vue` 时 rollup 按常规顺序命中 `exports` 的 `import` 条件，指向兄弟包的 `./dist/*.esm-bundler.js`，而对方尚未构建、dist 是空目录，解析失败刷出大量 `UNRESOLVED_IMPORT`。根因即 13.4 的双候选默认落在 dist 一侧，构建顺序依赖悄悄回来了。修复：补回 `exportConditions: ['source']`，`onwarn` 同时滤掉 CIRCULAR 与 UNRESOLVED_IMPORT 噪声，日志只留真正的错误。

为什么踩过的坑值得逐条记下？因为构建配置的 bug 不像运行时 bug 有测试兜底，多数在「换个环境消费产物」时才发作，而那时的排查成本要翻倍。三个坑的共同点也在这里：它们都不是语法错误，而是工具语义与直觉的偏差。流水线至此搭完，可以回头验收整个系列了。

现在可以走得比 00 篇更细。`state.count = 1` 这行赋值，先落进 Proxy 的 `set` 拦截器（01），trigger 按两层账本找出订阅者，渲染副作用经 scheduler 入队而非同步重跑（02、08）；微任务到来，队列按 uid 父先子后地刷（08）；patch 遇到编译器留下的补丁标记，只比对动态文本那一处（11）；最终落盘的是一次 `textContent` 赋值（06）。改十次状态，仍只是这一次 DOM 操作。

为什么最后还要一章构建？因为 ②③④ 里每个环节的代码都散在七个包里，是构建流水线把它们捆成一个 `MiniVue`：esm-bundler 给打包器、cjs 给 Node、global 给直引页面，`__DEV__` 与跨包解析决定捆进去的是什么，`.d.ts` 决定 TypeScript 用户看到什么。十四张拼图，这是最后一块。

## 本章小结

构建编排由 `scripts/build.js` 扫包、重建 dist、逐包 spawn rollup 注入 `TARGET` 与 `NODE_ENV`；共享配置按 `buildOptions.formats` 把每包译成 esm-bundler / cjs / global 三种产物。`__DEV__` 因「具名绑定遮蔽自由标识符」未被 define 替换，dev/prod 的现行差异只来自压缩，官方的环境声明方案是改进路径。`exports` 的 source 条件配合 `exportConditions: ['source']` 让构建期直接吃兄弟包源码，构建顺序依赖消失；类型声明经「tsc 碎片 → rollup-plugin-dts 捆包」两段式产出单入口。

## 与官方实现的差距

以下均经 `third_party/vue-core`（v3.5.x）当前源码核对：

- **格式集合**：官方 `rollup.config.js` 定义七种格式（cjs、esm-bundler、global、global-runtime、esm-browser、esm-bundler-runtime、esm-browser-runtime），含浏览器直用 ESM 与 runtime-only 变体；本工程三种，覆盖主要消费形态，`FORMATS` 环境变量留了扩展位。
- **`__DEV__` 的处置**：官方为环境声明加分格式替换（13.3 三层方案）；本工程为源码常量的已知取舍。
- **dev/prod 产物布局**：官方仅对浏览器直用格式生成 `.prod.js` 伴随文件，esm-bundler 保留 `process.env.NODE_ENV` 判断交消费端；本工程 `--prod` 整套重建 dist，dev 与 prod 不共存于同一次输出。
- **编排能力**：官方 build.js 以 `runParallel(cpus().length, ...)` 按核数并行构建，`git rev-parse --short=7 HEAD` 取 commit 哈希经 `__COMMIT__` 替换项注入产物，发布流程附 `scripts/size-report.js` 体积报告；本工程串行 for-await，全量构建（七包加类型声明）实测 4.9 秒，并行的复杂度暂无收益。
- **插件面**：官方配置用 replace、json、commonjs、alias、inline-enums 等一组插件；本工程只留 node-resolve 与 esbuild 两个，七包均 private、按 `package.json` 存在性全部构建。
