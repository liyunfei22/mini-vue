# 02-渲染器与组件：一份 VNode 协议，跑通从模板到真实 DOM 的闭环

每天写组件、改数据、看着页面自己更新——这套体验的后半程（一堆 JS 对象怎么变成 DOM、数据变了之后怎么做到少动 DOM）都发生在一个叫「渲染器」的模块里。

如果你写过 `h('div', { onClick }, ...)`，却说不清 Vue 是怎么把这两行代码变成页面上会响应、会复用的交互元素的，这篇就是为你准备的。我对照一份逐行手写的 Vue3 内核复刻工程，把渲染器这位"翻译官"讲透：VNode 这种纯数据为什么能跨平台、patch 凭什么一条 switch 走天下、组件更新为什么是异步的，以及被吹上天的 LIS 到底在列表 diff 里帮了什么忙。读完你会收获一张完整的渲染链路地图——以后再聊性能优化，脑子里是真的有那张从依赖到 DOM 再回依赖的循环图。

## 为什么需要渲染器

模板编译的产物是渲染函数，渲染函数返回 VNode。VNode 是一格纯数据：`type` 记节点类型，`props` 记属性，`key` 记身份，`children` 记子节点，挂载后 `el` 指向真实 DOM。它从头到尾不碰任何 DOM API——这正是关键：同一棵树要渲染到 DOM、小程序、Canvas，只需要换一层"宿主操作"。

Vue 把脏活累活全交给渲染器，而渲染器的构造方式相当优雅：依赖注入。`createRenderer(options)` 接收一套宿主接口（createElement / insert / remove / patchProp / parentNode…），产出平台无关的渲染器；runtime-dom 把 DOM 版的 `nodeOps` 和 `patchProp` 组装成 options 后调一次 `createRenderer(rendererOptions)` 即得。渲染器回吐两个东西：底层 `render(vnode, container)` 和公用的 `createApp`，后者会记住容器上的上一个 vnode，下一次渲染拿它做新老对比。双方之间的通信协议只有 VNode：渲染器不认识 `document`，`document` 也不认识 vnode。

## 关键实现

### 1. shapeFlag 位图：三种类型的判定，一次"位与"完成

vnode 身上的 `shapeFlag` 是一张位图，组合标记"这个格子是什么、孩子是什么形态"。建 vnode 时按 type 编码：

```ts
// packages/runtime-core/src/vnode.ts —— 位图编码
const shapeFlag = isString(type)
  ? ShapeFlags.ELEMENT
  : isObject(type)
    ? ShapeFlags.STATEFUL_COMPONENT
    : isFunction(type)
      ? ShapeFlags.STATEFUL_COMPONENT
      : 0

// normalizeChildren 用"位或"追加孩子形态位
vnode.shapeFlag |= type // TEXT_CHILDREN | ARRAY_CHILDREN | SLOTS_CHILDREN
```

字符串命中 ELEMENT（1 << 0），对象或函数命中 STATEFUL_COMPONENT（1 << 2）；`normalizeChildren` 再按孩子的形态用"位或"打上 TEXT_CHILDREN（1 << 3）、ARRAY_CHILDREN（1 << 4）或 SLOTS_CHILDREN（1 << 5）。到了 patch 里分发就变成常数时间：

```ts
// packages/runtime-core/src/renderer.ts —— patch 五路分发
function patch(n1, n2, container, anchor, parentComponent, isSVG) {
  if (n1 === n2) return
  const { type, shapeFlag } = n2
  if (n1 && !isSameVNodeType(n1, n2)) {
    anchor = getNextHostNode(n1) // 先算锚点
    unmount(n1, parentComponent) // 再卸载旧节点
    n1 = null
  }
  switch (type) {
    case Text:     processText(n1, n2, container, anchor); break
    case Fragment: processFragment(n1, n2, container, anchor, parentComponent); break
    default:
      if (shapeFlag & ShapeFlags.ELEMENT)        processElement(n1, n2, container, anchor, parentComponent, isSVG)
      else if (shapeFlag & ShapeFlags.COMPONENT) processComponent(n1, n2, container, anchor, parentComponent)
  }
}
```

Text / Comment / Fragment 是三个独立 Symbol，直接 `switch(type)`；真正的元素和组件走 default 分支，靠 `shapeFlag & ELEMENT`、`shapeFlag & COMPONENT` 一次位与判完。五路分发（Teleport / Suspense 未实现）就这么齐了。Fragment 值得一提：`<template>` 里多个根节点会编译成它，挂载时渲染器用一前一后两个注释锚点把它围起来，subTree 就永远只有一个出口。位图之于 vnode，妙在"组合"本身就存在同一个字段里——`ELEMENT | ARRAY_CHILDREN` 就是"带数组孩子的元素"，读一次字段，判两类属性。

### 2. 组件实例 = effect + scope + scheduler

组件挂载时渲染器衔接三个动作：`createComponentInstance` 建实例 → `setupComponent` 跑 setup → `setupRenderEffect` 建渲染 effect。整个组件系统的核心浓缩在一行：

```ts
// packages/runtime-core/src/renderer.ts —— 组件实例的渲染 effect
const update = (instance.update = effect(componentUpdateFn, {
  scheduler: () => queueJob(update), // 依赖变 → 入微任务队列，而非同步重渲染
  allowRecurse: true,
}))
update.id = instance.uid // 队列按 id 升序插队（uid 越小越靠前）：父组件先更新
```

实例的更新函数就是一个 effect：渲染函数里读过的每个响应式变量都成了它的依赖。变量一变，effect 不会立刻重渲染，而是通过 scheduler 把 update 送进作业队列。scheduler 有两个关键点：按 `uid` 二分插队（父组件永远排在子组件前），以及用 QUEUED 位去重——同一刷新周期里，一个组件无论被触发多少次只会执行一次。队列刷新被排进一条微任务里逐条执行，执行期间被重新入队的作业会在同一轮继续被消费（flushJobs 对 `queue` 是活引用），新增的排到队尾同轮跑完；只有 pre/post 类回调显式推迟到下一轮，就这样循环直到队列稳定。这就是"更新是异步的、会批量合并"的根因。

每个实例还自带一个 `EffectScope`。setup 里创建的 effect、computed 全部挂在它名下，组件卸载时 `instance.scope.stop()` 一个动作全停掉，不漏监听。`nextTick` 的实现顺走的就是同一把流水：`currentFlushPromise` 正是那条排队的微任务，所以同步改完数据再调 `nextTick`，回调保证跑在整批渲染之后、拿到的是最新 DOM。

### 3. keyed diff 五步 + LIS：为什么移动最少

children 从一个数组变成另一个数组时，`patchKeyedChildren` 走五步。一二两步同步前后缀——头尾相同的节点直接 patch 复用；三四两步处理两个犄角：旧的没了=新增全挂，新的没了=剩下全卸。真正的重头戏是中间乱序区：

1. 用新 children 建 `keyToNewIndexMap`（key → 新下标）；
2. 遍历旧 children 找对应新位置，记入 `newIndexToOldIndexMap`（存 oldIndex+1，0 表示"这个新节点没有旧对应"），同时用 `maxNewIndexSoFar` 判断 moved——新下标一路递增说明顺序没乱，没必要动；
3. 只有 moved 才价值算 LIS，然后从后往前挂载/移动：

```ts
// packages/runtime-core/src/renderer.ts —— keyed diff 第 5.3 步
const increasingNewIndexSequence = moved ? getSequence(newIndexToOldIndexMap) : EMPTY_ARR
j = increasingNewIndexSequence.length - 1
for (i = toBePatched - 1; i >= 0; i--) {
  const nextIndex = s2 + i
  const nextChild = c2[nextIndex]
  const anchor = nextIndex + 1 < l2 ? c2[nextIndex + 1].el : parentAnchor
  if (newIndexToOldIndexMap[i] === 0) {
    patch(null, nextChild, container, anchor, parentComponent) // 新节点：挂载
  } else if (moved) {
    if (j < 0 || i !== increasingNewIndexSequence[j]) {
      move(nextChild, container, anchor) // 不在 LIS 里才需要移动
    } else j--
  }
}
```

`newIndexToOldIndexMap` 本质是把"旧下标序列"按新顺序重排。如果整条序列递增，说明相对顺序没乱；LIS 则是在必然乱序的中间区里，找出最长的那条不变量子序列——长度固定时，剩下需要移动的节点数最少。求 LIS 用的是耐心排序：二分维护一个递增的尾下标数组，再把前驱链回溯还原，O(n log n)。遍历为什么从后往前？因为要用"后一个已经就位的节点"的 el 当插入锚点，从前往后会把锚点越挪越远。

### 4. 事件 invoker：换回调不碰 addEventListener

最朴素的写法是更新一次就 remove + add 一次；真 Vue 的优化是事件调用器：每个事件名只 addEventListener 一次，之后换处理函数只改一个引用。这套机制值得完整保留，我的复刻就长这样：

```ts
// packages/runtime-dom/src/patchProp.ts —— patchEvent：换 handler 不换监听器（节选）
const veiKey = '__vei'
function patchEvent(el, rawName, _prevValue, nextValue) {
  const invokers = el[veiKey] || (el[veiKey] = {})
  const existingInvoker = invokers[rawName]
  if (nextValue && existingInvoker) {
    existingInvoker.value = nextValue // patch：只换值，零 DOM 操作
  } else {
    const name = rawName.slice(2).toLowerCase()
    if (nextValue) {
      const invoker = (invokers[rawName] = createInvoker(nextValue))
      el.addEventListener(name, invoker) // 一个事件名只绑一次
    } // else：新值为空且存在旧 invoker → removeEventListener（见工程源码）
  }
}
```

调用器本身只有几行，状态全藏在闭包里：

```ts
// packages/runtime-dom/src/patchProp.ts —— createInvoker：调用时拿最新版
function createInvoker(initialValue) {
  const invoker = (e) => {
    const value = invoker.value // 调用时永远拿最新版 handler
    if (isArray(value)) for (const h of value) h && h(e) // 数组 = 多个监听器
    else if (value) value(e)
  }
  invoker.value = initialValue
  return invoker
}
```

`el.__vei` 是缓存在元素上的调用器表，handle 更新是纯内存操作；触发时闭包里的 `invoker.value` 永远是最近一次 patch 的版本。处理函数还可以是数组，天然支持多个监听器。真源码里这套 `patchEvent` 在官方仓库历经几代演进（https://github.com/vuejs/core），复刻它让我第一次真切体会到"把状态藏在闭包里"对 DOM 操作频率的杀伤力。

## 动手验证

用配套工程直接跑这个最小示例，观察 keyed diff 的移动行为：

```ts
// 一个最小组件：验证 keyed diff 只移动不重建
import { createApp, h, ref } from '@mini-vue/runtime-dom'

const App = {
  setup() {
    const list = ref([{ k: 1, t: 'A' }, { k: 2, t: 'B' }, { k: 3, t: 'C' }, { k: 4, t: 'D' }])
    const rotate = () => { list.value = [...list.value.slice(1), list.value[0]] }
    const remove = () => { list.value = list.value.slice(0, -1) }
    return { list, rotate, remove }
  },
  render(ctx) {
    return h('div', [
      h('button', { onClick: ctx.rotate }, '前移一位'),
      h('button', { onClick: ctx.remove }, '删尾部'),
      h('ul', ctx.list.map((item) => h('li', { key: item.k }, `${item.t} (key=${item.k})`))),
    ])
  },
}
createApp(App).mount('#app')
```

点"前移一位"：ABCD 变 BCDA，keyed diff 只让 A 的最后一次 move 落盘，其余 li 全部复用；再给某个 li 挂上 `onClick`，在 DevTools 控制台用 `getEventListeners(el)` 查：无论点多少次按钮、经历多少轮 patch，监听器始终只有一个——这就是 invoker 只绑一次的现场。对照组是去掉 `key`——AB 转 BA 直接整棵卸载重建，事件全丢。这就是 Vue 反复强调 key 的原因，亲眼见过一次就不再忘。

## 真实踩过的坑

**坑一：先取锚点，再卸载。** patch 里 `!isSameVNodeType` 时我一度先 `unmount` 再取 `nextSibling` 当锚点，实测直接抛 NotFoundError。根因：卸载是把旧节点从 DOM 里摘除，此时拿已脱离文档的节点做相邻查询必然失败。正确顺序是先 `getNextHostNode(n1)` 拿锚点、再 unmount。

**坑二：编译产物的 children 不一定是数组。** 手写 `h()` children 是数组，但编译器路径里单 vnode 直接挂在 children 上、只打 ARRAY_CHILDREN 位，并不包一层数组。我最初按"children 必为数组"写 mountChildren，一跑编译产物就挂。根因是两个入口的形状约定不一致。统一在挂载前归一：`isArray(children) ? children : [children]`。

**坑三：LIS 里的 0 值才是真凶。** `newIndexToOldIndexMap` 用 0 表示"新节点无旧对应"，而旧下标要 +1 存储（否则存不下 0 语义）。我第一次直接用原始下标存，getSequence 也没跳过 0，结果新节点被误判成"该移动的旧节点"，顺排的列表渲染全乱了。根因：0 是一种哨兵值，凡是参与 LIS 算法就必须先滤掉。

## 三步走复盘

- **机制怎么串**：组件挂载时把渲染函数包成一条 effect，数据变化经 scheduler 进队列、合并成微任务批量执行；重跑产出新 vnode，patch 按 type 与 shapeFlag 分发，数组孩子走 keyed diff + LIS 保证移动最少，事件靠 invoker 换值不换监听器。
- **复刻第一行**：`patch(n1, n2, container)` 的 switch 骨架——先让一个元素能挂上屏，再逐路补 Text、Fragment、组件，最后才是 keyed diff 与调度。
- **讲给同事听**：「虚拟 DOM 的快不在多了一层结构，而在新旧对比后只把必要的 DOM 操作落盘——连列表移动都给你算成最少次数。」
