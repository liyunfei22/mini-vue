# 04-内核补全：Options 与 Composition 握手、过渡缓存、以及那条性能快速路径

> 读者画像：会写 Vue3、写过几个组件、但没亲手拆过内核的同学。本篇收获：把四条看似无关的能力串成一条主线——组件模型如何在 setup 之上兼容旧写法、渲染器如何留「开放点」给过渡与缓存、编译器又如何把「哪里会变」提前预判好交给运行时提速。所有代码都来自我手写的 mini Vue3 内核，与 Vue 官方思路一致但实现足够小，适合逐行读懂。

## 为什么需要补全这四块

上一轮我已经有了响应式、虚拟 DOM、组件的 setup 渲染链路和指令系统。但一个能自称「内核」的运行时还差四块拼图：

- `Options API` 是 Vue2 留下来的国民写法，`data/computed/methods` 必须能和 `setup` 共存，且优先级没有歧义；
- `Transition` 与 `KeepAlive` 是渲染器能力的「试金石」——它们要求渲染器在挂载、卸载、组件切换这几个硬节点上开放钩子；
- `patchFlag` 与 block 则是性能的脊梁：**编译器把「哪些节点会动态变化」预判好，运行时照单抄捷径**，这是 Vue3 相对 Vue2 全量 diff 最核心的改进思路。

这四块补齐后，一个模板编译进来、组件渲染出去、动态更新走快速路径的闭环才算完整。在你动手之前先记住一句话：**后两块的定位和前两块完全不同**——前两块是「能力」，解决能用不能用；后两块是「性能契约」，编译器生产标记、渲染器消费标记，两头谁是源、谁是宿，在下面都会看得清清楚楚。

## 关键实现

### Options 与 Composition：setup 先跑，options 后并

共存的关键是「执行顺序」与「公共面」。`setupStatefulComponent` 里先同步跑 `setup`，处理完返回值之后，才调用 `applyOptions` 把 `data/computed/methods/watch` 与生命周期选项追加进来：

```ts
// packages/runtime-core/src/component.ts（setupStatefulComponent 节选）
const { setup } = Component

if (setup) {
  // ...同步执行 setup，结果交给 handleSetupResult()
  handleSetupResult(instance, setupResult)
} else {
  finishComponentSetup(instance)
}
// Options API 追加：setup（Composition）之后合并 data/computed/methods/watch
if (isOptionComponent(Component)) {
  applyOptions(instance, Component)
}
```

`applyOptions` 的落点非常统一：`data/computed/methods` 全部写进 `instance.data` 这一个命名空间（真 Vue 也是 data 一个命名空间，官方实现见 [vuejs/core](https://github.com/vuejs/core) 的 `componentOptions.ts`）。`data` 拿 `reactive()` 包成响应式，`methods` 逐个 `bind(proxy)`，`computed` 转成响应式计算属性后也挂进 `data`——读时由响应式 getter 兜底解包：

```ts
// packages/runtime-core/src/componentOptions.ts（节选）
export function applyOptions(instance, options) {
  const { proxy } = instance
  if (options.data) {
    instance.data = reactive(options.data.call(proxy, proxy))
  }
  if (options.methods) {
    for (const key in options.methods) {
      instance.data[key] = options.methods[key].bind(proxy)
    }
  }
  if (options.computed) {
    for (const key in options.computed) {
      const userDef = options.computed[key]
      const getter = () => userDef.call(proxy)
      instance.data[key] = computed(getter)
    }
  }
}
```

公共面的一致性来自 `proxy` 的读取优先级。模板里 `this.msg` 会走上公共实例代理，顺序是 **setupState → props → data → ctx**：

```ts
// packages/runtime-core/src/componentPublicInstance.ts（get 拦截节选）
if (setupState !== EMPTY_OBJ && hasOwn(setupState, key)) return setupState[key]
else if (props !== EMPTY_OBJ && hasOwn(props, key)) return props[key]
else if (data !== EMPTY_OBJ && hasOwn(data, key)) return data[key]
else if (ctx !== EMPTY_OBJ && hasOwn(ctx, key)) return ctx[key]
```

所以同名冲突时 setup 赢——写混用组件时如果 data 里的字段被 setup 无声覆盖，回头看这个顺序就明白原因了。

`watch` 选项走的是另一条路：它直接在 `applyOptions` 里转成 `doWatch` 调用，绑定 `this=proxy`；键名带点号（如 `a.b.c`）时用 `createPathGetter` 按路径逐段取作为 watch 的 getter。生命周期选项则分两类处理：`beforeCreate/created` 当场同步执行，其余（`mounted`、`beforeUpdate`……）逐个登记进实例的钩子容器 `injectHook`，由渲染器在对应时机统一派发——和 `setup` 里用 `onMounted` 注册的钩子共用同一套容器，所以混用组件里两个写法注册的生命周期会按注册顺序一起执行。

### Transition：渲染器在三个硬节点上调用钩子

`Transition` 是一个不渲染自己的包装组件：它取唯一的子元素 vnode，往 `vnode.transition` 上挂一套钩子，剩下的交给渲染器。渲染器只在三处读它：`mountElement` 里 `insert` 前调 `beforeEnter`、`insert` 后调 `enter`，`unmount` 时调 `leave(el, done)`——动画结束后才真正 `remove`。

```ts
// packages/runtime-core/src/renderer.ts（挂载节选）
vnode.transition && vnode.transition.beforeEnter(el)
hostInsert(el, container, anchor)
vnode.transition && vnode.transition.enter(el)
```

钩子的内容很直白：`enter` 时先加 `v-enter-from/v-enter-active` 类，下一帧切换成 `v-enter-to`，等 `transitionend` 或超时兜底后清类；`leave` 对称处理。`nextFrame` 在真实浏览器是双 rAF 语义，我复刻时用双 `setTimeout` 近似——因为测试跑在 jsdom 里，没有真实的 `requestAnimationFrame` 节奏；`transitionend` 也存在同样的问题，所以必须配一个 `duration` 超时兜底，事件和定时器谁先到谁收尾，保证 `leave` 的 `done` 回调最终一定会被调用、DOM 一定会被移除。

### KeepAlive：隐藏代替卸载

KeepAlive 的诀窍是「缓存 vnode + 两个私有标记 `_deactivate` / `_activate`」，这是 KeepAlive 组件与渲染器的契约。缓存 Map 以 key（无 key 用组件类型）存下当前渲染的子组件，一旦这个子组件被换掉，卸载分支看到 `_deactivate` 就不卸载，而是把根元素 `display:none` 藏起来：

```ts
// packages/runtime-core/src/components/KeepAlive.ts（setup 节选）
const key = child.key != null ? child.key : child.type
const cachedVNode = cache.get(key)
if (cachedVNode && cachedVNode.component) {
  child = cachedVNode          // 回魂：返回缓存的同一个 vnode/实例
  child._activate = true
} else {
  cache.set(key, child)
}
child._deactivate = true       // 被换掉时由渲染器隐藏而非卸载
```

```ts
// packages/runtime-core/src/renderer.ts（卸载节选）
if (vnode._deactivate && vnode.component) {
  const rootEl = vnode.component.subTree && vnode.component.subTree.el
  if (rootEl) hostHideNode(rootEl)
  return
}
```

组件再切回来时，`processComponent` 的挂载入口看到 `_activate`，把元素显示出来并调用 `instance.update()` 刷新——**不重跑 setup**，所以内部状态（输入框内容、滚动位置、定时器）原样保留。注意这里是「显示 + 刷新」而不是重新 `mountComponent`：实例对象还是缓存里的那个，setup 不会执行第二次，元素的 DOM 也没有被销毁重建，只是从 `display:none` 状态醒过来。我复刻时砍掉了真 Vue 的 `include/exclude/max` 剪裁、`activated/deactivated` 钩子和动态存储容器，保留的就是这条最核心的「缓存实例对抗卸载」链路。

### patchFlag：编译器替渲染器预判

我复刻过程中最兴奋的一环：变换阶段遍历元素 props 时统计「动态点」，产出 `patchFlag` 位掩码与动态属性名单。`:class/:style` 占特定位，其余动态属性进 `PROPS` 位并逐个记入 `dynamicProps` 名单；动态属性名本身是变量时只能升级为 `FULL_PROPS` 全量比较；插值文本打 `TEXT` 位。

```ts
// packages/compiler-core/src/transforms/transformElement.ts（节选）
function markDynamicProp(flag, name, names) {
  if (name === 'class') return flag | PatchFlags.CLASS
  if (name === 'style') return flag | PatchFlags.STYLE
  names.push(name)
  return flag | PatchFlags.PROPS
}
```

渲染器的 `patchElement` 读到这些位后不走全量递 diff，而是「CLASS 只比 class、STYLE 只比 style、PROPS 只比名单里的键」，更新量直接砍到动态键的数量级。注意分类别忘了一类：动态属性名本身是变量（`:xx` 这种运行时才知道名字）时，编译器没法写死名单，只能打 `FULL_PROPS` 位，渲染器用新旧 props 的键并集逐个比——这是退化路径，能用但还是比朴素 diff 多了一层「去重排除」。

需要提醒的是 `patchFlag` 是基于编译期信息的静态分析：`v-if/v-for` 或运行时动态插入的节点它管不着，所以只有当元素来自模板编译路径、且动态信息可静态确定时快路径才成立。数据驱动的一切仍由响应式系统兜底。

### block 与静态提升：只 patch 会变的

同一趟编译里，根节点被标记为 block，codegen 生成 `_openBlock() + _createElementBlock(...)`。运行时创建 vnode 时，凡是 `patchFlag > 0` 或组件类型都会被收进 `currentBlock`，块根收集成 `dynamicChildren`。更新时尺寸匹配就只 patch 这份动态清单，整棵静态树连 diff 都不做：

```ts
// packages/runtime-core/src/renderer.ts（children 快速路径节选）
if (
  n1.dynamicChildren && n2.dynamicChildren &&
  n2.dynamicChildren.length > 0 &&
  n1.dynamicChildren.length === n2.dynamicChildren.length
) {
  patchBlockChildren(n1, n2, el, parentComponent)
  return
}
```

配合的另一半是静态提升：`patchFlag === -1` 的静态子树在 codegen 阶段被提取为 render 作用域顶层的 `const _hoisted_N`，跨渲染复用同一个 vnode，永远不会被 patch：

```ts
// packages/compiler-core/src/codegen.ts（节选）
const hoistedNodes = []
collectHoistedNodes(ast.codegenNode, hoistedNodes)
if (hoistedNodes.length) {
  for (let n = 0; n < hoistedNodes.length; n++) {
    // ...
    push(`const _hoisted_${n + 1} = ${tmp.code}`)
    newline()
  }
}
```

## 动手验证

把 Options 与 setup 混着写，再用模板编译看一眼产物。下面这段是我仓库里可跑的 demo 骨架：

```js
import { createApp, ref } from '@mini-vue/vue'

const app = createApp({
  setup() {
    const count = ref(0)
    return { count, inc: () => count.value++ }
  },
  data() {
    return { msg: '来自 options 的 data' }
  },
  computed: {
    double() { return this.count * 2 }
  },
  template: `<button @click="inc">count={{count}} double={{double}}</button><span>{{msg}}</span>`,
})
app.mount('#app')
```

`{{double}}` 在模板里读到的是 computed 值，`{{msg}}` 走 data 分支。让模板带上一块纯静态子树——对 `compile('<div id="a"><span>ok</span><b>{{n}}</b></div>')`，得到的 render 源码是（实测编译产物）：

```js
const { createElementVNode: _createElementVNode, toDisplayString: _toDisplayString,
        openBlock: _openBlock, createElementBlock: _createElementBlock } = Vue
const _hoisted_1 = _createElementVNode("span", null, "ok", -1)  // 静态子树被提升
return function render(_ctx, _cache) {
  with (_ctx) {
    return _openBlock(), _createElementBlock("div", { id: "a" }, [
      _hoisted_1,
      _createElementVNode("b", null, _toDisplayString(n), 1)   // 动态文本 → TEXT 位
    ], -1)
  }
}
```

`_openBlock()` 开启块收集，`{ id: "a" }` 是静态的所以没进动态名单；`_hoisted_1` 只创建一次，跨渲染都是同一个 vnode，渲染器见 `n1 === n2` 直接跳过 patch——这几行就是整条快速路径的缩影。给演示加上两块贴合约束的「外套」：`<Transition>` 包**一个**元素子节点（如带 `v-if` 的单 `<p>`，离开时先补 `v-leave-*` 类、动画结束才移除）；`<KeepAlive>` 包**子组件**并用 `:is` 在两套子组件间切换，给被缓存组件加自增计数器，切走再切回计数不归零，就说明缓存链路「不重跑 setup」是真的。

## 真实踩过的坑

复刻过程中有三处最深的坑，根因都写在代码注释里：

1. **TEXT_CALL 会包住纯静态文本。** 判断「是否有动态文本」时，如果看到 `TEXT_CALL` 节点就当成动态，会把纯静态文本误打成 `TEXT` 位，静态子树因此失去提升资格。根因是 `TEXT_CALL` 是个打包节点，必须剥开 `content` 看内层到底是 `Text` 还是插值/复合表达式。

2. **块快速路径会漏更新根节点自己的文本。** 像 `<div>{{x}}</div>` 这种根自身动态（带 TEXT 位）但没有独立动态子节点的情况，如果无脑走「只 patch dynamicChildren」，根自己的文本永远不更新。守卫条件必须是 dynamicChildren「非空且新旧等长」才走捷径，否则回退全量 diff。

3. **静态提升把 `_ctx` 依赖移出了 with 作用域。** 提升的节点被罩到 render 顶层，脱离 `with(_ctx)`；一旦静态子树里出现依赖 `_ctx` 的表达式（如 `renderSlot` 或动态工具函数 `_looseToNumber(...)`），运行时就抛 `ReferenceError`。所以提升条件必须保守：children 只能是纯静态形态、props 必须全是静态字面量。
