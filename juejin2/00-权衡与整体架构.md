# 00 · 权衡与整体架构：Vue 3 为什么长成这样

> 本篇是系列第一篇。在进入任何具体实现之前，先回答三个设计层面的问题：声明式框架用什么换取了可维护性；编译器与运行时如何分工；官方仓库为什么拆成七个包。后续五篇分别实现其中一块，本篇给出它们的总装图。

## 引言

使用 Vue 3 的工程师大多能准确描述框架的对外行为：修改响应式状态，视图随之更新；模板中的 `v-if`、`v-for` 会被框架处理；组件可以嵌套复用。但如果追问一层——状态变更如何传播到视图、模板如何变成可执行的渲染逻辑——答案往往就模糊了。本系列的目的就是把这一层补齐：跟随一个从零实现的 mini-vue 工程，逐个子系统地重写 Vue 3 的内核。

本篇先不写代码，只建立三个认知框架，后续所有篇章都在这三个框架内展开。

## 一、命令式与声明式

以「把 `div` 的文本更新为 `hello`」为例。命令式实现关注过程，每一步操作都由开发者给出：

```js
const div = document.querySelector('#app')
div.textContent = 'hello'
```

声明式实现只描述结果，过程交由框架完成：

```html
<div>{{ msg }}</div>
```

两种范式的差异可以概括为一次交换：声明式用运行时性能换取可维护性。开发者不再维护「如何从旧状态到达新状态」的过程代码，代价是框架必须自己计算出这个差异——而计算差异本身需要消耗运行时资源。项目规模越大，过程代码的维护成本增长越快，这笔交换就越划算。这是 Vue、React 等现代框架共同的前提。

由此得出本系列的第一个结论：**声明式框架的内部，必然存在一个命令式层**。Vue 中所有 `document.createElement`、`textContent` 赋值都集中在这个命令式层——渲染器中，其余部分（响应式系统、编译器）分别负责「何时需要重新执行」与「如何生成渲染逻辑」。

## 二、运行时与编译时

框架实现有三个可能的落点：纯运行时、纯编译时、两者结合。

**纯运行时**：框架只提供 `h` 这样的节点描述函数，渲染逻辑由开发者手写。

```js
import { h, createApp } from 'vue'
createApp({
  render: () => h('div', { id: 'app' }, 'hello'),
}).mount('#root')
```

灵活性最高，但开发者负担重，且框架对「将要渲染的内容」一无所知，只能做通用处理。

**纯编译时**：把声明式代码在构建期直接编译为等价的命令式代码（如 Svelte 的路线）。性能上限最高——没有运行时框架的介入，但灵活性受损：动态结构（运行时才能确定的组件、插槽内容）难以完全静态化。

**Vue 的选择是结合**：运行时保留通用的虚拟 DOM 渲染能力，编译器则利用模板的确定性尽可能「泄漏」信息给运行时。官方文档对模板与渲染函数的比较明确指出了这一点：渲染函数更灵活，但模板具有**确定的语法，更容易做静态分析**。Vue 3 的编译优化——补丁标记（patch flags）、缓存静态内容、区块（block）——全部建立在这个前提上：编译期能确定「哪些节点可能变化、以何种方式变化」，运行时就能跳过确定不变的部分。

这也解释了本系列的实现顺序：先实现运行时（响应式、渲染器），再实现编译器，最后把编译器产出的优化信息接回渲染器。运行时是自洽的，编译器是增量收益。

## 三、虚拟 DOM 的定位

官方文档将虚拟 DOM 定义为一种编程概念：将目标 UI 通过数据结构「虚拟」地表示出来，保存在内存中。对 Vue 而言，虚拟节点（vnode）承担两个职责：

1. **声明式描述的载体**。渲染函数返回 vnode 树，渲染器对比新旧两棵树、将必要的更新应用到真实 DOM——文档将这一过程概括为渲染管线的三个阶段：**编译**（模板编译为渲染函数）、**挂载**（渲染器执行渲染函数、创建真实 DOM）、**更新**（依赖变化后副作用重新运行，比对并应用差异）。
2. **跨平台协议**。vnode 是纯数据，不含任何平台 API。渲染核心只依赖注入的宿主操作集（`createElement`、`insert`、`patchProp` 等），替换这一层即可对接 canvas、SSR 等非浏览器环境。

关于性能需要澄清一点：虚拟 DOM 并不比精心手写的命令式代码更快——多出一层中间表示必然有成本。它的价值在于为声明式范式提供了「性能可接受的下限」，且这个下限可以被编译期信息持续抬高（见 04 篇）。理解这一定位，才能理解 Vue 3 相对 Vue 2 的优化为什么发生在编译器而不是运行时。

## 四、分包架构

Vue 3 官方仓库按职责拆为七个包（本系列工程按同样结构镜像实现）：

| 包 | 职责 | 代表导出 |
|---|---|---|
| `shared` | 工具与常量：类型判断、ShapeFlags/PatchFlags 位图 | `isObject` `hasChanged` |
| `reactivity` | 响应式系统：代理、依赖收集、副作用与作用域 | `reactive` `ref` `computed` `effect` |
| `runtime-core` | 平台无关的渲染器、组件模型、调度 | `createRenderer` `h` |
| `runtime-dom` | 浏览器适配：DOM 操作、属性/事件补丁 | `createApp` |
| `compiler-core` | 平台无关的模板编译：parse/transform/codegen | `baseCompile` |
| `compiler-dom` | 浏览器专属的编译选项 | `compile` |
| `vue` | 聚合入口：运行时 + 运行时编译器 | `createApp` `compileToFunction` |

依赖方向严格单向：

```
shared → { reactivity, compiler-core }
reactivity  → runtime-core → runtime-dom
compiler-core → compiler-dom
(以上全部) → vue
```

拆分的工程动机有三个。其一，**平台无关的核心可复用**：`runtime-core` 不认识 `document`，换一套宿主操作即可移植。其二，**编译与运行可分离**：预编译场景可以只引入运行时包，不承担编译器体积——这是按需加载（tree-shaking）的前提。其三，**边界即测试边界**：每个包有独立的测试集，行为锚定在测试上。

## 五、一次更新的完整数据流

把七个包串起来，一次「状态变更到 DOM 更新」的路径如下：

```
"<div>{{ count }}</div>"
  │ ① vue: compileToFunction —— 模板经 compiler 编译为渲染函数（运行时编译）
  ▼
render 函数（返回 vnode 树）
  │ ② runtime-dom: createApp(App).mount('#root')
  ▼
runtime-core: setupRenderEffect
  instance.update = effect(componentUpdateFn, { scheduler })
  │ ③ count 变更 → reactivity: trigger → scheduler → 调度队列（微任务批量执行）
  ▼
componentUpdateFn 重跑 → 新 vnode 树
  │ ④ runtime-core: patch(n1, n2) —— 比对新旧树，按补丁标记走快速路径
  ▼
runtime-dom: hostPatchProp / hostInsert —— 差量操作真实 DOM
```

四个环节各有归属：①③ 依赖编译器与响应式系统，②④ 依赖渲染器。其中 ③ 是理解 Vue 更新行为的关键——组件更新不是同步发生的，多个状态变更会被合并为一次渲染，这是调度器的职责，02 篇展开。

## 六、本系列的范围与已知简化

完整复刻 Vue 3 内核不在预期内，以下简化是明确决策而非遗漏：

- 表达式编译采用 `with(_ctx)` 方案，官方为 `prefixIdentifiers`（CSP 兼容、可静态分析），03 篇分析两者的取舍；
- 不实现 SSR/hydration、compiler-sfc（`.vue` 单文件组件）、Teleport/Suspense；
- Transition、KeepAlive 为核心链路的简化版（保留与渲染器的协作契约，裁剪配置项），04 篇逐项列出差异;
- 区块快速路径在动态节点数变化时回退全量比对。

每篇正文设「与官方实现的差异」一节，专门交代该子系统的简化点。

## 小结

声明式框架用运行时成本换取可维护性，其内部必然存在命令式层（渲染器）与「何时重渲染」的判定机制（响应式系统）；编译器利用模板语法的确定性向运行时泄漏优化信息，这是 Vue 3 性能改进的主要来源；七个包按「平台无关/平台相关、编译期/运行期」正交切分，依赖单向。后续五篇按「响应式系统 → 渲染器与组件 → 编译器 → 内核补全 → 构建发布」的顺序逐个实现。
