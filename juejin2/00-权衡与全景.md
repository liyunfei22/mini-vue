# 00 · 权衡与全景：Vue 3 为什么长成这样

在写任何一行代码之前，我们先花一章回答三个问题：为什么框架要用声明式来写界面？虚拟 DOM 到底解决了什么问题？编译器和运行时是怎么分工的？

这三个问题看起来很「务虚」，但它们决定了后面十三章的每一步。比如：为什么响应式系统是整个内核的地基？为什么渲染器里看不到一行 `document.createElement`？为什么模板编译器要单独占三个包？在这个过程中，我们会不断遇到「权衡」这个词——框架设计里到处都是权衡，几乎没有哪个决策是免费的。

本章是全系列唯一不贴仓库代码的一篇。它要建立的是一张地图：先认识三种范式取舍，最后把 mini-vue 的七个包放到这张地图上。

## 1.1 命令式与声明式

先看一段自然语言需求：

```text
- 获取 id 为 app 的 div 标签
- 把它的文本内容设为 hello world
- 为它绑定点击事件
- 点击时弹出提示：ok
```

把它翻译成原生 JavaScript，几乎是逐行对应：

```js
const div = document.querySelector('#app')   // 获取 div
div.textContent = 'hello world'              // 设置文本
div.addEventListener('click', () => {        // 绑定事件
  alert('ok')
})
```

代码描述的是「做事的过程」，一步接一步。这就是命令式：**关注过程**。

同样的需求，用 Vue 来写是什么样？

```html
<div id="app" @click="alert('ok')">{{ msg }}</div>
```

这里没有「获取」「再设置」「再绑定」的过程，只描述了最终结果：一个 div，文本是 `msg`，点击时弹提示。这就是声明式：**关注结果**。过程去哪了？被 Vue 封装掉了。我们等于在对 Vue 说：我要的就是这么一个东西，怎么造出来是你的事。

由此可以推出一个很重要的结论：**Vue 暴露给用户的是声明式，内部实现一定是命令式的**。`querySelector`、`textContent`、`addEventListener` 这些调用一行都不会少，只是从用户的代码里搬进了框架里。后面第 5 篇要写的渲染器，就是框架内部那个命令式层。

## 1.2 用性能换可维护性

声明式更「高级」，那它有没有代价？这里先抛一个结论：**声明式代码的性能，不会优于等价的命令式代码**。

原因不难想。命令式代码里，每一步 DOM 操作都是开发者明确指定的，做到极致就是「只做必要的修改」。而声明式代码只给出了「结果」，框架要自己算出「从旧结果到新结果」需要哪些修改——这个计算本身就是开销。上例中，直接写 `div.textContent = 'hello world'` 只有一次 DOM 操作；而 Vue 需要先对比新旧两次描述，再决定要不要改、改哪里。

那为什么大家还选声明式？因为**可维护性**。项目规模一大，「维护每一步过程」的成本增长得比业务本身还快：状态散落在各个回调里，改一处要在三处同步。声明式把「怎么改」收归框架，开发者只维护「现在应该是什么样」。

代价到底有多大，数一数就直观了。假设界面有一百个节点、用户一次操作只影响其中一个：命令式写法你自己知道是哪个，一次 DOM 操作搞定；声明式框架不知道，它得先把新旧两份描述整个比一遍（一百次比较），才能确认「哦，只有这一个要改」——最终 DOM 操作仍然是一次，但多付了一百次比较的成本。这个「比较」就是后文反复出现的 diff，Vue 全部的性能故事，都是围绕怎么把这笔比较的开销往下压展开的。

性能和维护性之间，Vue 选择了后者的同时，用两个手段把性能损失压住：一是虚拟 DOM（让比较变便宜，下一节），二是编译期优化（让比较根本不发生，第 11 篇）。记住这个主线，后面每一章都站在它上面。

## 1.3 虚拟 DOM：让「算差异」变便宜

声明式框架的核心工作量在「找出新旧描述的差异」。直接对真实 DOM 做对比可行吗？想想 DOM 节点的成本：一个元素对象身上挂着几十个属性和方法。拿它做频繁比对，太重了。

虚拟 DOM 的思路是：用**轻量的普通 JavaScript 对象**描述 UI，比对在这层对象上做，比对完把必要的修改落回真实 DOM。官方文档对它的定义是「将目标所需的 UI 通过数据结构“虚拟”地表示出来，保存在内存中」。这个轻量对象就是 vnode（虚拟节点），大概长这样：

```js
// 一个 vnode：对「一个 div、带一个动态文本」的纯数据描述
const vnode = {
  type: 'div',            // 是什么
  props: { id: 'app' },   // 有什么属性
  children: 'hello',      // 孩子是什么
  el: null,               // 挂载后指向真实 DOM（回写通道）
}
```

注意两点。第一，vnode 从头到尾不调用任何 DOM API，它就是一份纯数据。第二，正因为是纯数据，它成了渲染器与外界唯一的「通信协议」——渲染核心不认识 `document`，换一套宿主操作就能渲染到别的平台。这两点分别是第 5 篇和第 6 篇的起点。

「算差异」具体指什么？看一个最小的例子。旧描述和新描述各是一棵 vnode 树，只有一处文本不同：

```js
// 旧树（上次渲染的描述）          // 新树（数据变了之后的描述）
{ type: 'ul', children: [          { type: 'ul', children: [
  { type: 'li', children: 'a' },     { type: 'li', children: 'a' },   // 没变
  { type: 'li', children: 'b' },     { type: 'li', children: 'B' },   // 文本变了
] }                                ] }
```

diff 的职责就是回答：新树相对旧树，最小要做什么？这里的答案是「第二个 li 的文本节点改成 B」——一次 `textContent` 赋值，两个 `li` 元素原样保留。注意比较发生在轻量的 vnode 上、结论落到真实 DOM 上，这正是虚拟 DOM「让比较变便宜」的含义。

还有一个常见误解要澄清：虚拟 DOM 不是为了「比手写 DOM 快」——多一层中间表示必然有成本。它买到的是「声明式范式下可接受的性能下限」，而这个下限还能被编译期信息不断抬高（第 11 篇的补丁标记与静态提升正是干这个的）。

## 1.4 运行时与编译时

框架实现落在哪一段？有三种选择。

**纯运行时**：框架只提供描述函数，渲染逻辑用户自己写。

```js
import { h, createApp } from 'vue'
createApp({
  render: () => h('div', { id: 'app' }, 'hello'),
}).mount('#root')
```

灵活，但写起来繁琐，而且框架对「要渲染什么」一无所知，只能做通用处理。

**纯编译时**：构建期把声明式代码直接编译成命令式代码（Svelte 的路线）。性能上限最高，因为运行时根本没有框架存在；代价是动态结构（运行时才能确定的组件、插槽）难以完全静态化。

**运行时 + 编译时**：Vue 的选择。运行时保留通用的虚拟 DOM 能力，编译器则利用模板语法的确定性，把「哪里会变、怎么变」提前算好塞给运行时。官方文档说得很直白：渲染函数更灵活，但模板「具有确定的语法，更容易对模板做静态分析」——Vue 3 的三大编译优化全部建立在这个前提上。

这也解释了本系列的写作顺序：先写运行时（响应式、渲染器），再写编译器，最后把编译器的产出接回渲染器。运行时自己就能转，编译器是增量收益。

## 1.5 七个包与一次更新

把上面的地图落到代码上。Vue 3 官方仓库按职责拆成七个包，本仓库按同样结构实现：

| 包 | 一句话职责 |
|---|---|
| `shared` | 工具与常量（类型判断、ShapeFlags/PatchFlags 位图） |
| `reactivity` | 响应式系统：代理、依赖收集、副作用 |
| `runtime-core` | 平台无关的渲染器、组件模型、调度 |
| `runtime-dom` | 浏览器适配：DOM 操作、属性/事件补丁 |
| `compiler-core` | 平台无关的模板编译：parse/transform/codegen |
| `compiler-dom` | 浏览器专属的编译选项 |
| `vue` | 聚合入口：运行时 + 运行时编译器 |

依赖方向严格单向：`shared` 被所有人用；`reactivity` 不认识渲染器；`runtime-dom` 组装 `runtime-core`；`vue` 聚合一切。上层永远不反向依赖下层——这是贯穿全仓库的铁律。

现在把所有包串起来，看一次完整的更新。从模板字符串到 DOM 更新，路径是：

```text
"<div>{{ count }}</div>"
  │ ① vue 包：compileToFunction 把模板编译成渲染函数
  ▼
render 函数（返回 vnode 树）
  │ ② runtime-dom：createApp(App).mount('#root')
  ▼
runtime-core：组件挂载时注册渲染副作用
  instance.update = effect(componentUpdateFn, { scheduler })
  │ ③ count 变了 → reactivity 的 trigger → 调度队列（微任务里批量执行）
  ▼
渲染副作用重跑 → 新 vnode 树
  │ ④ runtime-core：patch(旧 vnode, 新 vnode)，只把差异落盘
  ▼
runtime-dom：真实 DOM 更新
```

四个环节各归其主：① 是编译器的事（第 9–11 篇），③ 是响应式的事（第 1–4 篇），②④ 是渲染器的事（第 5–8 篇）。

① 的产出不是比喻，是真实代码。对本仓库跑 `compile('<div id="app"><p class="t">static</p><li v-for="(item, i) in list" :key="i">{{ item }}</li></div>')`，得到的渲染函数源码长这样（实测产物，第 10 章会逐行指认每一项的来历）：

```js
const { createElementVNode: _createElementVNode, renderList: _renderList, toDisplayString: _toDisplayString, openBlock: _openBlock, createElementBlock: _createElementBlock } = Vue
const _hoisted_1 = _createElementVNode("p", {class: "t"}, "static", -1)
return function render(_ctx, _cache) {with (_ctx) {
    return _openBlock(), _createElementBlock("div", {id: "app"}, [_hoisted_1, _renderList(list, (item, i) => _createElementVNode("li", {key: i}, _toDisplayString(item), 9, ["key"]))], -1)
  }
}
```

现在能读懂四个细节了：静态的 `<p>` 被提到函数外只创建一次（第 11 篇的静态提升）；`v-for` 变成了 `_renderList` 调用（第 10 篇）；末尾的 `9` 和 `["key"]` 是编译器塞给渲染器的「更新类型标记 + 动态属性名单」（第 11 篇）；开头的 `_openBlock()` 则是「把动态节点打平收集」的起手式（同样第 11 篇）。

其中 ③ 藏着一个很多人答不清的问题：改十次状态，组件会重渲染十次吗？答案是不会——更新被合并成一次微任务批量执行，这是调度器的功劳（第 8 篇）。

「渲染核心不认识浏览器」也不是口号，可以亲手验证。在本仓库执行：

```bash
grep -rn "document\.\|window\." packages/runtime-core/src/   # 零命中
grep -rn "document\." packages/runtime-dom/src/nodeOps.ts     # 命中一堆
```

所有 DOM API 集中在 `runtime-dom` 的 nodeOps 一张表里，`runtime-core` 一行都没有——第 5 篇就是把这张表「注入」进渲染器的过程。

## 1.6 本系列的地图

全系列十四章，正好是这张地图的顺时针展开：

- **第 1–4 篇 · 响应式**：从手写一个最小的「桶」开始，逐步长出 track/trigger、依赖清理、computed、ref、watch。读完能回答「`state.count = 1` 之后谁来重跑、凭什么找到该重跑的函数」。
- **第 5–8 篇 · 渲染器**：vnode 怎么挂成真实 DOM、属性和事件怎么打补丁、两组子节点怎么比、组件为什么是「带副作用的子树」。读完能回答「虚拟 DOM 到底快在哪」。
- **第 9–11 篇 · 编译器**：模板怎么被状态机啃成 AST、AST 怎么变成渲染函数源码、编译器怎么把「哪里会变」提前告诉渲染器。
- **第 12–13 篇 · 补全与交付**：Options API、Transition、KeepAlive 这些「组合拳」，以及把七个包打成能发布产物的构建流水线。

每章的结构一致：先从一个能运行的小例子出发，写出朴素版，指出它做不到什么，再看仓库实现怎么演进过去；章末有小结、源码索引、与官方实现的差距和动手验证。

需要先说明几个全系列的已知简化，免得读到一半产生困惑：表达式编译用 `with(_ctx)` 方案（官方是 `prefixIdentifiers`，第 10 篇分析取舍）；不实现 SSR、`.vue` 单文件编译、Teleport/Suspense；Transition 与 KeepAlive 是保留核心链路的简版（第 12 篇逐项列差距）。

## 本章小结

声明式用性能换可维护性，其内部必然存在一个命令式层（渲染器）和一个「何时该重跑」的判定机制（响应式系统）。虚拟 DOM 是让「算差异」变便宜的轻量中间层，同时也是跨平台协议。Vue 选择运行时与编译时结合：运行时保底，编译器利用模板的确定性持续加码优化。七个包按这条主线正交切分、依赖单向。

把工程跑起来，对照 1.5 节的数据流走一遍：

```bash
pnpm install
pnpm test           # 全套行为测试
pnpm dev:showcase   # 模板驱动的展示页：点按钮，观察「状态变 → 页面自己更新」
```
