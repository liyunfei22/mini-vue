# 03 模板编译器：把「模板字符串」变成「render 函数」

如果你已经会写 Vue3，天天打 `{{ msg }}`、写 `v-for`，这一篇带你钻进模板到页面的那几毫秒：模板是怎么被解析、被改写、最后变成一个能 `new Function` 出来的 render 函数的。本篇收获：状态机解析的全貌、transform 管线「进入/退出」的设计动机、v-if 本质是一组 branches、v-for 本质是 renderList，以及 codegen 里 `with(_ctx)` 这个反直觉的取舍。看完你就能回答：`nextTick` 之前，模板到底经历了什么。

## 为什么需要

两条路都能把组件画出来：手写 render 函数，或写模板。render 是程序式——你要自己拼 h、自己算条件；模板是声明式——`v-if="ok"` 一眼看懂。但**浏览器根本不懂模板**，必须有个编译器翻译成程序。

更关键的是，模板的「形状是确定的」：编译器在编译期就知道哪里是静态文本、哪里引用变量、哪个 vnode 需要 key diff。这些信息提前算好、打进产物（就是 codegen 里的 patchFlag 和静态提升），运行期照单执行——这是模板编译区别于运行时硬拼的根本价值。

整个编译器是一条三站流水线：**parse**（模板 → AST）→ **transform**（改写 AST，收集优化信息）→ **codegen**（AST → 函数源码字符串）。下面逐个说。

## 关键实现

### 一、parse：一个光标滚过整份模板

解析不写正则大法，而是状态机。核心对象是一个一直指向「还没解析的部分」的滚动源字符串：

```ts
// packages/compiler-core/src/parse.ts
export interface ParserContext {
  source: string
  options: ParserOptions
  offset: number
}

function advanceBy(context: ParserContext, n: number): void {
  const { source } = context
  context.source = source.slice(n)
  context.offset += n
}
```

主循环只看 `source` 开头一两个字符就能分流：`<` 打头是标签/注释，`{{` 打头是插值，否则是文本——这就是「状态机」的全部秘密。

```ts
// packages/compiler-core/src/parse.ts —— parseChildren 主循环（节选）
while (!isEnd(context, ancestors)) {
  const s = context.source
  let node
  if (s[0] === '<') {
    if (s[1] === '!')  { /* 注释 / DOCTYPE：advanceBy 跳过 */ }
    else if (s[1] === '/') { break }        // </ 父标签，结束本层
    else { node = parseElement(context, ancestors) } // 递归下沉
  }
  if (!node) node = parseInterpolation(context, mode) || parseText(context, mode)
  if (node) children.push(node)
}
```

不同区域语法规则不同，用 `TextModes` 标注。重要性被低估：`<script>` 里的 `{{ not_an_interpolant }}` 绝不能当插值解析（对齐真 Vue：RAWTEXT 内 `{{ }}` 是纯文本；早期版本曾漏掉这道 mode 门控，已修复）。

```ts
// packages/compiler-core/src/parse.ts
const enum TextModes { DATA, RCDATA, RAWTEXT, CDATA, ATTRIBUTE_VALUE }

function getRawTextOrRcDataMode(tag: string): TextModes | undefined {
  if (tag === 'textarea' || tag === 'title') return TextModes.RCDATA // {{}} 仍有效
  if (tag === 'style' || tag === 'script') return TextModes.RAWTEXT   // 全当纯文本
}
```

enum 里还有两档没在上面露面：CDATA 给 SVG 等「外来内容」语境、ATTRIBUTE_VALUE 给属性值内的实体解码语境预留，是官方为浏览器边角场景备的档位；mini 的模板解析没走到这两种语境，所以实际生效的就是上面三档。

元素是递归解析的：`parseElement` 读标签名和属性后，把自己压进 `ancestors`，递归 `parseChildren` 生成 children，再吃结束标签；`isEnd` 就是看滚动源里有没有出现 `</父标签` 或到 EOF。属性解析在 `parseAttribute`：`:`/`@`/`#`/`v-` 前缀会被标记为 DIRECTIVE 节点，并顺手拆出 arg（`:click`）和 modifiers（`.once`）。

### 二、transform：把「声明」改写成「可执行指令」

parse 产出的 AST 是声明性的（`<p v-if>` 只是一个属性），codegen 需要的是可执行的形状（`(ok) ? vnode : vnode`）。transform 干三件事：深度遍历逐节点跑变换、收集运行时 helpers、定出 `root.codegenNode`。

管线最精妙的是**进入/退出两阶段**：节点变换进入时执行，返回的函数放进 exit 栈，等子树遍历完再**逆序**执行。为什么？因为 v-if/v-for 这类结构变换必须先把结构换掉，生成 codegenNode 的 `transformElement` 得在结构定稿后的退出阶段才动手——顺序一错，v-if 的 children 永远等不到转化。

```ts
// packages/compiler-core/src/transform.ts —— traverseNode 节选
for (let i = 0; i < nodeTransforms.length; i++) {
  const onExit = nodeTransforms[i](node, context)
  if (onExit) exitFns.push(onExit)
  if (!context.currentNode) return
  node = context.currentNode // 结构变换可能替换了节点，后续变换跟新节点走
}
// ...按类型分发遍历子节点...
let i = exitFns.length
while (i--) exitFns[i]()   // 逆序执行退出钩子
```

v-if 用 `branches` 数据结构把一串兄弟折叠成一个 IF 节点：

```
<div v-if="a"/><div v-else-if="b"/><p v-else/>
→ IF { branches: [
    { condition: a, children: [div] },
    { condition: b, children: [div] },
    { condition: undefined, children: [p] },  // else 无条件
  ] }
```

v-else 的回链靠 `context.parent + childIndex` 找前一个兄弟，必须是 IF 才能挂上去；挂完在退出阶段把原元素从兄弟列表里摘掉。此时有个隐蔽细节（见「踩过的坑」）：删除要用身份查找而非 childIndex。

```ts
// packages/compiler-core/src/transforms/transformIf.ts —— v-else 回链
const prevSibling = context.parent!.children[context.childIndex - 1]
if (prevSibling && prevSibling.type === NodeTypes.IF) {
  prevSibling.branches.push({
    type: NodeTypes.IF_BRANCH,
    condition: dir.name === 'else-if' ? dir.exp : undefined,
    children: [node],
  })
  return () => {                       // 退出阶段：摘除原元素
    const list = context.parent!.children
    const index = list.indexOf(node)   // 身份查找，绝不用 childIndex
    if (index > -1) { list.splice(index, 1); context.currentNode = null }
  }
}
```

v-for 则是把 `(item, i) in list` 用一条正则剖开：`/([\s\S]*?)\s+(?:in|of)\s+([\s\S]*)/`，左边是别名（item、i、key——注意真 Vue 的第三参是 index，mini 此处只是命名差异），右边是数据源表达式，变成 FOR 节点。codegen 阶段一行拼出 `_renderList`：

```ts
// packages/compiler-core/src/codegen.ts —— genFor
context.push(`${context.helper(RENDER_LIST)}(${source.content.trim()}, (`)
context.push(params.join(', '))   // item, i, key
context.push(`) => `)
genNode(children[0].codegenNode, context)
context.push(`)`)
```

### 三、codegen：把 AST 拼成一段函数源码

codegen 就是一个按节点类型分发的字符串拼接器，产物是「函数源码字符串」。这里我做了整条复刻里最大的一个取舍：**用 `with (_ctx)` 包住整个函数体**。模板里的表达式（`msg`、`count++`）不经过任何改写，原样输出进 `with (_ctx)` 块里，运行期靠 `with` 的作用域把变量命中到 `_ctx` 上。对一次实验性质的复刻来说，这是把表达式处理砍到零成本的路。

```ts
// packages/compiler-core/src/codegen.ts —— generate 骨架
push(`const { ${usedHelpers.map(h => `${helperNameMap[h]}: _${helperNameMap[h]}`).join(', ')} } = Vue`)
push(`return function render(_ctx, _cache) { with (_ctx) { return `)
// ...逐节点拼接...
```

一段真实产物长这样（`{ id: "app" }` 的 props 里写法我做了格式简化，结构完全一致）：

```ts
const { createCommentVNode: _createCommentVNode, toDisplayString: _toDisplayString,
        createElementVNode: _createElementVNode, renderList: _renderList,
        openBlock: _openBlock, createElementBlock: _createElementBlock } = Vue
return function render(_ctx, _cache) {
  with (_ctx) {
    return _openBlock(), _createElementBlock("div", { id: "app" }, [
      (ok) ? _createElementVNode("p", null, _toDisplayString(msg), 1)
           : _createElementVNode("p", null, "none", -1),          // 嵌套三元 = v-if/else
      _renderList(list, (item, i) =>
        _createElementVNode("li", { key: i }, _toDisplayString(item), 9, ["key"]))
    ], -1)
  }
}
```

看产物：v-if 是嵌套三元，v-else 分支里 `none` 是全静态文本所以 patchFlag 是 -1，v-for 是 `_renderList(list, (item, i) => ...)`，插值包了 `_toDisplayString`。静态提升也顺手做了：全静态子树被预扫描成 `const _hoisted_1 = ...vnode...`，跨渲染复用同一个 vnode——渲染器见 n1 === n2 直接跳过 patch。

代价实打实：`with` 是 sloppy mode 特性，整个 render 不能开 strict mode，打包器也对 `with` 皱眉。官方方案是 `prefixIdentifiers`：把每个标识符显式编译成 `_ctx.msg`，完全不碰 `with`，还能把跟 `_ctx` 无关的常量提升出函数体外——这笔账我记成了「未来升级项」。

### 四、compileToFunction：最后一脚 new Function

源码字符串离 run 只差一步——实例化。聚合包的编译入口是这样收尾的：

```ts
// packages/vue/src/index.ts
export function compileToFunction(template: string, options?: CompilerOptions) {
  const { code } = compile(template, options)
  const render = new Function('Vue', code)(runtimeDom) // 注入运行时模块
  render._rc = true                                    // 标记编译产物
  return render
}
registerRuntimeCompiler(compileToFunction)             // 让 template 选项可用
```

`new Function('Vue', code)` 造一个匿名函数，`code` 就是上一节那段源码——它顶部 `const {...} = Vue` 解构了需要的 helpers，所以实例化时只要喂一个 `Vue` 参数（整个 runtime-dom 聚合模块）。`registerRuntimeCompiler` 把编译能力登记进运行时，此后 `createApp({ template: '...' })` 也走这条路。

### 五、编译期 / 运行期分工

一次 API 切换：运行时组件在 `h` 里拿到的是编译好的 render；`createApp` 只认 render，不知道模板存在。能上提给编译期的事（v-if 变三元、静态盘点成 hoist、patchFlag 预算），编译期全干完；必须留运行期的事（响应式依赖收集、真实 DOM diff、生命周期），编译器一行都不碰。整条链路大致是 `模板 → (parse) AST → (transform) 改写AST+优化 → (codegen) 源码 → (new Function) render`，编译器全程不认识你的组件，只用 helper 符号跟运行时「对暗号」——运行时同名函数补齐即可。

## 动手验证

仓库里 `@mini-vue/*` 已通过 pnpm workspace 就绪，最小验证是编译一段模板、看产物：

```ts
// 仓库根目录开个 spec 文件，或 node -e 直接跑
const { compile } = require('@mini-vue/vue')   // @mini-vue/vue 再导出 compile
const { code } = compile('<p v-if="ok">{{ msg }}</p><li v-for="(item, i) in list" :key="i">{{ item }}</li>')
console.log(code)
```

输出就是第三节那种形态：v-if 变成 `(ok) ? ... : ...`，v-for 变成 `_renderList(list, (item, i) => ...)`。再近一步，直接拿到可调用的 render：

```ts
const { compileToFunction } = require('@mini-vue/vue')
const render = compileToFunction('<p class="t">{{ msg }}</p>')
const vnode = render({ msg: 'hello' }, [])   // 第一参是 _ctx，第二参是 cache
// vnode.type === 'p'，vnode.props === { class: 't' }，vnode.children === 'hello'
```

打开页面、把 `msg` 换成 `ref`，响应式那一套会自动接上——编译器到此功成身退，后面的故事全归渲染器。

## 真实踩过的坑

1. **插值解析的下标偏移。** 解析 `{{ msg }}` 时，`closeIndex` 是在「还没 advance」的源串上算出来的；等你 `advanceBy` 掉开头的 `{{` 之后，滚动源已经短了 2 个字符，如果直接 `slice(0, closeIndex)`，内容前面会多出两个字符。正确写法是 `slice(0, closeIndex - open.length)`。这个经典错位在我复刻时真实出现过，输出一度是 `{{ msg` 这样诡异的内容。

2. **v-else 删除节点差点删错人。** transform 的遍历是深度优先、内层子节点的遍历会改写 `context.childIndex`，所以 v-else 若在退出阶段用 childIndex 去 splice，很可能把别的兄弟删了。我最后改成 `indexOf(node)` 身份查找：在啥都改之前定位，再到退出时按引用删——退出钩子里再想用坐标，已经「时移世易」了。

3. **静态提升的自引用陷阱。** 提升出的 `const _hoisted_N` 在生成自身的表达式时，节点上还挂着 `_hoistedId` 标记，`genVNodeCall` 检测到标记就直接短路输出 `_hoisted_N`——于是生成了 `const _hoisted_1 = _hoisted_1`。修法是生成 const 时先揭掉标记再拼，拼完再挂回去。另有一个边界：动态 props（如 `:age`）绝不能进提升，否则表达式会在 `with` 作用域外面被求值，直接 ReferenceError。

## 三步走复盘

- **机制怎么串**：parse 用「吃掉开头、看清剩下」的状态机把模板滚成 AST；transform 进/出两阶段把声明改写成可执行结构（v-if 折叠成 branches、v-for 换成 renderList）；codegen 拼出 `with(_ctx)` 包裹的函数源码；最后一脚 `new Function` 实例化成 render。
- **复刻第一行**：`advanceBy(context, n)`——先让光标能往前走，整个解析器就是围着它转的循环；跑通 `<div>{{ msg }}</div>` 的最小 parse，再一层层加 transform 与 codegen。
- **讲给同事听**：「编译器就是一台把模板字符串重写成 JS 源码的字符串拼接器，运行时只认它留下的 helper 暗号。」
